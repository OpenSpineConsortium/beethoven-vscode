# Deep research: running Claude Code for students on the Wayne State grid
Generated 2026-09-28 from a 173-agent research workflow (8 topics, one web-researching agent each; every finding marked *critical* was then handed to an independent verifier told to refute it). 136 agents finished; 37 verifiers (all of the VS Code topic, most of the container topic's second half, and the final critic) died on the Claude usage limit, so findings without a verdict below are **unverified**. Raw data: `docs/research/deep_research_2026-09-28.json`. This file is generated by a script from that JSON; the design decisions it fed are in `ARCHITECTURE.md`.

The product was called Ashley when this research ran; it is Beethoven for VS Code since 4.0.0 (2026-09-30). The topics, findings and recommendations below are the research record and keep the words the research used, the old name included.

## How the findings shaped the design (version 1, when the product was Ashley)
- The worker runs `claude -p ... --output-format stream-json` inside a Debian 12 container because the native binary's Linux floor (Ubuntu 20.04 / Debian 10) is above CentOS 7's glibc 2.17.
- The grid credential is a `claude setup-token` token in `CLAUDE_CODE_OAUTH_TOKEN`; the daemon never passes `--bare` (it would ignore that token) and treats a 401 as "regenerate the token", not "retry".
- One student, one token: the Consumer Terms and the Agent SDK terms forbid sharing accounts or offering claude.ai login/limits to others, so rotation is only among a student's own credentials.
- Rate limits are read from the `-p` result (`is_error`, text) and answered with a cooldown; `claude -p` draws from the subscription's own window.
- Sessions are files under `<CLAUDE_CONFIG_DIR>/projects/<cwd>/<uuid>.jsonl`; Anthropic advises against sharing `~/.claude` over network filesystems, which our per-account directories on the shared home do. Mitigation: exactly one worker job per account (`--dependency=singleton`), and the caveat is stated in the manual.
- The file queue was chosen over `--input-format stream-json` long-lived processes: simpler failure modes on a preemptable queue; the stream mode remains the documented path if latency must drop below the ~5 s start-up.
- VS Code Remote-SSH on the grid follows C&IT's sysroot variables; the VS Code topic's findings are unverified, so the manual cites C&IT's page rather than the workflow for that.
- Xcode: no host for a wizard; the port is the CLI plus the MCP server.
- Since version 2 the grid credential is no longer a token Beethoven handles: the student signs in through Claude Code's own flow and Claude Code keeps the credential (`ARCHITECTURE.md`, "Credentials"); the setup-token bullet above describes version 1.

## Claude Code headless / non-interactive CLI reference (flags, JSON schemas, stream-json stdin protocol, env vars, setup-token, session storage, failure semantics) as of docs current on 2026-09-27 (docs reference Claude Code v2.1.283)
The official reference for non-interactive use is code.claude.com/docs/en/headless plus cli-reference, and both were current to v2.1.283. `claude -p` exits 0 on success and non-zero on failure (143 on SIGTERM); `--output-format json` returns one object whose success arm carries `result`, `session_id`, `total_cost_usd`, `duration_ms`, `duration_api_ms`, `num_turns`, `usage`, `modelUsage`, `permission_denials`, `structured_output`, `stop_reason`, and whose error arm (subtypes `error_max_turns`, `error_during_execution`, `error_max_budget_usd`, `error_max_structured_output_retries`) has no `result` key but has `errors: string[]`. `--input-format stream-json` (with `--output-format stream-json --verbose`) turns the process into a long-lived NDJSON loop: each stdin line is `{"type":"user","message":{"role":"user","content":<string|blocks>}}`, each turn emits its own `result`, and the process ends when stdin closes; the CLI-level envelope is not formally documented (Anthropic closed the docs request as not-planned) but the SDK's `SDKUserMessage` type and a Sept-2026 bug report confirm the shape and a `control_request`/`control_response` interrupt channel. Permission modes for `-p` are `default|acceptEdits|plan|auto|dontAsk|bypassPermissions|manual`; `-p` starts in `default` on every plan; `--dangerously-skip-permissions` is refused as root/sudo unless a recognized sandbox is detected; `--permission-prompts none` (v2.1.259+) prevents hangs on prompts. `--bare` (recommended for scripts, future default) never reads OAuth or `CLAUDE_CODE_OAUTH_TOKEN`, so a subscription-backed design must not pass it. `claude setup-token` prints (does not store) a one-year OAuth token for Pro/Max/Team/Enterprise, consumed via `CLAUDE_CODE_OAUTH_TOKEN`; it is not refreshed after a 401, so expiry means regenerate and restart. Transcripts live at `<CLAUDE_CONFIG_DIR|~/.claude>/projects/<cwd with non-alnum→'-'>/<session-id>.jsonl`, `--resume <uuid>` finds them across projects (v2.1.223+), retention is `cleanupPeriodDays` default 30, and Anthropic explicitly does not recommend sharing `~/.claude` across machines or network filesystems. On policy, a support article dated 2026-06-16 says `claude -p`/Agent SDK usage still draws from the subscription's usage limits (the announced separate credits were paused), while the SDK overview forbids third-party developers from offering claude.ai login or rate limits in their products without approval. The native binary needs no Node.js but the documented Linux floor is Ubuntu 20.04/Debian 10, well above CentOS 7.9's glibc 2.17, so the CLI must run inside the container image, not on the host.

**Recommendation for Ashley.** Run one persistent process per student inside the Singularity container (never on the CentOS 7.9 host: the binary's documented floor is Ubuntu 20.04/Debian 10) as the student's own non-root UID, launched as: `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompts none --permission-mode acceptEdits --allowedTools "Bash(sbatch *)" ... [--add-dir ...] [--max-budget-usd N]` and optionally `--session-id <uuidv4>` you generate so the laptop knows the id before the first `result`. Do NOT pass `--bare` (it refuses OAuth and `CLAUDE_CODE_OAUTH_TOKEN`), do NOT set `ANTHROPIC_API_KEY` in the job environment (it silently overrides the subscription in `-p`), and avoid `--dangerously-skip-permissions` (refused as root, and the docs reserve it for isolated containers; if used, run as a normal user and understand `IS_SANDBOX`). Feed prompts as one NDJSON line each: `{"type":"user","message":{"role":"user","content":"..."}}` (content may be a block array with base64 images); treat every `{"type":"result",...}` line as end-of-turn keyed by `session_id`, read `subtype` before `result` (the key is absent on error/interrupted turns), and keep the process alive by keeping stdin open; close stdin to exit cleanly, send SIGINT to end a turn, and expect exit 143 on SIGTERM. Use `{"type":"control_request","request":{"subtype":"interrupt","request_id":"..."}}` for cancel only as best-effort (feature-detect via `system/init`.`capabilities`), since the CLI-level control protocol is undocumented. Authenticate with `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` run on the student's laptop (one-year token, Pro/Max/Team/Enterprise only, not refreshed after 401, so the extension must detect `authentication_failed`/`OAuth token revoked` and prompt re-mint); keep the token in the job's environment, not in a settings file on shared storage. Put `CLAUDE_CONFIG_DIR` on the student's CephFS path (e.g. `/rs/rs_grp_oschome/<id>/.claude`) with `CLAUDE_CODE_TMPDIR` off the swept `/tmp`, set `DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `CLAUDE_CODE_AUTO_CONNECT_IDE=0`, pin the binary version in the image, and note Anthropic's statement that `~/.claude` is not recommended on network filesystems: one writer per config dir at a time, and resume after a job restart with `claude -p --resume <session-id>` (which searches all projects under that config dir) rather than sharing a live transcript. Set `cleanupPeriodDays` high (e.g. 3650) if transcripts must outlive 30 days. Before shipping, get written clarification from Anthropic on whether a university-distributed extension that wraps each student's own subscription falls under "third party developers ... offer claude.ai login or rate limits", because that note is the single largest policy risk; the 2026-06-16 support article confirms `claude -p` draws on the subscription's own usage limits.

**Open questions:** The CLI-level stdin protocol for `--input-format stream-json` (user envelope, control_request/control_response for interrupt, set_permission_mode, initialize) is not in Anthropic's docs (issue #24594 closed not-planned); the shapes above come from the SDK's TypeScript types and a Sept-2026 bug report and should be verified against the pinned binary version before relying on interrupt.; No numeric glibc minimum is published for the native binary; the container image's glibc must be tested (Ubuntu 20.04+/Debian 10+ documented; CentOS 7.9's 2.17 is presumed unsupported).; Whether a single `CLAUDE_CONFIG_DIR` on CephFS/Panasas (network FS) is safe for one long-lived writer plus occasional `claude -p --resume` readers is unverified; Anthropic says sharing `~/.claude` over network filesystems is not recommended but gives no failure mode.; Whether a university-distributed VS Code extension that drives `claude -p` with each student's own Pro/Max token counts as a 'third party developer offering claude.ai login or rate limits' under the Agent SDK overview note needs written confirmation from Anthropic; press reports describe active enforcement against third-party harnesses in 2026.; Behavior of a 30-day-wall process when the subscription's 5-hour/weekly usage window is exhausted (rate_limit error category vs. process exit) is not documented for stream-json input mode.; Whether `claude setup-token` can complete over an SSH session without a browser on the same machine (the `/login` flow has a 'Paste code here if prompted' fallback; setup-token is said to use the same flow but the fallback is not stated for it) — plan to mint the token on the laptop and ship it to the job environment.; `--session-id` is documented in the raw CLI reference as 'must be a valid UUID'; whether a v4 UUID generated by the extension is accepted for a brand-new session in `-p --input-format stream-json` (vs. only for resume) should be tested.; The docs say `--bare` 'will become the default for `-p` in a future release'; if that lands, subscription-backed `-p` would break unless an opt-out flag exists — pin the binary version and watch the changelog.

## Claude Pro/Max subscription rate limits, Claude Code -p limit behaviour, extra usage, concurrency, and the Consumer Terms / Usage Policy / Claude Code legal page as they bear on running a student's Claude Code persistently on an HPC node (and on a lab pooling subscriptions)
Pro and Max quotas are per-account rolling allowances: a five-hour session window plus a weekly window that resets at a fixed time assigned to the account, shared across claude.ai, Desktop, Cowork and Claude Code, with additional model-family (Opus/Sonnet) windows; usage credits ("extra usage", formerly pay-as-you-go) can be enabled by the subscriber at claude.ai Settings > Usage and are billed at standard API rates with a monthly spend limit, and they apply to Claude Code. When a window is exhausted the CLI prints one of four documented strings ("You've hit your session limit · resets 3:45pm", "... weekly limit · resets Mon 12:00am", "... Opus limit ...", "... Sonnet limit ...") and blocks requests until the reset; the stream-json protocol emits a `rate_limit_event` with `status: "rejected"`, `resetsAt`, `utilization` and, when included usage is gone and credits are off, `errorCode: "credits_required"`; the final `result` message carries `is_error` and `api_error_status` (HTTP status), and a failed `-p` run exits non-zero with the failure text placed in the `result` field on stdout. The documented `-p` JSON body for a subscription limit is not spelled out verbatim anywhere I could fetch, so that exact payload must be captured empirically. `--fallback-model` does not help: the model-config page says rate-limit, billing and authentication errors "never trigger a switch". The interactive auto-continue-at-reset feature (`autoContinueAtUsageLimit`, v2.1.234+) is documented for interactive claude.ai-signed-in sessions only, so an unattended worker must implement its own wait using `resetsAt`. Nothing in the docs or terms forbids one person running several Claude Code sessions or machines on one subscription; they share the same quota, and GitHub issue #96872 shows an infrastructure 429 ("Rate limited", `rateLimits: null`) appearing at 6+ concurrent sessions at only 27% quota. Headless use of a subscription is explicitly sanctioned: `claude setup-token` mints a one-year OAuth token for "CI pipelines, scripts, or other environments where interactive browser login isn't available", set as `CLAUDE_CODE_OAUTH_TOKEN`, requiring Pro/Max/Team/Enterprise, and not read in `--bare` mode. The legal side is unambiguous against pooling: the Consumer Terms say "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else. You also may not make your Account available to anyone else"; the Claude Code legal page says OAuth is "intended exclusively for purchasers" of subscription plans "to support ordinary use", that "Advertised usage limits for Pro and Max plans assume ordinary, individual usage", that customers "may not pay for, resell, or intermediate Claude usage on their end users' behalf", and that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." The Consumer Terms contain no explicit multiple-accounts or "rate limit" clause; the operative anti-circumvention text is "bypassing any of our systems or protective measures" (Consumer Terms) and the AUP's ban-evasion and multi-account-coordination clauses. Legitimate shared routes are Team seats (2-150 seats; Standard $20-25 at 1.25x Pro, Premium $100-125 at 6.25x Pro, per-member limits, admin spend limits on usage credits), Enterprise (seat + usage at API rates), Console API keys with workspace spend/rate limits and a per-user-capped "Claude Code" workspace, and the institution-level Claude for Education plan (contact sales; no individual student price is published).

**Recommendation for Ashley.** 1) Architecture: one persistent worker per student, authenticated only with that student's own credential; never a shared or lab-owned pool of student subscriptions. The sanctioned pattern in Anthropic's own text is "an end user ... signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code". 2) Credential handling in the Ashley extension: do not have the extension collect, store or relay the Claude.ai OAuth token or session cookies ("developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow"). Instead, have the extension open a terminal on the compute node (or locally) and let the student run `claude setup-token` (one-year token) or `claude` + `/login` (paste-code flow works over SSH/containers); the student writes the token into their own grid home (e.g. `~/.claude/env` or `~/.bashrc`, mode 0600) and the Slurm job exports `CLAUDE_CODE_OAUTH_TOKEN` from there. Prefer setup-token over `/login` for a 30-day job because `/login` credentials expire and refresh, and an unattended session "stops making progress once the credential expires". Ensure `ANTHROPIC_API_KEY` is unset in the job (it silently takes over billing in -p mode) and do not pass `--bare` (it ignores `CLAUDE_CODE_OAUTH_TOKEN`). 3) Limit handling in the worker: run with `--output-format stream-json --verbose`, watch for `rate_limit_event` (`status: "rejected"`, `resetsAt`, `errorCode: "credits_required"`) and the result's `is_error`/`api_error_status`; on a rejection, park the queue until `resetsAt` and surface "You've hit your session/weekly limit · resets …" to the student in VS Code; do not rely on `--fallback-model` (documented as never triggering on rate-limit/billing errors) or on the interactive auto-continue (documented for interactive sessions only). Poll `/usage`-style data sparingly (the usage endpoint itself rate-limits). Keep concurrency per student low (one worker, few subagents): issue #96872 shows infra 429s at 6+ concurrent sessions even at 27% quota. 4) Capacity: tell students Pro/Max windows are 5-hour + weekly and are shared with their claude.ai chat; offer the documented overflow: enable usage credits at claude.ai Settings > Usage with a monthly spend limit (Pro/Max only), which the CLI exposes via `/usage-credits`. 5) For the lab/program itself, use the legitimate shared routes: a Claude Team plan (2+ seats, Premium seats 6.25x Pro, per-member limits, admin spend limits, `forceLoginOrgUUID` to pin logins), or Console API keys in a workspace with spend and rate limits (the auto-created "Claude Code" workspace supports per-user monthly caps and Claude-Code-only roles), or ask WSU to negotiate Claude for Education, which includes Claude Code institution-wide. Under any org plan the same rule holds: one seat/key identity per student, billed to the org, not one student's subscription serving others. 6) Before shipping, capture empirically the exact `claude -p --output-format json` payload and exit code at a real subscription limit (not documented verbatim), and note issue #87983's `is_error:false`-with-no-`result` envelope so the worker treats a missing `result` as failure.

**Open questions:** Exact `claude -p --output-format json` body (result text, is_error, subtype, api_error_status) and process exit code when a Pro/Max subscription 5-hour or weekly limit is hit on Claude Code 2.1.283 — no official page states it verbatim; must be captured by running a -p call at the limit.; Whether the interactive auto-continue-at-reset (`autoContinueAtUsageLimit`) has any effect on `-p`/stream-json runs; docs describe it only for interactive claude.ai-signed-in sessions.; The lifetime of a `/login` OAuth credential (docs give a 3-day expiry warning and refresh semantics but no absolute lifetime) versus the stated one-year `setup-token` lifetime; and whether a setup-token can be revoked from claude.ai if a student's grid home is compromised (revocation path not documented on the pages fetched).; Whether an extension that merely launches `claude setup-token` in a terminal and lets the student paste the token into their own dotfile counts as 'collect, store, or intermediate Claude.ai credentials' — the legal page's wording targets third-party developers routing requests for their users; a written answer from Anthropic sales/legal (contact-sales link on the legal page) would settle it for a university deployment.; The undocumented concurrent-session/infrastructure 429 ('Rate limited', rateLimits: null) reported from ~2026-09-16 at 6+ simultaneous sessions (issue #96872) — no maintainer statement yet on per-plan concurrency caps.; Whether WSU already holds a Claude for Education or Team/Enterprise agreement (which would change both the terms — Commercial vs Consumer — and the login-restriction settings the extension should ship).; Whether the Consumer Terms were revised after October 8, 2025 in a way not captured by the fetched page (the page shows 'Effective October 8, 2025' with a 'Previous Version' link only).

## Running Claude Code inside Singularity/Apptainer on a Slurm compute node whose host is CentOS 7.9 (glibc 2.17, kernel 5.15)
Claude Code is now a single Bun-based native ELF binary on Linux; since v2.1.113 the npm package ships the same binary with no JavaScript fallback, so "npm vs native installer" is not a glibc escape hatch. Official requirements list Ubuntu 20.04+/Debian 10+/Alpine 3.19+ (no RHEL/CentOS 7); the native installer performs no glibc check; a user diff shows 2.1.243 raised the maximum required symbol from GLIBC_2.17 to GLIBC_2.26, and 2.1.176 already SIGILLed on a CentOS 7.9/glibc 2.17 host. Running on the host is therefore not viable; running inside a node:22-bookworm (glibc 2.36) container is, because Apptainer/Singularity containers share only the host kernel (5.15 satisfies Bun's 5.6 recommendation) and use the image's glibc. Claude Code writes to ~/.claude (transcripts, credentials 0600, shell snapshots, plugins), ~/.claude.json (OAuth session, trust), and /tmp/claude-<uid>; CLAUDE_CONFIG_DIR moves all of the first two, CLAUDE_CODE_TMPDIR moves the third, DISABLE_AUTOUPDATER=1 stops writes to ~/.local/share/claude. Apptainer pulls docker:// images to SIF unprivileged (no root/fakeroot), binds $HOME, CWD, /tmp, /var/tmp, /proc, /sys, /dev by default, uses the host network namespace unless --net, and honours APPTAINERENV_/SINGULARITYENV_ prefixes plus --env/--env-file in both 3.8 and 1.2; critically, non-setuid Singularity 3.8 must extract every SIF to a sandbox directory per run and cannot use --writable-tmpfs, whereas Apptainer 1.1+ mounts SIF with bundled squashfuse and, on kernel >=5.11, uses unprivileged kernel overlayfs, so the apptainer/1.2.2 module is the right runtime. --dangerously-skip-permissions is refused for uid 0 (so never --fakeroot), and Anthropic's own devcontainer docs endorse it for a non-root user inside a container. Subscription auth works headlessly via the paste-code login flow or a one-year `claude setup-token` in CLAUDE_CODE_OAUTH_TOKEN; that token cannot start Remote Control, which needs a full /login and Pro/Max/Team/Enterprise, uses outbound HTTPS polling only, and must live in tmux/screen. No published report of Claude Code inside Apptainer was found; the closest are HPC-center pages (JHPCE, CU Neurology, Anthropic's own SLURM+tmux write-up) and issue #42952 (Bash tool shell-snapshot failure under HPC cgroups). Slurm facts verified verbatim: pam_slurm_adopt denial strings and its PrologFlags=contain requirement, srun --x11 (no --x11 on sbatch), --signal=B:USR1@N semantics (up to 60 s early, batch-shell only, needs background+wait+trap), --requeue vs PreemptMode=REQUEUE, --dependency=singleton, and srun --jobid --overlap --pty as an ssh alternative. VS Code adds a second glibc wall: VS Code Server 1.99+ needs glibc >=2.28, so Remote-SSH must land inside the container via `RemoteCommand` + `remote.SSH.enableRemoteCommand`, and the Claude Code VS Code extension bundles its own native binary that would also fail on the host.

Run it inside a container built from docker://node:22-bookworm (glibc 2.36), pulled unprivileged with the apptainer/1.2.2 module (not the conda Singularity 3.8.6, which must unpack the SIF to a sandbox on every run and cannot use --writable-tmpfs); set APPTAINER_CACHEDIR and APPTAINER_TMPDIR to CephFS before pulling. ## Claude Code multi-account / multi-profile management: credential storage, refresh-token rotation, CLAUDE_CONFIG_DIR, claude setup-token, community switchers, rate-limit detection in -p mode, Remote Control vs Claude Code on the web, and Anthropic's policy on accounts and credential handling (state as of 2026-09-27, Claude Code 2.1.28x docs)
On Linux, Claude Code keeps the subscription login in `$CLAUDE_CONFIG_DIR/.credentials.json` (default `~/.claude/.credentials.json`, mode 0600) under a `claudeAiOauth` object with `accessToken`, `refreshToken`, `expiresAt` (epoch ms, ~8 h), `refreshTokenExpiresAt` (~28-30 days), `scopes`, `subscriptionType` and `rateLimitTier`; macOS uses the Keychain item `Claude Code-credentials` and falls back to the same file when the Keychain is locked (e.g. in an SSH session). Refresh tokens are single-use and rotate on every refresh: three independent official-repo issues describe the race in which the second process to present the old refresh token gets `401 Invalid authentication credentials` and Claude Code then clears the stored credential, so a copied `.credentials.json` on a second machine does not keep working alongside the original; refreshing also does not extend the login's ~30-day server-side lifetime. `CLAUDE_CONFIG_DIR` gives a fully separate profile (settings, sessions, plugins, `.credentials.json`, and a Keychain entry keyed to that directory), which is the mechanism every community switcher ultimately relies on and the resolution Anthropic accepted for issue #261. `claude setup-token` mints a one-year `sk-ant-oat01-…` OAuth token that is printed, not stored; it is consumed via `CLAUDE_CODE_OAUTH_TOKEN`, is always used in `-p` mode, is not read in `--bare` mode, can only make model requests (no Remote Control, no claude.ai connectors), and can be revoked only one-by-one at claude.ai → Settings → Claude Code (no CLI; one April-2026 report says revocation did not take effect). The community tools differ: `claude-swap` (PyPI, `pipx install claude-swap`, command `cswap`) swaps the credential file/Keychain item under Claude Code's own credential locks and auto-rotates accounts at 90% of the 5-hour/7-day windows; `cc-switch` (ccswitch.io) is a Tauri GUI that needs glibc 2.35+ and targets API-key/relay providers; `ccswitch` (BNhashem16) is a bash script that backs up and restores the credential file; npm `claude-profiles` swaps settings/MCP/commands only and explicitly shares auth. In `-p` mode a usage-limit hit surfaces as a non-zero exit with `You've hit your session limit · resets 3:45pm` (or weekly/Opus/Sonnet) in the `result` field, and with `--output-format stream-json` a `system/api_retry` event carries `error: "rate_limit"`; an expired login yields `Failed to authenticate: OAuth session expired and could not be refreshed` with structured code `authentication_failed`; the interactive auto-wait (`continuing automatically at …`) is not offered in `-p`. Live quota can be polled at `GET https://api.anthropic.com/api/oauth/usage` (`anthropic-beta: oauth-2025-04-20`) returning `five_hour`/`seven_day` `{utilization, resets_at}`. Remote Control (`claude remote-control` server mode, `claude --remote-control`, `/rc`) keeps the session on the local machine, uses outbound HTTPS only to api.anthropic.com, needs a full-scope claude.ai login (not a setup-token, not an API key), and the docs explicitly say to run it inside tmux/screen on a remote SSH machine, so it could steer a Slurm-hosted session, but the login must be renewed interactively every ≤30 days. Claude Code on the web runs on Anthropic-managed VMs cloned from GitHub (self-hosted environments are Team/Enterprise only) and cannot reach an HPC node. Anthropic's consumer terms forbid account sharing and automated access without an API key; the Claude Code legal page says usage limits "assume ordinary, individual usage", that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow", but that nothing prevents "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code".

**Recommendation for Ashley.** 1. Never collect, copy or relay the student's Claude credential. Ashley must not scp `.credentials.json` to the grid, must not store the OAuth token in its own settings, and must not put a token-pooling proxy in front of api.anthropic.com. The legal page allows exactly one thing: the student signs in to the unmodified `claude` binary with their own subscription, through Anthropic's own flow. Design the extension to open a terminal on the compute node (inside the Singularity container) and let the student run the flow themselves; over SSH the browser shows a paste-code, which the docs cover. 2. Use two credentials on the grid, both minted by the student, both isolated with `CLAUDE_CONFIG_DIR` set to a per-student directory on CephFS or home (never /tmp) so the grid never shares a refresh-token family with the laptop: (a) for the persistent `-p` worker, `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN` in the job's environment (one year, always used in -p, do not pass `--bare`, do not route it through apiKeyHelper); (b) only if Remote Control is wanted, a full `claude auth login` in that same `CLAUDE_CONFIG_DIR`, run inside tmux/screen in the Slurm job with `claude remote-control --name <student>-<jobid>`; tell the student it dies at ≤30 days and must be renewed by hand. 3. Do not treat Remote Control or Claude Code on the web as a replacement for the SSH bridge. Web/cloud sessions run on Anthropic VMs and cannot reach the grid. Remote Control can steer a grid session from a phone (outbound 443 only, docs sanction the tmux-on-SSH case) but is subscription-only, unattended-renewal-impossible, and stores transcripts on Anthropic servers; keep the SSH/shared-filesystem bridge as the primary channel and offer `/rc` as an optional extra. If a push channel into the container is wanted without SSH polling, a custom Channels webhook server (`--dangerously-load-development-channels server:<name>`, port 8788 reached through the existing SSH tunnel) works with a setup-token or API key and can relay permission prompts; note it is research-preview and container/host socket sharing is undocumented for Singularity. 4. Run the worker with `--output-format stream-json --input-format stream-json` (or `--resume <session_id>` per prompt) and implement failover on three signals: `system/api_retry` with `error` in {`rate_limit`, `overloaded`}; a final `result` with `is_error: true` whose `result` matches `You've hit your (session|weekly|Opus|Sonnet) limit · resets (.+)`; and `authentication_failed` / `Failed to authenticate: OAuth session expired and could not be refreshed`. On a plan limit, parse the reset time or poll `GET https://api.anthropic.com/api/oauth/usage` (`anthropic-beta: oauth-2025-04-20`) for `five_hour`/`seven_day.resets_at`, then either sleep until reset or restart the worker with `ANTHROPIC_API_KEY` set (it outranks OAuth in -p) using a lab or student Console key; on `authentication_failed`, stop and notify the student to re-run setup-token. Never fail over to a second subscription account of the same student: that is the limit-evasion pattern Anthropic acts on. 5. Do not depend on community switchers on the grid. cc-switch needs glibc 2.35 and a GUI; claude-swap/ccswitch swap the live credential file and would fight the running worker's refresh; npm claude-profiles does not switch accounts. For laptop-side profile separation, ship shell aliases over `CLAUDE_CONFIG_DIR`. 6. Surface `claude auth status` (exit 1 when not logged in; JSON `subscriptionType`, `email`) in the extension's health check, and warn students not to sign in to Desktop, VS Code and CLI on the same machine with different accounts because they share one `oauthAccount` slot.

## Persistent Claude Code worker accepting remote prompts (stream-json bidirectional mode), orchestration tools, IPC over shared/parallel filesystems vs sockets vs ssh tunnels, and orchestrator-to-N-worker fan-out/join, for the Ashley VS Code extension on the WSU grid
The bidirectional protocol is real, stable and used by Anthropic's own Agent SDK: start `claude` with `--input-format stream-json --output-format stream-json --verbose` (the docs describe both flags as print-mode flags and third parties report `-p` is now mandatory, so pass `-p`), feed one NDJSON line per user turn shaped `{"type":"user","message":{"role":"user","content":"..."},"parent_tool_use_id":null}` (the Python SDK also sends `"session_id":""`), and treat `{"type":"result",...}` as end of turn; the same process accepts unlimited further turns until stdin EOF, and Anthropic's SDK source says explicitly that "a result ends a turn, not necessarily the run." No official cold-start number exists; measured points range from ~0.7 s process boot (`claude -p` boot-to-ready 679 ms median, v2.1.251) to 20-74 s wall clock for a trivial `claude -p` on slow or unlucky hosts, with a documented 12.5 s stall from a failed startup config fetch, so a warm long-lived process is the only reliable way to get low latency, and the `result` event itself now carries `duration_ms`, `duration_api_ms`, `ttft_ms` and `time_to_request_from_spawn_ms` for measuring it. `--resume` re-sends the whole transcript; it is cheap only while the prompt cache is warm (1 h on a subscription within plan usage, 5 min on API billing), otherwise the full history is reprocessed. Of the orchestration tools, Agent Teams are interactive-only ("In non-interactive mode with the -p flag, including Agent SDK sessions, Claude doesn't spawn teammates") and single-machine (JSON mailboxes under `~/.claude/teams/`), claude-squad and ccmanager drive TTYs with tmux/PTY and worktrees, and claude-flow/Ruflo is a large MCP/CLI layer with 667 open issues; the built-in mechanisms that do work headless are subagents (in-process, 20 concurrent default) and dynamic workflows (`agent()/parallel()/pipeline()`, 16 concurrent default, allowed in `-p` via a `Workflow` permission rule). Anthropic's own same-machine IPC is a per-session Unix domain socket that even `claude -p` workers bind (not in `--bare`), and its cross-machine path goes through Anthropic servers via Remote Control, which requires an interactive claude.ai login and is not available to a `claude setup-token` token. For a shared-filesystem inbox, NFS is the weak case (close-to-open consistency, 3-60 s attribute cache, inotify blind to remote writes, O_EXCL atomic only on NFSv3+), whereas CephFS documents "strong cache coherency across clients" and PanFS DirectFlow claims "fully POSIX-compliant and cache-coherent" behaviour; an atomic rename plus polling is the portable pattern, and a `/dev/shm` Unix socket reached via `ssh -J warrior node socat STDIO UNIX-CONNECT:...` or an `ssh -L` tunnel (OpenSSH 6.7+ forwards Unix sockets, 7.3+ has ProxyJump) gives millisecond delivery. Authentication for the worker is `claude setup-token` -> `CLAUDE_CODE_OAUTH_TOKEN` (one-year, Pro/Max/Team/Enterprise), which `--bare` does not read; and the Agent SDK's license note forbids third parties from offering claude.ai login in their own products, which the design must weigh. The native Claude Code binary is a Bun single executable that has crashed (SIGILL/Bus error) on CentOS 7.9 glibc 2.17, so it must run inside the Singularity image with its own glibc, never on the host.

**Recommendation for Ashley.** Run ONE long-lived Claude Code process per student inside the Singularity image in the Slurm job, started as `claude -p --input-format stream-json --output-format stream-json --verbose --session-id <uuid> [--replay-user-messages] [--permission-mode acceptEdits|--allowedTools ...] --settings '{"crossSessionInbound":"accept"}'` with stdin attached to a PIPE held open by a small shim (never a PTY, never `--bare`, since `--bare` disables OAuth and `CLAUDE_CODE_OAUTH_TOKEN`). Authenticate with `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` (one-year, Pro/Max), stored 0600 on the shared home; set `DISABLE_AUTOUPDATER=1`, pin the CLI version in the image (glibc 2.17 on the host is unsafe for the Bun binary), and set `CLAUDE_CODE_MCP_STARTUP_WAIT_MS=0` unless MCP servers are needed. Each prompt from the laptop is one NDJSON line `{"type":"user","message":{"role":"user","content":"..."},"parent_tool_use_id":null}`; the extension streams `stream_event`/`assistant` lines to the UI and marks the turn done on `{"type":"result"}` (then waits briefly for a possible follow-on `system/init` if background tasks exist, or for a `session_state_changed: idle` event). For the laptop-to-node channel, prefer a Unix socket (or FIFO pair) in node-local `/dev/shm` owned by the shim, reached with `ssh -J warrior.grid.wayne.edu <node> socat STDIO UNIX-CONNECT:/dev/shm/ashley/<jobid>.sock`, using `ControlMaster auto`/`ControlPersist` so each send skips the double handshake; the equivalent `ssh -L <local>:/dev/shm/ashley/<jobid>.sock` Unix-socket forward through ProxyJump is a fine alternative if VS Code's Remote-SSH connection is already up. Use the shared filesystem only for durability and discovery (job registry, session id, transcript in `~/.claude/projects/...`, result JSON written to CephFS via write-to-temp then `rename()`, plus a `.done` marker), never as the low-latency prompt path: NFS attribute caches are 3-60 s, inotify is blind to remote writes, and Anthropic itself uses a Unix socket locally and its own servers cross-machine. Do not depend on Agent Teams (interactive-only) or on cross-machine Claude messaging (needs Remote Control, unavailable with setup-token). For fan-out, keep it inside the single worker first (subagents, 20 concurrent; dynamic workflows with `parallel()`/`pipeline()` approved via a `Workflow` allow rule in `-p`), and reach for multi-node only with Slurm job arrays (`--array`, `%N` cap) whose tasks run one-shot `claude -p --output-format json --json-schema ...` and drop results by atomic rename for the orchestrator to poll and join; guard every job with `--signal=B:USR1@120` so the shim can flush and stop cleanly before walltime. Measure cold start on the grid before design freeze: `time claude -p ok --output-format json` and read `duration_ms`, `duration_api_ms`, `ttft_ms`, `time_to_request_from_spawn_ms`; expect roughly 0.7 s process boot plus network fetches plus several seconds to first token, and treat any first-turn number under 3 s as unproven.

## VS Code extension engineering facts for the "Ashley" extension (vsce/bundling, extensionKind, extensionDependencies, SecretStorage, environmentVariableCollection, programmatic Remote-SSH, VS Code Server on glibc 2.17, headless tests on Windows, SSH FS alternative, Windows OpenSSH client)
The current @vscode/vsce is 4.0.0 (released 2026-09-14) and, like @vscode/test-cli 0.0.15 and @vscode/test-electron 3.1.0, requires Node >= 22, not 20; `vsce package --no-dependencies` ("Disable dependency detection via npm or yarn") is the documented pairing with an esbuild bundle that externalises only 'vscode' and .vscodeignores node_modules. An extension with a `main` entry and no `extensionKind` is deduced as `['workspace']` in VS Code's source, so Ashley must declare `"extensionKind": ["ui"]` or it will be installed onto the compute node's VS Code Server instead of the laptop; a `ui` extension's SecretStorage lives on the laptop (Electron safeStorage: DPAPI on Windows, Keychain on macOS, libsecret/kwallet or insecure basic_text on Linux; keytar removed in 1.83) and is "not synced across multiple machines". Source inspection shows a UI extension's `environmentVariableCollection` does reach remote terminals: every extension host's MainThreadTerminalService writes into one workbench EnvironmentVariableService whose `mergedCollection` is applied in TerminalProcessManager._resolveEnvironment for both local and remote `backend.createProcess` paths; `persistent` defaults to true and the collection is invalidated on uninstall, which is better than writing tokens into plain-text `terminal.integrated.env.linux`. For programmatic connection the only documented, collaborator-endorsed route is `vscode.openFolder` with `vscode-remote://ssh-remote+<user@host>/<path>` (or `vscode.newWindow` with `remoteAuthority`); `opensshremotesexplorer.emptyWindowInNewWindow` was removed in Remote-SSH 0.92.0 and the argument shape of `opensshremotes.openEmptyWindow` is undocumented. On glibc 2.17 the official FAQ workaround is real but "not an officially supported usage scenario": since VS Code 1.99 (PR #235232, merged 2025-03-10) `check-requirements-linux.sh` skips its glibc check whenever `VSCODE_SERVER_CUSTOM_GLIBC_LINKER` is non-empty and `code-server-linux.sh` runs `patchelf --set-rpath` then `--set-interpreter` on `$ROOT/node` only, requiring patchelf >= 0.18; the docs never say which shell file must export the variables, one 1.99.2 user with them in ~/.bashrc and useExecServer=true failed (closed not-planned), while Red Hat's bash carries the SSH_SOURCE_BASHRC patch so ~/.bashrc is plausibly read by Remote-SSH's non-interactive shell. Two premises in the task are wrong: CentOS 7.9's sshd (OpenSSH 7.4) has negotiated hmac-sha2 MACs since 5.9 and RSA/SHA-2 signatures since 7.2, so neither `MACs +hmac-sha1` nor `+ssh-rsa` is needed from a Windows 9.x client, and the Windows client's default MAC list still contains hmac-sha1 anyway. Headless testing on Windows does not exist as such: the CI recipe uses xvfb only on Linux and runs `npm test` bare on windows-latest, which has an interactive desktop session. SSH FS (Kelvin.vscode-sshfs) is alive (v1.27.0 published 2026-06-07, 78 open issues, ~790k installs) and needs no server binary, so it sidesteps glibc entirely, at the cost of having no remote extension host.

**Recommendation for Ashley.** Build Ashley as a Node-22 toolchain project (vsce 4.0.0, test-cli 0.0.15, test-electron 3.1.0), bundle with esbuild (external: ['vscode']) and package with `vsce package --no-dependencies`. Declare `"extensionKind": ["ui"]` explicitly — with a `main` entry and no declaration VS Code deduces `['workspace']` and would install Ashley onto the compute node's server. Declare `"extensionDependencies": ["ms-vscode-remote.remote-ssh"]` and ship through the Marketplace (dependencies are resolved from the gallery); for VSIX side-loads, install Remote-SSH first. Keep all five credentials in `context.secrets` (laptop-side safeStorage; on Linux/WSL guard against the basic_text fallback) and never in settings.json. Inject `HF_TOKEN`, `GITHUB_TOKEN` etc. via `context.environmentVariableCollection` with `persistent=true` and a `description`; source inspection says a UI extension's collection is applied to remote terminals too, but verify on the first Remote-SSH window (and check whether the hover reveals values) before relying on it. Open the compute-node window with `vscode.commands.executeCommand('vscode.openFolder', Uri.parse('vscode-remote://ssh-remote+<accessid>@<node>/<path>'), {forceNewWindow:true})` (or `vscode.newWindow` with `remoteAuthority`), not the undocumented `opensshremotes.*` commands; write a `Host wsu-node-*` block with `ProxyJump warrior.grid.wayne.edu` into `%USERPROFILE%\.ssh\config` (or a file named by `remote.SSH.configFile`), set `remote.SSH.remotePlatform` to linux for those hosts, raise `remote.SSH.connectTimeout` to 60, and set `remote.SSH.serverInstallPath` to an absolute CephFS path (no `${HOME}`/`~`). For glibc 2.17 the design must assume the unsupported-workaround path: Ashley's grid bootstrap should install patchelf >= 0.18 and a glibc-2.28 sysroot in user space, export the three `VSCODE_SERVER_CUSTOM_GLIBC_*` variables in BOTH `~/.bashrc` (above any interactive-return guard) and `~/.bash_profile`, verify with `ssh node 'echo $VSCODE_SERVER_CUSTOM_GLIBC_LINKER'`, try `remote.SSH.useExecServer=false` if the banner still reports the prerequisite failure, and pin the student's VS Code version in the docs since the workaround is officially unsupported; keep SSH FS as the documented fallback for file editing because it needs no server binary. Do not add `MACs +hmac-sha1` or `+ssh-rsa` to the Windows config; generate Ed25519 keys, fix ACLs with `icacls <key> /inheritance:r /grant:r "<user>:R"`, and load them into the Windows ssh-agent service. Run integration tests on windows-latest without xvfb (an interactive session is present) and on Linux with `xvfb-run -a`.

**Open questions:** Exact argument shape (if any) of `opensshremotes.openEmptyWindow` and of `remote-explorer.connectToRemoteInNewWindow`: both closed-source and undocumented; only `vscode.openFolder`/`vscode.newWindow` are confirmed.; Does the terminal hover for an extension env contribution display the variable VALUE (which would show a token on screen)? environmentVariableInfo.ts only renders `extensionName: description`; the mutator-level strings were not found and should be checked in a live window.; Which shell file Remote-SSH's non-interactive install shell reads on CentOS 7.9: the Red Hat SSH_SOURCE_BASHRC patch was confirmed in the c9s spec but the el7 spec and the GNU bash manual could not be fetched; issue #246375 shows ~/.bashrc failing for one 1.99.2 user with useExecServer=true. Needs an empirical test on warrior and on a compute node.; How `remote.SSH.serverInstallPath` keys are matched (ssh-config alias vs resolved hostname) — issue #8065 was never answered by maintainers; with per-job node names a wildcard may not work.; The default of `remote.SSH.connectTimeout` (15 s per HPC-centre pages and issues) and the semantics of `remote.SSH.lockfilesInTmp` on a node whose /tmp is swept were seen only in search snippets, not fetched official pages.; Whether patching only `$ROOT/node` suffices for all native components of the current server (node-pty spawn-helper, @parcel/watcher, ripgrep) on glibc 2.17 with kernel 5.15 — the FAQ claims it works but community reports include unresolved failures.; The inbox OpenSSH version on the students' Windows 11 builds (users report OpenSSH_for_Windows_9.5p2 on 24H2) and whether WSU's warrior sshd has been hardened away from OpenSSH 7.4 defaults.; Whether a Marketplace install of Ashley in a window that is already Remote-SSH-connected installs Remote-SSH locally as expected, and what happens on a machine without Marketplace access (VSIX side-load).; SSH FS marketplace 'last updated' could not be read from the listing; GitHub API dates (2026-06-07) are the basis for the maintenance claim.

## Xcode as a second host for the Ashley tool: Xcode 26.x/27 agentic coding, Source Editor Extension limits, Claude Code/Agent SDK in Xcode, and porting strategies (as of 2026-09-27)
Xcode 26.3 (RC 2026-02-03, macOS Sequoia 15.6+) added agentic coding with Anthropic's Claude Agent and OpenAI Codex built in, and exposed Xcode's own tools to any external agent over MCP via `xcrun mcpbridge`; Anthropic confirmed the in-Xcode agent runs on the Claude Agent SDK ("the same underlying harness that powers Claude Code", with subagents, background tasks and plugins). Xcode 26.6 (17F113, 2026-06-25) added Gemini and the Agent Client Protocol (ACP) so any ACP-speaking agent can be added via Intelligence > Agents > "Add an Agent"; Xcode 27 (27A266a, 2026-09-14, macOS Tahoe 26.6+, Apple silicon only) added agent plug-ins that bundle skills, MCP servers and ACP agent configurations, a filesystem security layer, and a preview `xcrun mcp-server` that works without an open workspace. Xcode has no general extension API for third-party wizards or commands: the only sanctioned extension point is the Source Editor Extension, which Apple documents as able to "read and modify the contents of a source file" and the selection, invoked from the Editor menu, one file at a time, sandboxed, no UI; tools like Copilot for Xcode escape this only through a non-sandboxed XPC service plus the Accessibility permission. Claude Code's official docs have no Xcode page (only VS Code and JetBrains), Xcode has no integrated terminal in any 26.3–27 release note, and Apple's documented path is to run Claude Code in Terminal.app and give it Xcode's tools with `claude mcp add --transport stdio xcode -- xcrun mcpbridge`. Custom MCP servers for Xcode's built-in Claude Agent are configured only via files under `~/Library/Developer/Xcode/CodingAssistant/ClaudeAgentConfig` (community-verified filename `.claude.json`, project-keyed `mcpServers`), not via the CLI's `~/.claude.json`, and Apple says these "only affect agents when you launch them in Xcode". Two Anthropic terms findings shape the design: the Agent SDK docs say third parties may not offer claude.ai login unless approved, and since 2026-06-15 subscription plans get only a small monthly Agent SDK credit ($20 Pro, $100/$200 Max) that also covers `claude -p`, so the persistent grid-side process should be the interactive `claude` CLI with a real `/login`, not an SDK or `-p` harness. Claude Code does not speak ACP natively (anthropics/claude-code#6686 closed as not planned); the maintained adapter is `@agentclientprotocol/claude-agent-acp`. The realistic Xcode port is a Developer-ID-signed, notarized Swift `MenuBarExtra` app embedding the shared TypeScript core compiled with `bun build --compile`, which (a) runs the credential/SSH/Slurm wizard, (b) registers an "ashley" MCP server for Xcode's Claude Agent and as an Xcode 27 plug-in, and (c) exposes the grid session as an ACP agent added through "Add an Agent" (26.6+). Shortcuts/Automator are viable only as launchers (`shortcuts run`), not as a credential UI.

**Recommendation for Ashley.** Treat Xcode as a *shell* host, not an extension host. Do not build an Xcode Source Editor Extension for Ashley: Apple limits it to text edits of one open file from the Editor menu, with no windows, settings, project or network flow. Recommended porting path, in order: (1) Keep the credential wizard, SSH ProxyJump writer and Slurm launcher in the shared TypeScript core and compile it once per platform with `bun build --compile --target=bun-darwin-arm64` (add `bun-darwin-x64` only if Intel Macs on Xcode 26.x matter; Xcode 27 is Apple-silicon only). Wrap it in a Swift `MenuBarExtra` app (macOS 13+, `LSUIElement`, `.menuBarExtraStyle(.window)`), signed with Developer ID, hardened runtime and notarized via `notarytool`; do not enable App Sandbox because the app must write `~/.ssh/config`, run `ssh`/`sbatch`, and write into `~/Library/Developer/Xcode/CodingAssistant/`. (2) Have the app install an "ashley" MCP server (stdio; tools such as provision_credentials, write_ssh_config, submit_grid_job, send_prompt, read_reply) for Xcode's built-in Claude Agent by writing `~/Library/Developer/Xcode/CodingAssistant/ClaudeAgentConfig/.claude.json` (project-keyed `mcpServers`, absolute paths, restart Xcode) and, for Xcode 27+, package the same server as an agent plug-in (JSON with `mcpServers`, `_meta.ideToolIconPath`) installable via Intelligence > Plug-ins > Add from URL; also register it for the student's terminal Claude Code with `claude mcp add --transport stdio ashley --scope user -- /abs/path/ashley-core mcp`. (3) On Xcode 26.6+, expose the grid-side Claude Code as an ACP agent: ship an `ashley-acp` binary (JSON-RPC over stdio, forwards prompts over the existing ProxyJump SSH to the grid session and streams results back) and register it through Intelligence > Agents > Add an Agent with an absolute Command path and Arguments; this gives students a "Grid Claude" entry in the coding-assistant picker without any Accessibility hacks. (4) For the grid-side persistent process, run the interactive `claude` CLI (tmux/`script`, `/login` with the paste-code flow, credentials in `~/.claude/.credentials.json`), and offer Remote Control (`claude remote-control --name`, outbound HTTPS only, Pro/Max) as the second prompt channel; do NOT build the daemon on the Agent SDK or on `claude -p`/`--input-format stream-json` with subscription auth until the Agent-SDK-credit accounting is confirmed, since Anthropic's terms forbid third-party claude.ai login on the SDK and the June-2026 credit is only $20/month on Pro; use `CLAUDE_CODE_OAUTH_TOKEN` only for model-request-only helpers, never for Remote Control. (5) Skip Automator; use Shortcuts/App Intents only as optional launchers (`shortcuts run`), and tell students that "Claude Code in Xcode's terminal" means Terminal.app with `claude mcp add --transport stdio xcode -- xcrun mcpbridge` and the project open in Xcode.

**Open questions:** Does Xcode's built-in Claude Agent (not just Claude chat) accept Pro/Max sign-in on current Xcode 26.6/27? Anthropic's help center says Pro/Max for 'Claude in Xcode' (2026-05-19), but a Feb-2026 forum user reported the Claude Agent's claude.ai sign-in failing without an enterprise account; verify on a Mac.; Exact billing path for a headless session: the help center says the Agent SDK credit covers `claude -p`; does a long-lived `-p --input-format stream-json` session or an SDK `query()` loop with subscription OAuth draw from the $20/$100/$200 credit rather than normal 5-hour limits, and does an interactive `claude` in tmux stay on normal limits? Anthropic has not published this precisely.; The in-Xcode Claude Agent MCP config format: the gist shows `"transport": "stdio"` per server, the CLI schema uses `"type": "stdio"`; confirm which key Xcode's bundled claude (2.1.x) accepts and whether user-scope (non-project-keyed) `mcpServers` in ClaudeAgentConfig/.claude.json is honored.; Whether Xcode's 'Add an Agent' ACP sheet supports environment variables and a working directory, and whether Xcode keeps an ACP agent subprocess alive across the laptop sleeping (relevant to an SSH-backed ACP bridge).; Whether Anthropic will publish (or Apple will document) the Xcode 27 agent plug-in manifest and a signed-agent mechanism for `xcrun mcp-server` code-signed permissions; no developer.apple.com page for the manifest was found.; The native `claude` binary's glibc floor versus the grid's CentOS 7.9 glibc 2.17 (the docs list Ubuntu 20.04+/Debian 10+ and musl builds; not tested here) — decide whether Claude Code must run inside the Singularity container's userland rather than on the host.; Whether Xcode 27.1/27.2 betas (2026-09-16/18) change the ClaudeAgentConfig layout or add a UI for MCP servers on built-in agents; release notes for those betas were not fetched.; Location of an official Apple guide page for the Shortcuts 'Run Shell Script' action (only the Automator page and the `shortcuts` CLI page were found).

## Programmatic literature-access credentials for a PRISMA-style review pipeline run from the WSU grid (compute nodes have internet), plus Wayne State library proxy/VPN coverage
Every metadata source a PRISMA pipeline needs (PubMed E-utilities, Europe PMC, Crossref, Unpaywall, NIH RePORTER, ClinicalTrials.gov v2, arXiv, bioRxiv/medRxiv) is reachable from any internet-connected node with no institutional key; the only credentials that materially change throughput are a free NCBI API key (3 -> 10 requests/s) and, new in 2026, an OpenAlex API key (OpenAlex retired the mailto polite pool and moved to a metered daily budget: $1/day free with a key, roughly a tenth of that without one, 429 on overrun). Semantic Scholar's key is free but paradoxically slow (1 request/s introductory), so it is optional. The two subscription indexes, Scopus (Elsevier) and Web of Science, both appear in WSU library guides behind proxy.lib.wayne.edu, so WSU is a subscriber; their APIs are keyed per user for free but full data only flows from a WSU IP range (Elsevier IP-based auth) or with an institution token, and Elsevier's policy forbids storing retrieved records except temporarily, which constrains a systematic-review cache. Google Scholar has no API; SerpAPI's Google Scholar engine costs $25/month for 1,000 searches (250/month free). GitHub push needs a fine-grained PAT with Contents: Read and write on the target repo (org-owned repos may sit 'pending' until approved; personal tokens may have no expiry, org policy defaults to 366 days). Hugging Face push needs a 'write' or fine-grained token, read via HF_TOKEN. For Wayne State, the EZproxy prefix is https://proxy.lib.wayne.edu/login?url= with AccessID login; on campus 'you typically won't need to sign in', and the GlobalProtect VPN (protect.wayne.edu, MFA) is limited to 'a current student or employee'. School of Medicine students authenticate to EZproxy with their AccessID like any WSU student; what ended 2026-06-30 was Tenet/DMC-sponsored residents' access, by Tenet's 'sole decision'. The binding constraint is WSU's acceptable-use policy, which prohibits robots/crawlers and systematic downloading of licensed resources, so the pipeline must pull full text from open-access routes or vendor TDM APIs, never by scripting EZproxy with a student's credentials. Whether the grid's compute-node egress IPs fall inside the publisher-registered WSU ranges was not verifiable from outside and must be probed from a node.

**Recommendation for Ashley.** Wizard credential model for the literature step: collect ONE contact email (reused as E-utilities `email`, Crossref `mailto`, Unpaywall `email`, and the arXiv/Europe PMC User-Agent), then three required tokens and a set of optional ones. Required: (1) NCBI_API_KEY (free, from NCBI Account settings -> API Key Management; lifts PubMed from 3 to 10 req/s; pipeline should pace at ~8 req/s, back off on the exact body `{"error":"API rate limit exceeded",...}`, and schedule bulk EFetch/ELink runs weekends or 21:00-05:00 Eastern); (2) OPENALEX_API_KEY (free from openalex.org/settings/api; since 2026-02-13 keyless use is a ~$0.10/day trial; $1/day ≈ 1,000 searches or 10,000 list calls; expect 429 on budget or >100 req/s; prefer list+filter endpoints over search and never use content download in bulk); (3) GitHub fine-grained PAT (github_pat_ prefix) with Repository permissions Contents: Read and write on the named repos, exported as GH_TOKEN; if the OpenSpineConsortium org repo is a target, either scope a second token to that org (may be `pending` until approved) or push there via SSH. HF_TOKEN (hf_ prefix, write or fine-grained-with-write) is required only if the review outputs go to the Hub; validate the role before saving. Optional, off by default: S2_API_KEY (free but 1 req/s; keyless shared pool is usually faster for small batches), ELSEVIER_API_KEY (+ ELSEVIER_INSTTOKEN only if the library issues one), WOS_API_KEY (Free Trial tier is 50/day and no times-cited; the 5,000/day tier needs WSU's subscription to be recognised), SERPAPI_API_KEY (Google Scholar spot checks, $25/month per 1,000 searches), ZENODO_TOKEN (deposit:write + deposit:actions, only for archiving). Store all of these on the grid in a mode-600 file under the user's home (never /tmp, which is swept), and inject them into the Slurm job environment for the Singularity container with `--env-file` or an exported env; set HF_HOME on CephFS. Rate-limit per client to the documented ceilings (Europe PMC 10/s and 500/min per IP — remember several students may share one node's IP; Crossref 50/s polite; NIH RePORTER 1/s; arXiv one call per 3 s; ClinicalTrials.gov undocumented, stay under 1/s; Scopus 9/s and 20,000/week). Full text: resolve OA copies via Unpaywall and Europe PMC/PMC first; for paywalled Elsevier content use the Article Retrieval API under the TDM terms only from a WSU IP, and never automate EZproxy with a student's AccessID (WSU policy bars robots and systematic downloading; the sanction is university-wide). Before shipping, run a one-time probe job from a compute node: `curl -sI https://api.elsevier.com/content/search/scopus?query=test -H 'X-ELS-APIKey: ...'` and a publisher page, to learn whether the node egress IP is inside WSU's registered ranges; if not, the Scopus/WoS and full-text steps must run from the laptop on VPN or be dropped. Have the wizard also record, for the PRISMA flow diagram, each database's query string, run date, and hit count, since Scopus/WoS results cannot be stored beyond a temporary cache under Elsevier's policy.
