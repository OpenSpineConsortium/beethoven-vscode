# Remote Control replaces the claude.ai interception

The interception design in `arch.txt` and `protocols.txt` does not survive: a MAIN-world `window.fetch` patch on claude.ai that aborts Anthropic's request, forges its SSE grammar and harvests the multimodal payload is, on the plain text of the Consumer Terms, access "through automated or non-human means" plus reverse engineering plus interference, with suspension "at any time without notice" as the remedy, and it is also technically wrong in three places (the background worker is not "continuous", SSE is a documented kill condition for a Chrome service worker, and the cookie claim is documented only for Chrome) and functionally self-defeating (the forged conversation never reaches Anthropic's servers, so a reload, the phone app and search all lose it). What replaces it is already shipped and permitted on the Pro and Max plans students hold: **Claude Code Remote Control**, which makes a `claude` process running inside the student's own Slurm job visible and steerable at claude.ai/code and in the iOS and Android apps, with attachments, transcript sync and push notifications, over outbound HTTPS only ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). That inversion shrinks the browser extension to a lightweight launcher and diagnostics panel that talks to exactly one origin, the student's Open OnDemand portal, and never touches claude.ai or any credential; it uses three OOD surfaces that exist on every 3.x and 4.x site without admin help (the Shell WebSocket, whose frame format has been byte-identical from 2.0 to 4.2.5, the Files JSON routes, and Active Jobs JSON) and an optional `/rnode/` fast path where an administrator has enabled it ([OOD shell app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js); [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html)). The cluster side becomes a university-agnostic framework of a static site profile, a six-call scheduler/runtime/egress adapter and one job template, which covers all twelve US university clusters sampled (eleven Slurm, one LSF) and reuses Ashley's existing sbatch wrapper, Apptainer sandbox recipe, CephFS state directory and signed-key licence gate. The design that passes the Chrome, Edge, Firefox and Apple stores and reads well on a HECVAT is the one with no `cookies` permission, no install-time host permission, no claude.ai scripts, an on-device audit log and an Ed25519-signed kill-list fetched as data; the Safari edition must be free or sold by in-app purchase because Apple forbids licence keys. What is not known and only a real cluster can settle is whether `claude remote-control` stays registered from inside an `sbatch` job under `tmux` with its two one-time prompts pre-accepted, whether the compute nodes can reach Anthropic's unnamed feature-flag host, and whether `ondemand.grid.wayne.edu` has the reverse proxy switched on. The build specification at the end of this report is written so that those three tests are the first thing the team runs.

## The interception design fails three independent tests

The two analyses are technically literate and legally blind. Their own words describe the mechanism: "overwrites the global window.fetch variable with a custom asynchronous proxy function... if the URL matches the signature of a conversational submission endpoint—such as routes containing /api/organizations/ or /chat_conversations/—the interception logic is triggered", after which "the outbound request to the external commercial cloud server is actively aborted" and a mocked `ReadableStream` "perfectly mimics the structural shape of Anthropic's proprietary events" so that the React UI renders HPC output "with the exact same typewriter effect as a standard LLM response" (`arch.txt`, lines 145–160; `protocols.txt`, lines 555–575). Set against the Consumer Terms in force (effective 8 October 2025), each step lands on a prohibition. The terms forbid access "through automated or non-human means, whether through a bot, script, or otherwise" except via an API key "or where we otherwise explicitly permit it"; they forbid attempts to "decompile, reverse engineer, disassemble, or otherwise reduce our Services to human-readable form"; they forbid conduct that would "interfere with, or disrupt our Services, including... bypassing any of our systems or protective measures"; and Section 12 lets Anthropic "suspend or terminate your access to the Services (including any Subscriptions) at any time without notice" ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms)). No Anthropic document grants an extension permission on claude.ai; the help centre's position is that "the preferred way to access Anthropic services using third-party software, tools, or services is through API key authentication" and that "third-party tools that misrepresent their identity to Anthropic's servers... is prohibited and such use may be enforced against" ([Log in to your Claude account](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account)). A forged client stream is the strongest possible form of misrepresentation. The Claude Code legal page adds the sentence that governs any vendor in this space: developers "may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow" ([Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)).

The enforcement record shows these clauses are used. On 20 February 2026 Anthropic's documentation was changed to say that using OAuth tokens from Free, Pro or Max accounts "in any other product, tool, or service — including the Agent SDK — is not permitted", with an Anthropic engineer explaining that third-party harnesses create "unusual traffic patterns without any of the usual telemetry"; OpenCode removed Pro/Max support citing "anthropic legal requests" ([The Register, 2026-02-20](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/)). On 4 April 2026 subscriptions were cut off from third-party agentic tools such as OpenClaw ([VentureBeat](https://venturebeat.com/technology/anthropic-cuts-off-the-ability-to-use-claude-subscriptions-with-openclaw-and)); a metered-credit reinstatement announced in May was paused on 15 June and the surfaces still draw from subscription limits "for now" ([Use the Claude Agent SDK with your Claude plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). The enforcement fell on students' accounts, not on vendors' invoices, which is the point that matters for a product handed to students. Anthropic's handling of its own browser extension is the clearest signal of how script injection into claude.ai is framed: when researchers showed in July 2026 that any extension able to run scripts on claude.ai could forge approvals for Claude in Chrome, Anthropic treated it as a security issue it was "already tracking", and the security press told users to "keep your extension list as small as possible and remove anything you don't fully trust" ([BleepingComputer](https://www.bleepingcomputer.com/news/security/claude-chrome-extension-flaw-lets-malicious-extensions-trigger-ai-actions/); [Malwarebytes](https://www.malwarebytes.com/blog/news/2026/07/claude-for-chrome-flaw-could-let-rogue-extensions-access-your-gmail)). A tool whose whole mechanism is a MAIN-world script on claude.ai is indistinguishable, from Anthropic's side, from that threat model.

The design also fails on the browser platform it chose. `protocols.txt` describes "the Background Service Worker, operating continuously as an invisible background process"; Chrome terminates an extension service worker "after 30 seconds of inactivity" and, separately, "when a `fetch()` response takes more than 30 seconds to arrive", which is exactly what a long SSE response is, whereas WebSocket traffic has been an explicit keepalive since Chrome 116 ([Chrome: service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle); [Chrome: WebSockets in service workers](https://developer.chrome.com/docs/extensions/how-to/web-platform/websockets)). The analyses' preference for SSE over WebSocket is therefore backwards for the background context they intended to use it in. Their reliance on `mozilla/webextension-polyfill` is stale: the repository was archived on 2026-07-30 because Chrome 148 ships the `browser.*` namespace natively and the polyfill "becomes a no-op on Chrome 148 and later" ([mozilla/webextension-polyfill](https://github.com/mozilla/webextension-polyfill); [Chrome: browser namespace](https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace)). Their central "cheat code", that a background `fetch` with `credentials: 'include'` rides the OOD session cookie, is documented only for Chrome, where "requests from an extension to a third-party are treated as same-site if the extension has host permissions for the third-party" but not "if third-party cookies are blocked" ([Chrome: Storage and cookies](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)); Mozilla documents no equivalent guarantee, and Safari developers report cookies attach only in the default profile ([Apple Developer Forums 776558](https://developer.apple.com/forums/thread/776558)). And the analyses never noticed that Rails, which runs the OOD dashboard, checks the `Origin` header on every non-GET request, so a `chrome-extension://` origin is rejected for file writes and job submissions however valid the cookie ([OOD application_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/application_controller.rb); [Rails configuring guide](https://guides.rubyonrails.org/configuring.html)).

Finally there is no shipped ancestor. As of 28 September 2026 no store-listed extension intercepts a claude.ai or chatgpt.com prompt and answers from private compute; what exists is a weaker class that injects tool-calling around a vendor-answered response. The largest, MCP SuperAssistant, has 10,000 Chrome users and deliberately does not support claude.ai; the two claude.ai-specific bridges have 346 and 603 users and one has been stale since April 2025 ([MCP SuperAssistant](https://github.com/srbhptl39/MCP-SuperAssistant); [MCP for claude.ai listing](https://chromewebstore.google.com/detail/mcp-for-claudeai/jbdhaamjibfahpekpnjeikanebpdpfpb?hl=en-US); [MCP Bridge listing](https://chromewebstore.google.com/detail/mcp-bridge-for-claudeai/ekjbhmnilcbfjmldknfkbipmkoeebnkg)). The analyses cite thirty-four and sixty-nine works respectively and not one is a shipped product, an Anthropic term, or a first-party surface; their only extension citation is a chat-to-Markdown exporter. What does survive from the two documents, and is carried into the specification below, is the cluster half: the WXT toolchain choice, the `/node/` versus `/rnode/` routing and `host_regex` description, the 4.1 header and cookie stripping, Apptainer's fakeroot ladder and the warning against overlays on network filesystems, defensive schema validation of model output, and the idea of a per-institution configuration schema, demoted from an LLM-generated artefact to a seed that a probe job overwrites.

## Remote Control already delivers the phone view, from inside a Slurm job

Anthropic's own description of Remote Control is the product goal restated: "Remote Control connects claude.ai/code or the Claude app for iOS and Android to a Claude Code session running on your machine"; "the web and mobile interfaces are a window into that local session"; the student can "attach a photo or file in the Claude app or at claude.ai/code" and Claude Code "downloads other files to your machine and passes them to Claude as `@` file references"; connected devices see the conversation, tool activity, a diff pane in a git directory, can set model and effort, and receive push notifications when a long task finishes or needs a decision ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). It is "available on Pro, Max, Team, and Enterprise plans. API keys are not supported", and the network model fits an HPC compute node exactly: "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports on your machine. When you start Remote Control, it registers with the Anthropic API and polls for work" ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). Anthropic's own scientific-computing write-up ran Claude Code "within terminal multiplexers (tmux) on remote compute nodes" launched from Slurm job scripts ([Anthropic, long-running Claude](https://www.anthropic.com/research/long-running-Claude)), and a community report confirms Remote Control "working on headless Linux VM via SSH + tmux" ([anthropics/claude-code#29479](https://github.com/anthropics/claude-code/issues/29479)). No published account shows it under `sbatch`; that is the first test in the open-questions list.

The prerequisites decide the launch sequence. Remote Control demands a full-scope subscription login: the error "Remote Control requires a full-scope login token" is returned for `claude setup-token` and `CLAUDE_CODE_OAUTH_TOKEN` credentials, which "can only make model requests", and the fix is "Run `claude auth login`" ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). That login works headless: "If your browser shows a login code instead of redirecting back after you sign in, paste it into the terminal", which is "common in WSL2, SSH sessions, and containers", and the credential lands in `~/.claude/.credentials.json` with mode `0600` ([Authentication docs](https://code.claude.com/docs/en/authentication)). This is precisely the boundary Ashley's earlier terms report already required (`Ashley terms of service constraints.md`, Feature 4): the student runs Anthropic's own flow on the node, and the vendor never reads the file. The current Ashley worker's `setup-token` capture must go, not merely be supplemented, because `CLAUDE_CODE_OAUTH_TOKEN` in the environment outranks the `/login` credential and would silently disable Remote Control in any process that inherits it. Two interactive prompts remain: a one-time `Enable Remote Control? (y/n)` consent and a per-directory `Trust <directory>? [y/N]` question that "saves the choice, except in your home directory, where trust is never saved", and "when its standard input or output isn't a terminal, the command can't ask and exits with a `Workspace not trusted` error" ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). The workable pattern, inferred from the documented behaviour rather than shown by any source, is that the student answers both once from an interactive allocation in a project subdirectory, and the batch script then starts `claude remote-control --name <job>` inside a detached `tmux` so the process has a pty; a feature request for a TTY-free `--headless` mode has been open since March 2026 with no staff response ([anthropics/claude-code#30447](https://github.com/anthropics/claude-code/issues/30447)).

Three more requirements shape the job template. The compute node must reach `api.anthropic.com` on port 443 and an unnamed feature-flag service; "If you set `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` or `DISABLE_GROWTHBOOK`, Remote Control is unavailable", and it is also unavailable through any `ANTHROPIC_BASE_URL` other than `api.anthropic.com` or through an enterprise gateway ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). Claude Code's full host list is `api.anthropic.com`, `claude.ai`, `claude.com`, `platform.claude.com` (which handles "OAuth token exchange, refresh, and revocation... for claude.ai accounts, so both Console and claude.ai sign-ins require it"), `mcp-proxy.anthropic.com`, `downloads.claude.ai`, `storage.googleapis.com` and `registry.npmjs.org`; it honours `HTTPS_PROXY`/`NO_PROXY` and "does not support SOCKS proxies" ([Network configuration](https://code.claude.com/docs/en/network-config)). Session lifetime is the Slurm wall time: server mode "gives up after roughly 10 minutes" of outage and exits, but `claude remote-control` in the same directory brings sessions back "for about four hours after the server stopped", which fits a requeue-and-resume pattern that has not been tested under Slurm preemption ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). And two Claude-Code-on-Slurm defects are on record: the bash tool fails on compute nodes without systemd user sessions with `EACCES: permission denied, mkdir '/run/user/<uid>'` and ignores `XDG_RUNTIME_DIR` (closed "not planned") ([anthropics/claude-code#21026](https://github.com/anthropics/claude-code/issues/21026)), and a WebAssembly out-of-memory under `ulimit -v` on a login node ([anthropics/claude-code#144](https://github.com/anthropics/claude-code/issues/144)); the container recipe must work around the first and the login-node rule avoids the second.

The costs are plain and must be told to students in those words. "While Remote Control is connected, the session transcript, including your messages, Claude's responses, and tool activity, is stored on Anthropic servers", and "Organizations with compliance requirements such as Zero Data Retention can't enable Remote Control" ([Remote Control docs](https://code.claude.com/docs/en/remote-control)); consumer transcripts are retained five years when the training toggle is on and 30 days otherwise ([Data usage](https://code.claude.com/docs/en/data-usage)). Usage is one pool: "Both Pro and Max plans offer usage limits that are shared across Claude and Claude Code" ([Using Claude Code with your Pro or Max plan](https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)), so a long autonomous cluster run visibly reduces what the student has left for chat, and the legal page conditions advertised limits on "ordinary, individual usage of Claude Code and the Agent SDK" ([Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). Trusted Devices, in beta and off by default, adds per-device enrolment and an 18-hour re-sign-in step that a Pro or Max user can turn on themselves ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). Under a personal plan there is no BAA: Anthropic's BAA covers "our first-party API or Enterprise plans" and Claude Code "Only... with ZDR enabled", which excludes the very feature the product relies on ([Anthropic BAA article](https://privacy.claude.com/en/articles/8114513-business-associate-agreements-baa-for-commercial-customers)).

The alternatives rank clearly behind. Self-hosted environments are the institutional design, runners on the cluster polling `api.anthropic.com` and claiming sessions started from claude.ai/code or the apps, but they are "in public beta on Team and Enterprise plans", assume a GitHub repository checkout, and the same page sends individuals to Remote Control ([Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)). A custom connector, a remote MCP server the student adds by URL "with no review by Anthropic", does appear inside ordinary chats on any plan, but it is a tool surface with a 240-second per-call timeout and a roughly 150,000-character result cap, must be reachable from `160.79.104.0/21` on the public internet (so an OOD `/rnode/` URL behind SSO cannot be its target), and carries a documented "10–30% of tool calls" spurious-failure rate open since June 2026 with no root cause from Anthropic ([Build an MCP server for Claude](https://claude.com/docs/connectors/building); [Authentication for connectors](https://claude.com/docs/connectors/building/authentication); [anthropics/claude-ai-mcp#469](https://github.com/anthropics/claude-ai-mcp/issues/469)). The request to let claude.ai chats use Remote Control's existing tunnel for MCP was closed as not planned ([anthropics/claude-code#29486](https://github.com/anthropics/claude-code/issues/29486)). Claude Science's SSH hosts are the nearest shipped analogue to the whole idea, Anthropic UI to login node to `sbatch` with per-job approval cards and an explicit "Remote jobs run outside the sandbox, as your user on the host" warning, but it runs from the student's own machine using `~/.ssh/config` and is not a phone view of a cluster session ([Claude Science remote compute clusters](https://claude.com/docs/claude-science/remote-compute-clusters)). The recommendation is therefore to adopt Remote Control now, keep a Cloudflare-Worker-fronted connector with real OAuth in reserve for the narrower "ask Claude in a chat to check my job" use, and treat self-hosted environments as the target if a department ever buys Team or Enterprise.

## Open OnDemand gives three channels everywhere and a fast path where admins allow it

Open OnDemand is the right gateway because it is where the student's authenticated browser session already is, it is deployed at "over 2,100 organizations worldwide" with a peer-reviewed count of 1,646 organisations in 95 countries as of 2023, and it does all authentication in Apache in front of everything ([openondemand.org](https://www.openondemand.org/); [Chalker et al., PEARC '24](https://par.nsf.gov/servlets/purl/10538354); [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html)). It is also a gateway with no API: no release through 4.2.5 (2026-09-24) ships a REST API or tokens, the maintainers say the endpoints "are internal APIs and subject to change" and that "It's not on our roadmap to open any API" ([Discourse 4202](https://discourse.openondemand.org/t/integrating-custom-job-submissions-via-ood-api/4202); [Discourse 2801](https://discourse.openondemand.org/t/exposing-job-composer-as-a-rest-api/2801)). The extension must therefore ride surfaces chosen for stability across versions, and reading the tagged sources from v2.0.32 to v4.2.5 identifies three.

The **Shell app WebSocket** is the universal bootstrap. The page at `/pun/sys/shell/ssh/<host>` embeds a CSRF token; the client opens `wss://<ood>/pun/sys/shell/ssh/<host>?csrf=<token>` with no subprotocol, sends JSON text frames `{"input": "..."}` and `{"resize": {"cols": N, "rows": N}}`, and receives raw PTY bytes as text frames; the server side is `pty.spawn('ssh', [host])` inside the user's per-user NGINX on the OOD web node ([apps/shell/app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js); [views/index.hbs](https://github.com/OSC/ondemand/blob/master/apps/shell/views/index.hbs); [ood_shell.2.js](https://github.com/OSC/ondemand/blob/master/apps/shell/public/javascripts/ood_shell.2.js)). That framing is identical in v2.0.32, v3.0.3, v3.1.14, v4.1.0 and v4.2.5, so a driver written against it is not version-fragile ([app.js @ v2.0.32](https://github.com/OSC/ondemand/blob/v2.0.32/apps/shell/app.js); [app.js @ v4.2.5](https://github.com/OSC/ondemand/blob/v4.2.5/apps/shell/app.js)). Admission runs three gates in order, each closing the socket with code 3146 and a reason string: "No clusters defined.", "Invalid Origin." (only if the client origin `startsWith('http')` and differs from the server origin, so a `chrome-extension://` origin skips the check by construction and a content script on the portal origin passes it), "Bad CSRF Token.", and `Host "<host>" not specified in allowlist or cluster configs.` ([app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js); [utils/helpers.js](https://github.com/OSC/ondemand/blob/master/apps/shell/utils/helpers.js)). The token secret is per Node process and Passenger kills an idle app after 300 seconds, so the token must be scraped seconds before connecting; defaults terminate a socket after 5 minutes without real input or output and after 1 hour regardless (`OOD_SHELL_INACTIVE_TIMEOUT_MS` 300000, `OOD_SHELL_MAX_DURATION_MS` 3600000), and the CSRF token travels in the query string and hence into access logs ([Customizations](https://osc.github.io/ood-documentation/latest/customizations.html); [pun.conf.erb](https://github.com/OSC/ondemand/blob/master/nginx_stage/templates/pun.conf.erb)). The consequences are that the shell is a login-node shell, "typically a login node" per the documentation, and is used only to open, run one `sbatch --parsable`, read the id and close; anything that keeps a login-node process alive for the extension's benefit breaks both the shell's timers and every login-node policy sampled ([Shell App docs](https://osc.github.io/ood-documentation/release-1.8/applications/shell.html)). A non-JSON frame makes `JSON.parse` throw in a process that is the user's only shell process, so frames are validated client-side.

The **Files routes** are the mailbox and the status channel. `GET /pun/sys/dashboard/files/fs/<abs path>` with `Accept: application/json` returns `path`, `url`, `shell_url`, `files_upload_path` (only when uploads are enabled) and `files[]` with `id`, `type` (`'d'`/`'f'`), `name`, `download_url`, `size`, `modified_at`, `owner`, `mode`, served with `Cache-Control: no-store`; `?download=1` streams a file or a zip; `PUT files/fs/<abs path>` writes the request body, `?dir=true` makes a directory, `?touch=true` touches; `POST files/upload/fs` is a multipart upload; `POST transfers` copies, moves or removes ([routes.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/config/routes.rb); [files_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/files_controller.rb); [index.json.jbuilder](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/views/files/index.json.jbuilder); [transfers_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/transfers_controller.rb)). Every write needs the Rails CSRF token and is gated by `upload_enabled`, `download_enabled`, `OOD_ALLOWLIST_PATH` and a 10 GB upload cap ([v4.1 notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.1-release-notes.html); [nginx_stage_example.yml](https://github.com/OSC/ondemand/blob/master/nginx_stage/share/nginx_stage_example.yml)). A worker that writes `status.json`, `connection.json` and a rotating log into a shared-storage state directory can be read by the extension with nothing but these GETs, on a timer of seconds, without a single scheduler call.

**Active Jobs JSON** is the one clean state read on every version: `GET /pun/sys/dashboard/activejobs.json?jobcluster=<cluster id or all>&jobfilter=user` returns `{"data":[[{cluster, status, pbsid, jobname, queue, walltime_used, nodes[], delete_path}, ...]], "errors":[...]}` (note the array of arrays, one inner array per 3,000-job slice), and `DELETE /activejobs?cluster=&pbsid=` cancels ([jobs_json_request_handler.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/models/active_jobs/jobs_json_request_handler.rb); [active_jobs_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/active_jobs_controller.rb)). Two shell-free submission routes exist but are not to be relied on: the Job Composer's JSON responders (`POST /pun/sys/myjobs/workflows.json`, `PUT .../workflows/:id/submit.json` returning 204, `GET .../workflows/:id.json` with a `status` field) are real but the app "is officially deprecated in 4.1" and disappears in 5.0 ([workflows_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/myjobs/app/controllers/workflows_controller.rb); [v4.1 notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.1-release-notes.html)); Interactive Apps accept `POST .../batch_connect/sys/<app>/session_contexts.json` (204 on success) and leave `connection.yml`, `output.log` and `job_script_content.sh` under `~/ondemand/data/sys/dashboard/batch_connect/.../output/<id>/`, which is the partner-site path once an admin installs an app whose `form.yml` launches the worker ([session_contexts_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/batch_connect/session_contexts_controller.rb); [batch_connect/session.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/models/batch_connect/session.rb)). A user with no admin help can install nothing under `/var/www/ood/apps`; development and sharing roots both require a root-created symlink ([Enabling App Development](https://osc.github.io/ood-documentation/latest/how-tos/app-development/enabling-development-mode.html)).

The **`/rnode/` fast path** is real, optional and unauthenticated at the job level. `node_uri` and `rnode_uri` both default to `null`; when set, any authenticated portal user can reach any TCP port on any host matching `host_regex`, whose default `"[^/]+"` admits "all hosts in the world (please change this if you enable this feature)"; the Lua handler maps the user, sets `X-Forwarded-User` and connects, with no job or ownership lookup ([ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml); [node_proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/node_proxy.lua); [ood/proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/ood/proxy.lua)). Since 4.1 the portal strips `mod_auth_openidc_session*` cookies and the `Authorization` and `OIDC_*` headers before proxying, which broke ttyd in 4.1.1 ([ood-portal.conf.erb](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/templates/ood-portal.conf.erb); [Discourse 4757](https://discourse.openondemand.org/t/the-ttyd-not-working-in-ood-4-1-1/4757)). The maintainers' own guidance for any third-party app behind the proxy is to "handle any authentication you need by providing the password/credentials in a `<form>`, header or query parameters" ([Discourse 4060](https://discourse.openondemand.org/t/avoid-launching-a-web-browser/4060)). So the worker generates a random per-job token, publishes it through the Files channel, and rejects any `/rnode/` request without it in a custom header; it never trusts the cookie, `Authorization` or `X-Forwarded-User`. Whether the proxy is on is observable: an Apache 404 for `/rnode/<host>/1/` means `rnode_uri` unset or `host_regex` mismatch, a 503 "Failed to connect to <host>:1" means the proxy is enabled and the host matched ([node_proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/node_proxy.lua)). Wayne State's portal lists Jupyter and RStudio Server among five Interactive Apps, which need the proxy, a strong but unverified indication that `/rnode/` works there; the portal is VPN-only with AccessID login ([WSU KB 20239](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20239)).

Which browser context talks to these endpoints is decided by cookies and CSRF together. Chrome and Edge send the OOD cookie from the service worker once the host permission is granted, unless third-party cookies are blocked, and the WebSocket handshake always uses credentials mode `include` ([Chrome: Storage and cookies](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies); [WHATWG WebSockets](https://websockets.spec.whatwg.org/)); Firefox and Safari have no documented guarantee. A content script injected into `https://<ood>/*` sidesteps the whole question because "content scripts initiate requests on behalf of the web origin that the content script has been injected into" ([Chrome: Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)), and it is also the only context whose `Origin` passes the dashboard's `protect_from_forgery with: :exception` for `PUT`, `POST` and `DELETE`. The rule is therefore: every write and the shell bootstrap run from the portal-origin content script carrying the page's `X-CSRF-Token`; polling GETs may run from the service worker on Chrome and Edge as an optimisation; Firefox and Safari use the content script for everything. The session the extension inherits lasts, with OOD's defaults, 8 hours of inactivity and 8 hours maximum (`oidc_session_inactivity_timeout` and `oidc_session_max_duration` both 28800), the cookie is HttpOnly and SameSite=Lax by default, and a 302 to an identity provider or a 401 means "sign in to your portal in a tab", never an automated login ([ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml); [auth_openidc.conf](https://github.com/OpenIDC/mod_auth_openidc/blob/master/auth_openidc.conf)). A cold per-user NGINX answers the first request with a redirect to `/nginx/init?redir=...`, which loses a POST body, so the extension pre-warms with `GET /pun/sys/dashboard/` before issuing writes ([pun_proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/pun_proxy.lua); [nginx.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/nginx.lua)).

## Twelve of twelve sampled clusters fit a six-call adapter and a probe job

Every mature portable tool converges on the same shape, a job-script template plus three commands (submit, status, cancel), an id regex, and a connection file written by the job; Open OnDemand's own adapters add `submit_host` and `bin_overrides`, Snakemake's `cluster-generic` executor is literally `--cluster-generic-submit-cmd`/`status-cmd`/`cancel-cmd`, dask-jobqueue renders `#SBATCH` directives from `queue`, `account`, `walltime` and `job_extra_directives`, and PSI/J ships executors for Slurm, PBSPro, LSF, Cobalt and Flux ([OOD Slurm adapter](https://osc.github.io/ood-documentation/latest/installation/resource-manager/slurm.html); [Snakemake cluster-generic](https://snakemake.github.io/snakemake-plugin-catalog/plugins/executor/cluster-generic.html); [dask-jobqueue SLURMCluster](https://jobqueue.dask.org/en/latest/generated/dask_jobqueue.SLURMCluster.html); [PSI/J](https://psij-python.readthedocs.io/en/stable/)). What they differ on is what they give up: Nextflow, Snakemake and Dask keep a driver alive on the login node, which Expanse forbids by name ("hosts for running workflow management tools") and Wayne State's 20-process cap forbids in effect; VS Code tunnels move the server into the job and are the documented pattern at UC Riverside, Oregon State, FASRC and NIH Biowulf precisely because Remote-SSH to a login node is banned ([Expanse User Guide](https://www.sdsc.edu/systems/expanse/user_guide.html); [WSU HPC Grid Policies](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20254); [FASRC VS Code deck](https://docs.rc.fas.harvard.edu/wp-content/uploads/2025/08/VSCode_on_the_FASRC_cluster_2025-08-14.pdf); [Biowulf VS Code](https://hpcwebapps.cit.nih.gov/apps/vscode.html)). A Claude Code worker follows the tunnel pattern: server inside the job, a connection record on shared storage, nothing persistent on the login node.

The five scheduler families expose the same verbs. Slurm: `sbatch --parsable` prints "only the job ID number and the cluster name if present" separated by a semicolon, `squeue --json`/`sacct --json` exist from 21.08 and the `-o`/`-P` delimited text forms exist everywhere, `scancel` cancels, and `srun --jobid=<id> --overlap --pty` attaches best-effort ([sbatch](https://slurm.schedmd.com/sbatch.html); [squeue](https://slurm.schedmd.com/squeue.html); [sacct](https://slurm.schedmd.com/sacct.html); [srun](https://slurm.schedmd.com/srun.html); [Slurm 21.08 NEWS](https://raw.githubusercontent.com/SchedMD/slurm/slurm-21.08/NEWS)). PBS Pro prints the id on stdout and has `qstat -F json`; LSF's `bjobs -json` works only with `-o`; Grid Engine has `qsub -terse`; HTCondor has `condor_q -json` and `condor_submit -terse` ([OpenPBS qsub](https://raw.githubusercontent.com/openpbs/openpbs/master/doc/man1/qsub.1B); [OpenPBS qstat JSON](https://openpbs.atlassian.net/wiki/spaces/PD/pages/37158917/PP-483:+PP-484:+PP-485:+Enhance+output+of+qstat+to+make+it+more+admin+and+script+friendly); [IBM LSF bjobs -json](https://www.ibm.com/docs/en/spectrum-lsf/10.1.0?topic=options-json); [SGE qsub](http://gridscheduler.sourceforge.net/htmlman/htmlman1/qsub.html); [condor_q](https://htcondor.readthedocs.io/en/latest/man-pages/condor_q.html)). Status JSON is version-gated on every one of them, so the adapter prefers delimited text and treats JSON as an optimisation. `slurmrestd` exists, JWT-authenticated and stateless, but none of the twelve university documentation sets sampled mentions exposing it, and SchedMD's guidance makes it an administrator decision; treat it as absent ([Slurm REST API](https://slurm.schedmd.com/rest.html)). Reach is what the sample shows, not a census: Wayne State, TACC, Expanse, FASRC, Yale, Sherlock, Penn, Delta and Stampede3 run Slurm and NC State's cluster documentation points to LSF; SchedMD's vendor figure is "approximately 65% of the TOP500" ([WSU Intro to Slurm](https://tech.wayne.edu/kb/high-performance-computing/hpc-tutorials/500260); [NC State Linux Cluster](https://hpc.ncsu.edu/QuickStart/LinuxCluster.php); [SchedMD](https://www.schedmd.com/)). The defensible statement is that Slurm alone covers every sampled US campus cluster except one LSF site, and Slurm plus PBS plus LSF covers all of them.

The container is mandatory on CentOS 7 and advisable everywhere. Claude Code's native binary is documented for "Ubuntu 20.04+", "Debian 10+" and Alpine 3.19+, with `linux-x64`, `linux-arm64` and musl variants, and "the installed claude binary does not itself invoke Node" ([Claude Code setup](https://code.claude.com/docs/en/setup)); Node's own Tier 1 Linux floor is "kernel >= 4.18, glibc >= 2.28" ([Node.js BUILDING.md](https://github.com/nodejs/node/blob/main/BUILDING.md)); a CentOS 7 host can run neither natively, and RHEL 8 and 9 application streams retire each Node major roughly every two and a half years ([Red Hat Application Streams Life Cycle](https://access.redhat.com/support/policy/updates/rhel-app-streams-life-cycle)). Inside an image pinned with `DISABLE_AUTOUPDATER=1`, the binary is the same on every site and does not rewrite `~/.local/share/claude/versions/` under a running worker ([Claude Code setup](https://code.claude.com/docs/en/setup)). Apptainer is the runtime on every sampled US university page that documents containers; since 1.1.0 it "no longer installs a setuid-root portion by default" and `--fakeroot` falls through a documented ladder from `/etc/subuid` mappings to a root-mapped user namespace to the host `fakeroot` command ([Apptainer CHANGELOG](https://github.com/apptainer/apptainer/blob/main/CHANGELOG.md); [Apptainer fakeroot](https://apptainer.org/docs/user/latest/fakeroot.html)). The admin guide names "Lustre, GPFS, and PanFS" together as lacking overlay support and fakeroot and says network filesystems "only support a single uid for each user", which makes Wayne State's practice of keeping sandboxes and caches off its Panasas home not a local quirk but what the documentation prescribes for any parallel home ([Apptainer admin installation](https://apptainer.org/docs/admin/latest/installation.html)). Rootless Podman (FASRC, OSC) and Enroot/Pyxis via `srun --container-image` (Sherlock, Penn) are the second and third runtimes to support; Shifter and Charliecloud can be named but left unimplemented ([FASRC Podman](https://docs.rc.fas.harvard.edu/kb/podman/); [Sherlock Enroot](https://www.sherlock.stanford.edu/docs/software/containers/enroot); [PARCC Containers](https://parcc.upenn.edu/training/software/containers/)).

Egress is the least uniform dimension and must be probed from inside a job, never from the login node. OSC routes all compute-node traffic through NAT; NC State's compute nodes "do not have a connection to any external network"; Great Lakes auto-configures an HTTP proxy at login; Princeton's `proxy/default` module is for "very limited and pre-approved cases"; TAMU offers a `WebProxy` module; FASSE forces a filtering proxy; Wayne State, TACC, Expanse, Delta and Sherlock do not document a compute-node egress policy at all ([OSC firewall](https://www.osc.edu/documentation/knowledge_base/firewall_and_proxy_settings); [NC State](https://hpc.ncsu.edu/QuickStart/LinuxCluster.php); [ARC internet-from-nodes](https://arc.umich.edu/document/internet-from-nodes/); [Princeton proxy](https://researchcomputing.princeton.edu/support/knowledge-base/ports-and-proxydefault); [TAMU WebProxy](https://hprc.tamu.edu/kb/Software/WebProxy); [FASRC FASSE proxy](https://docs.rc.fas.harvard.edu/kb/proxy-settings/)). Four egress classes cover the sample, `direct`, `http-proxy-auto`, `http-proxy-module` and `none`, and two traps follow: Open OnDemand submits with `--export=NONE` by default, which strips a login-set proxy from the job, so the adapter must inject `https_proxy`/`no_proxy` explicitly into the container ([OOD Slurm adapter](https://osc.github.io/ood-documentation/latest/installation/resource-manager/slurm.html); [ood_core slurm.rb](https://github.com/OSC/ood_core/blob/master/lib/ood_core/job/adapters/slurm.rb)); and an allowlist containing only `api.anthropic.com` will pass a pre-authenticated worker and fail a fresh login, because token exchange goes to `platform.claude.com` ([Network configuration](https://code.claude.com/docs/en/network-config)). Login-node rules converge on three prohibitions a naive design would break: long-lived processes (Wayne State's 20-process cap with immediate deletion and suspension; OSC's 20 CPU-minute shell limit; Great Lakes' 1 CPU-hour), tight polling (FASRC: do "not poll more frequently than once a minute"; TACC: "once every few minutes rather than several times a second") and servers or workflow engines on the login node ([WSU HPC Grid Policies](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20254); [OSC Login Environment](https://www.osc.edu/supercomputing/login-environment-at-osc); [FASRC Customs](https://docs.rc.fas.harvard.edu/kb/responsibilities/); [TACC Good Conduct](https://docs.tacc.utexas.edu/basics/conduct/)). Node-local temp is discovered per site (`$SLURM_TMPDIR`, then `$TMPDIR`, then Expanse-style `/scratch/$USER/job_$SLURM_JOB_ID`, then `/tmp`), and IPC goes under `/dev/shm` because Wayne State's `/tmp` cleaner and FASRC's per-job `/tmp` both show that `/tmp` is reclaimed on a schedule the job does not control ([WSU Grid FAQs](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20229); [Sherlock Storage](https://www.sherlock.stanford.edu/docs/storage/)). Design for Wayne State's constraints and the result is portable by construction; the one Wayne State constraint that does not generalise, CentOS 7's glibc 2.17, is the one the container already absorbs.

Discovery needs no admin and almost no login-node work. Phase 1 on the login node costs under a second of CPU and no network: `command -v` for the nine scheduler CLIs, `module -t avail` piped through grep for apptainer/singularity/podman/enroot, `srun --help | grep -c container-image` for Pyxis, `sysctl -n user.max_user_namespaces`, the proxy and temp environment variables, one `sinfo -h -o '%P|%l|%a'` for partitions, `/etc/os-release` and `ldd --version`. Phase 2 is one five-minute probe job on the default partition that prints `$TMPDIR` and `/dev/shm` sizes, tests `apptainer exec docker://alpine true` (registry egress and user namespaces together) and runs `curl -m 10` against `https://api.anthropic.com/`, `https://platform.claude.com/` and `https://claude.ai/` with and without the inherited proxy variables; TACC hides the Apptainer module on login nodes, so `module avail` is negative there while the runtime exists, which is why the probe job is not optional ([Containers@TACC](https://containers-at-tacc.readthedocs.io/en/latest/singularity/01.singularity_basics.html); [Apptainer admin: user namespaces](https://apptainer.org/docs/admin/latest/user_namespace.html)). The prior analyses' idea of an LLM reading the university wiki into a configuration schema is kept as a seed, because for eight of the twelve sampled sites the documentation was silent on at least one of egress, runtime version or temp size, and the probe overwrites it.

## Stores and universities accept one origin, no credential, and a signed kill-list

The realistic adversary is not a browser exploit but a compromised publisher account, store API key or dependency that ships a malicious update, which the browser auto-installs. Cyberhaven's December 2024 compromise came through a phishing e-mail styled as a Chrome Web Store policy notice and an OAuth grant that could "see, edit, update, or publish" extensions "without developer passwords or 2FA"; the payload "Harvested authentication tokens and session cookies" ([Sekoia](https://www.sekoia.com/blog/targeted-supply-chain-attack-against-chrome-browser-extensions)). ShadyPanda's five extensions "operated legitimately for seven years before weaponization" and reached 4.3 million users; Trust Wallet's December 2025 breach used "a leaked Chrome Web Store API key"; GlassWorm was "the first self-propagating worm targeting VS Code extensions on OpenVSX", which matters because Ashley's other surface is a VS Code extension; Shai-Hulud compromised over 200 npm packages in four days ([Malwarebytes](https://www.malwarebytes.com/blog/news/2025/12/sleeper-browser-extensions-woke-up-as-spyware-on-4-million-devices); [The Hacker News](https://thehackernews.com/2025/12/trust-wallet-chrome-extension-bug.html); [BleepingComputer](https://www.bleepingcomputer.com/news/security/self-spreading-glassworm-malware-hits-openvsx-vs-code-registries/); [Krebs on Security](https://krebsonsecurity.com/2025/09/self-replicating-worm-hits-180-software-packages/)). The prior analyses' "zero-credential" claim is true as stated and misleading in effect: an extension that rides the OOD session is a bearer of the user's portal identity for eight hours at a time, and the design must be built so that a stolen build inherits access to one origin per user, not to "all sites".

The store rules already require most of the controls. Chrome bans remotely hosted code ("RHC is not allowed"; JSON and CSS are data and are fine), demands "the narrowest permissions necessary", requires 2-Step Verification on developer accounts, forbids obfuscation, and puts wildcard host access, new developers and new extensions into in-depth review that takes "a few days" but "can take up to a few weeks" ([Chrome: remote hosted code](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code); [CWS Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies); [CWS Review process](https://developer.chrome.com/docs/webstore/review-process)). Mozilla requires "a copy of the source code before any of these steps have been applied" with build instructions, forbids remote code and relaxing page security headers, signs within "up to 24 hours" unless picked for manual review, and since 3 November 2025 forces every new extension to declare its data collection in `browser_specific_settings.gecko.data_collection_permissions` ([Firefox Add-on Policies](https://extensionworkshop.com/documentation/publish/add-on-policies/); [Signing and distribution](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/); [Firefox built-in data consent](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/)). Edge forbids permissions requested for "future proofing", takes "up to seven business days", and wants test credentials or an explanation ([Edge Add-ons developer policies](https://learn.microsoft.com/en-us/legal/microsoft-edge/extensions/developer-policies); [Edge publishing](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension)). Apple says Safari extensions "should not claim access to more websites than strictly necessary" and apps "may not download, install, or execute code which introduces or changes features or functionality" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). The permission that makes all four happy is `optional_host_permissions: ["https://*/*"]` (Chrome 102, Firefox 128, Safari 15.5) with a runtime `permissions.request({origins: ["https://ondemand.<university>.edu/*"]})` from a click handler, which Chrome documents as the way to handle "any origin discovered at runtime" and which means an upgrade adding optional permissions does not disable the extension for existing users ([chrome.permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions); [BCD optional_host_permissions](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/optional_host_permissions.json)). The `cookies` permission is never requested because the network path carries the cookie without it; `webRequest` buys nothing since MV3 cannot block; extension storage "is not encrypted", so per-session material lives in `storage.session` and no durable secret is kept at all ([MDN: cookies API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/cookies); [Chrome: chrome.webRequest](https://developer.chrome.com/docs/extensions/reference/api/webRequest); [MDN: storage API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage)). Dropping the claude.ai hijack removes any claude.ai host permission, which is the single largest reduction of attack surface and review friction: the extension then talks to one origin, the user's portal, and its single purpose reads as one narrow function.

The customary controls come from public-sector and OWASP guidance and from what the ecosystem now supports. CISA's browser guide warns that extensions "operate with high levels of privilege and have access to all data traffic between the user workstation and the network" ([CISA guide](https://www.cisa.gov/sites/default/files/2023-09/Non-Fed%20-%20Guidance_for_Securing_Your_Web_Browsers%20Aug-23%20Revision.pdf)); OWASP lists "Malicious Updates", "Third-Party Dependencies", "Insecure Storage" and prototype-based data skimming as extension vulnerability classes and tells authors to validate `sender.id` on every message ([OWASP cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Browser_Extension_Vulnerabilities_Cheat_Sheet.html)). The secret-keyed `CustomEvent` bridge the analyses proposed is not a security boundary, because Chrome's own guidance says "hostile web pages may manipulate parts of the DOM the content script depends on" and "Do not send sensitive data... to content scripts" ([Chrome: Stay secure](https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure)). Ed25519 verification in WebCrypto shipped enabled by default in Chrome 137, joining Safari and Firefox, so a signed kill-list can be verified offline in the service worker against a public key in the bundle ([Igalia, 2025-08-25](https://blogs.igalia.com/jfernandez/2025/08/25/ed25519-support-lands-in-chrome-what-it-means-for-developers-and-the-web/)). Universities can already confine the extension by policy: Chrome's `ExtensionSettings.runtime_blocked_hosts` blocks an extension from "injecting javascript, altering and viewing webRequests/webNavigation, viewing and altering cookies" on listed hosts, and `runtime_allowed_hosts` overrides, so the documentation should publish the exact host and permission list so a security office can set them ([Chromium ExtensionSettings](https://www.chromium.org/administrators/policy-list-3/extension-settings-full/)). Force-install of a non-store extension on Windows or macOS requires domain, Entra or MDM enrolment, so students' personal laptops need a store-hosted item; unlisted Chrome, hidden Edge and unlisted-signed Firefox distribution all pass the same review without a public listing ([ExtensionInstallForcelist](https://raw.githubusercontent.com/chromium/chromium/main/components/policy/resources/templates/policy_definitions/Extensions/ExtensionInstallForcelist.yaml); [CWS distribution](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution)).

University policy reads the design as the user's own use, subject to approval. None of the nine acceptable-use policies read defines credential sharing as anything other than transfer to another human: Wayne State's UP 00-1 prohibits "Accessing another person's computer account without permission" and "Obtaining access to an account name or password through the negligence or naivete of another"; Case Western says "Sharing accounts or login credentials is strictly prohibited" and "Users are responsible for all activities conducted under their account"; Maryland says "Do not share your login credentials with anyone else" ([WSU UP 00-1](https://wayne.edu/policies/acceptable-use); [CWRU HPC AUP](https://case.edu/utech/departments/research-computing-and-infrastructure-services/resources/acceptable-use-policy-high-performance-computing-hpc-cluster); [UMD HPCC policies](https://hpcc.umd.edu/home/policies/)). Software the student installs, running in the student's own browser profile against the student's own session, is on the same footing as the portal's JavaScript or a Jupyter session launched through OOD; the extension does not touch the MFA approval step, so UConn-style prohibitions on "Automated systems that intend to interfere with the approval component of multi-factor authentication" are not triggered, and the documentation should say so in those words ([UConn MFA Policy](https://policy.uconn.edu/2023/03/29/multifactor-authentication)). The binding constraints are elsewhere. Wayne State's generative-AI guideline states that "All AI tools must first be approved by C&IT; third-party AI bots are not approved for use at this time" and bars FERPA data, PHI and "unsanitized research data" from AI tools ([WSU AI guidelines](https://tech.wayne.edu/policies/aiguidelines)); Utah's CHPC says "Any autonomous agents, such as OpenClaw, are prohibited on all CHPC systems" and "Do not allow AI agents to run commands without your explicit approval"; NERSC says "Models must not be permitted to operate unsupervised" and deployed a managed hook for Codex and Claude Code on 19 August 2026; USC's CARC says "Do not use login nodes to run coding agents" and requires approval for `sbatch`, `git push` and `mpirun`; TACC says "All AI-assisted workloads must be executed on compute nodes only" and charges their SUs to the allocation ([CHPC Coding Agents](https://www.chpc.utah.edu/documentation/software/codingagents.php); [NERSC coding agents](https://docs.nersc.gov/development/coding-agents/); [USC CARC AI Coding Agents](https://www.carc.usc.edu/user-guides/ai-computing/ai-coding-agents); [TACC Good Conduct](https://docs.tacc.utexas.edu/basics/conduct/)). The product therefore ships in supervised mode by default, every command approved in the Remote Control interface, and is presented to each campus as a supervised, user-run agent inside a batch job, which is the shape every center-run assistant found (Kentucky, NCSA, ALCF, ACCESS) stops short of: those read live queue state and file tickets but none submits jobs on the user's behalf from a chat surface ([UKY CCS assistant](https://chat.ccs.uky.edu/); [Delta help](https://docs.ncsa.illinois.edu/systems/delta/en/latest/help.html); [ACCESS MCP servers](https://support.access-ci.org/announcements/connect-your-ai-assistant-access-ci)). The measured failure signature that a worker framework must design against is quiet deviation rather than gross failure: in LLNL's `fractale` study 982 of 1,000 Slurm specs translated correctly but 13 of 76 generated commands carried erroneous affinity flags, one of 19 successful workflow runs added an unrequested filtering step, and agents chose `sleep` polling over event subscription, so a validator step and `≥60 s` polling are cheap and address exactly what a queue administrator would object to ([Sochat & Milroy, arXiv 2607.10081](https://arxiv.org/abs/2607.10081)); Li's "hijacked authorized agent" analysis shows why per-user cookies and SSH keys are sufficient for identity and insufficient for intent, which is the argument for a task manifest and an egress allowlist that an institution can check independently of the agent ([Li, arXiv 2607.18485](https://arxiv.org/abs/2607.18485)).

Data classification determines what the extension must say and refuse. Under a personal plan the transcript sits on Anthropic's servers while connected, retained five years or 30 days by the training toggle, with no BAA; FERPA's school-official route requires that an outside party be "under the direct control of the agency or institution", which a student's subscription plus a one-person vendor cannot supply; and the EAR encryption safe harbour fails because "the means of decryption" are provided to a third party ([Data usage](https://code.claude.com/docs/en/data-usage); [34 CFR 99.31](https://www.law.cornell.edu/cfr/text/34/99.31); [15 CFR 734.18](https://www.law.cornell.edu/cfr/text/15/734.18)). The clusters already forbid the categories, Case Western confining HIPAA to its secure enclave, Maryland capping at "Moderate (Level 2)", Kamiak excluding HIPAA, EAR, ITAR and CUI ([Kamiak AUP](https://hpc.wsu.edu/kamiak-hpc/aup/)). So the extension states, at first run and at each job start, that files the worker reads and every command's output go to Anthropic and that the transcript is stored on Anthropic's servers while connected, names the plan class and the training toggle consequence, states that no BAA covers a personal plan, and refuses to start in a directory the student has marked restricted or when the CLI reports Remote Control unavailable under ZDR. ### Cluster-side framework

The **site profile** is a static JSON file, one per university, generated by the two-phase discovery and editable by hand: `scheduler` (`slurm|pbs|lsf|sge|htcondor`), `submit_host`, `bin_dir`, `partition_cpu`, `partition_gpu`, `qos_requeue`, `account`, `max_walltime`, `node_tmp_var` (`TMPDIR`, `L_SCRATCH`, `SLURM_TMPDIR` or a literal path pattern), `ipc_dir` (`/dev/shm`), `shared_state_dir`, `runtime` (`apptainer|singularity|podman|pyxis`), `runtime_module`, `image_store` (SIF on shared storage; sandbox only where the shared filesystem is not Lustre/GPFS/PanFS), `cache_dir` (node-local), `fakeroot_rung` (1–4 or `none`), `egress` (`direct|http-proxy-auto|http-proxy-module|none`), `proxy_env` or `proxy_module`, `ca_bundle` (for `NODE_EXTRA_CA_CERTS`), `ood_base_url`, `ood_shell_host`, `ood_rnode_enabled` (probed), `vpn_required`, `login_node_rules` (`max_processes`, `poll_floor_seconds`), `xdg_runtime_fix` (boolean). Wayne State's profile carries `reqp` with `--qos=requeue`, `gmsap`/`gvohp`, the CephFS path, the `-D` submit-directory rule for `#SBATCH --output`, `afterany` over `afterok`, and `vpn_required: true`; none of those is exotic.

The **adapter interface** is eight calls, each a single command template plus an id or status regex, with a delimited-text path first and JSON second:

| Call | Slurm | PBS Pro | LSF | Contract |

The **egress adapter** is two calls: `egress_probe()` runs inside the probe job and returns the class plus the working proxy environment by testing `https://api.anthropic.com/`, `https://platform.claude.com/` and `https://claude.ai/` with and without the inherited variables (only HTTP CONNECT proxies count; an `ssh -D` SOCKS tunnel is unusable because Claude Code refuses SOCKS); `egress_env()` renders the variables the job template exports into the container.

The **job template** is one file rendered from the profile: header directives (`--partition`, `--qos`, `--account`, `--time`, `--tmp`, `--requeue`, `--signal=B:TERM@120`, `-D <shared_state_dir>/<run>`), then a fixed body: `cd $(node_tmp)`; stage the SIF to node-local storage if the profile says so; export egress env; `mkdir -p /dev/shm/$USER/xdg && export XDG_RUNTIME_DIR=/dev/shm/$USER/xdg`; generate `JOB_TOKEN=$(head -c 32 /dev/urandom | base64)` and write it with mode 0600 into the state directory; write `status.json` (`state: starting`); start the Remote Control process (next section); write `connection.json` (`host`, `port` if the optional `/rnode/` service is enabled, `pid`, `started_at`, `session_name`, `token_path`); a `SIGTERM` trap that flushes `status.json` (`state: preempted`, `resume_hint`) and exits cleanly. All persistence lives on shared storage; `/tmp` is treated as ephemeral; nothing runs on the login node beyond the one `sbatch`.

### The Remote Control path

The one-time interactive step is the student's, not the tool's. From an interactive allocation on a compute node (`srun --pty` on the CPU partition, or an OOD interactive shell followed by `srun --pty`, never on `warrior`), inside the worker image: `claude auth login` using the paste-code flow so the credential lands in `~/.claude/.credentials.json` (mode 0600, on the shared home, readable only by the student); `cd` into the project directory (not `$HOME`, where trust is never saved); run `claude remote-control` once and answer `Enable Remote Control? (y/n)` and `Trust <directory>? [y/N]`; confirm the session appears at claude.ai/code; Ctrl-C. The extension guides this with text and checks afterwards; it never types the answers.

The batch step, in the job template, is `tmux new-session -d -s rc "apptainer exec ... claude remote-control --name '<site>-<jobid>' --capacity <N> --permission-mode default 2>&1 | tee -a <shared_state_dir>/<run>/rc.log"` followed by a loop that waits for the registration line in `rc.log`, then writes `connection.json` and `status.json` (`state: online`). `tmux` supplies the pty the trust check requires and detaches the process from the job's lack of a controlling terminal; `script -qfc` is the fallback. Supervised mode is the default so that every command is approved from the app, which is what Utah, NERSC and USC require; a student may choose a broader `--permission-mode` knowingly. The extension surfaces the session name and the instruction "Open claude.ai/code, or tap Code in the Claude app, and find `<site>-<jobid>`"; the QR code is unnecessary because sessions are found by name. On preemption or wall-time expiry the next job runs `claude remote-control --continue` in the same directory, which the docs say works for about four hours after the server stopped; whether it survives a Slurm requeue is untested. If `rc.log` shows the full-scope-token error, the extension tells the student to run `claude auth login` again on a node and does nothing else, because the login expires and "a Remote Control session that outlives the login stops making progress" ([Authentication docs](https://code.claude.com/docs/en/authentication)).

Held in reserve, not built this week: a Cloudflare Worker exposing `submit_job`, `job_status` and `tail_output` tools as a custom connector with OAuth (never `none`), relaying to the cluster-side state directory through a channel the student owns; every tool returns inside 240 seconds; documented for the "ask Claude in a chat to check my job" use only, with the 10–30% failure rate stated.

### Extension architecture and permission manifest

WXT emits the Chrome/Edge MV3 service worker and the Firefox event page from one background entry and the Safari build for the packager ([WXT: Targeting Different Browsers](https://wxt.dev/guide/essentials/target-different-browsers)). Per browser: Chrome and Edge use a `sidePanel` for the monitoring UI and may hold a service-worker WebSocket alive with a ≤20-second ping only during the seconds-long bootstrap; Firefox ships as MV2 with a persistent background or as MV3 with alarms, uses `sidebar_action`, and treats `port.onDisconnect` as routine because "Message ports cannot prevent an event page from shutting down" ([MDN: Background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts)); Safari uses a popup or a pinned extension tab, assumes the background dies within tens of seconds, and does all network work from the content script. The `alarms` API enforces the ≥60-second scheduler-facing floor by construction, since Chrome will not honour periods under 30 seconds ([Chrome: chrome.alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms)). Connection state lives in `storage.session`; only the portal hostname, granted origin, UI preferences and the agreement-acceptance record live in `storage.local`; there is no durable secret. The content script is registered programmatically with `scripting.registerContentScripts` for the one granted origin after the click-time grant, because the host is not known at build time.

### Security controls

The extension declares no install-time host permission and requests the single portal origin from a button click, so a malicious update inherits one origin per user rather than "all sites". It never requests `cookies`: the OOD cookie is used by the network stack and never read. It runs no script on claude.ai and its only content script is on the portal origin, which removes the DOM-injection and prototype-skimming classes for everything except the portal page itself; messages are accepted only after checking `sender.id`. Every portal request passes through one chokepoint that appends an append-only on-device audit record (UTC time, endpoint, method, job id, byte count, outcome), viewable and exportable by the student and never transmitted; the same chokepoint enforces the poll floor and the shell single-use rule. Once a day the service worker fetches a signed JSON kill-list, permitted because JSON is data, verifies it with `crypto.subtle.verify` (Ed25519; ECDSA P-256 fallback below Chrome 137, Firefox 130 and Safari 17) against a public key compiled into the bundle, and a revoked version refuses to send commands and tells the student why; the extension fails safe, working offline on the last good list and refusing only on a verified revocation, so an outage of a one-person vendor does not strand a campus. The worker carries its own per-job token so that a request reaching the proxy with a valid portal session cannot drive another student's worker. The release pipeline uses a lockfile and `npm ci`, actions pinned by commit SHA, a build attestation from a hosted builder (SLSA level 2 at minimum, with signing material inaccessible to build steps as the level 3 target), reproducible-build instructions published for all stores because Mozilla requires them anyway, and no long-lived store API key in CI (the Trust Wallet vector); the publisher account and the kill-list signing key sit behind a hardware security key with no third-party OAuth grants (the Cyberhaven vector) ([SLSA v1.1 levels](https://slsa.dev/spec/v1.1/levels); [Mozilla 2FA](https://blog.mozilla.org/addons/2021/03/11/two-factor-authentication-required-for-extension-developers/)). The documentation publishes the exact host and permission list so a security office can set `runtime_allowed_hosts` and `runtime_blocked_hosts`, states that the extension never stores a credential and never touches the MFA approval step, and points at the source repository and build instructions. On the cluster side the worker runs supervised by default, keeps a task manifest (working directory, allowed partitions, allowed egress hosts) that the framework enforces independently of the agent, keeps input data read-only with a separate writable working directory, and never polls the scheduler faster than the profile's floor.

## Conclusion

The research inverts the prior architecture rather than refining it. The two analyses treated claude.ai as the scarce asset to be captured and the cluster as the place to hide the mechanism; the documentation shows the opposite is true. Anthropic has already built the phone-and-browser window onto a session running anywhere with outbound HTTPS, licensed it to the exact plans students hold, and written its terms so that the only thing a vendor may do is stay out of the credential path. The scarce asset is therefore not the chat interface but the student's authenticated portal session and the cluster's rules, and the honest product is small: a launcher that lives on one origin, a framework that runs one job well on any scheduler, and a set of disclosures that say plainly where the transcript goes.

Three consequences follow for how the team should think about the week. First, the extension's value is now almost entirely diagnostic: on twelve sampled clusters the facts that break a worker (egress, runtime, temp, login-node policy, proxy settings) are undocumented or admin-controlled, and a tool that finds them from inside a probe job and explains each failure in a sentence is worth more to a student than any UI on claude.ai. Second, portability is a by-product of Wayne State's strictness, not an extra project; a design that satisfies a 20-process login-node cap, a swept `/tmp`, a Panasas home and a CentOS 7 host satisfies every other sampled site. Third, the open questions are few and cheap, and the first three of them can be answered in one afternoon on `reqp` before a line of extension code is written; if `claude remote-control` will not register from an `sbatch` job, the fallback is not interception but Anthropic's `--headless` request, a partner-site OOD app, or the Team/Enterprise self-hosted runner, and the framework built here serves all three.
