# University-agnostic "HPC worker" layer: what must be abstracted so one script set can start a containerised Claude Code worker as a batch job on most US university clusters

Research notes, 2026-09-28. Reference blueprint: Wayne State's grid (Slurm; CentOS 7 login node `warrior`; `module load apptainer/1.2.2`; Open OnDemand at ondemand.grid.wayne.edu; no jobs or container commands on the login node; node-local `/tmp` swept; `/dev/shm` for IPC; compute nodes with internet egress). Where a fact about WSU comes from the task brief or local memory rather than a WSU web page, it is marked "(local observation, not in WSU public docs)".

Fetch failures to know about: `documentation.its.umich.edu` (Great Lakes user guide and policies), `rcac.purdue.edu/knowledge/anvil/...`, `researchcomputing.princeton.edu`, `hprc.tamu.edu` and `docs.tacc.utexas.edu/software/containers/` returned 403/404 to automated fetches. Where only a search-index excerpt of those pages was available, that is stated inline.

## Dimension 1 — Schedulers: commands, machine-readable outputs, exec-in-job, REST

### Takeaway
Slurm, PBS Pro/OpenPBS, LSF, Grid Engine and HTCondor all expose the same five verbs (submit → id on stdout, status, cancel, interactive attach, and an id-only submit flag), and all but Grid Engine now have first-party JSON output for status. Slurm's REST daemon exists (JWT, stateless) but none of the twelve university documentation sets sampled mention exposing it to users; CLI-over-SSH remains the only interface a tool can assume.

### Inferences
- A five-verb adapter (submit-with-id, status-by-id, cancel, attach-shell, plus a "list my jobs" convenience) is sufficient across all five families; the only structural difference is where the job id is parsed from (Slurm `--parsable` semicolon pair; PBS bare id on stdout; LSF "Job <N> is submitted" text unless `-json` is available for `bjobs` only; SGE `-terse`; HTCondor `-terse` ranges).
- Status JSON is version-gated on every scheduler (Slurm ≥21.08; LSF only with `-o`; PBS `-F json` with escaping bugs in older builds). The adapter should therefore prefer a *delimited text* status path (`squeue -h -o '%i|%T|%N'`, `sacct -P`, `qstat -f`, `bjobs -noheader -o 'jobid stat exec_host'`) and treat JSON as an optimisation, not a dependency.
- Exec-in-job is the verb most likely to be locally disabled: `srun --overlap` requires the step to be allowed by site config, `condor_ssh_to_job` requires daemon configuration, and PBS/LSF have no first-party "attach to a running batch job" primitive beyond `ssh <node>` (which YCRC, ICER and Pitt document as permitted only for nodes in your allocation). The worker design should not depend on attach; a file-based inbox/outbox plus `ssh node` as a diagnostic fallback is the portable choice.
- slurmrestd should be treated as absent. Nothing in the twelve sites' user docs fetched here mentions it, and SchedMD's own guidance (run as a dedicated unprivileged user, JWT key management) makes it an admin decision the user cannot influence.

### Gaps
- No adoption survey by scheduler *for US universities* was found. The CASC/PEARC'20 survey of academic research computing organisations ([Chalker et al., ACM](https://dl.acm.org/doi/fullHtml/10.1145/3311790.3396642)) exists but its scheduler breakdown, if any, was not retrievable; the 65% figure is Top500, vendor-stated, not a campus census. The ACCESS resource catalogue does not expose "batch system" as a searchable field on the pages that were reachable.
- Grid Engine `qstat -xml` and LSF `bsub -Is` full text were not fetched (only their existence is confirmed above).
- Which US universities still run PBS Pro or Altair/Univa Grid Engine in 2026 was not established from primary pages in this pass.

## Dimension 2 — Container runtimes: Apptainer/Singularity, Podman, Enroot/Pyxis, Shifter, Charliecloud

### Takeaway
Apptainer is the default on every sampled US university cluster that documents containers; since Apptainer 1.1.0 it installs without setuid and runs/builds through unprivileged user namespaces with a ladder of `--fakeroot` fallbacks, which is why WSU's unprivileged `--sandbox` build works. Rootless Podman (FASRC, OSC) and Enroot/Pyxis (Sherlock, Penn PARCC) are growing second options; Shifter and Charliecloud appear in Slurm's own list of integrations but not in any university page sampled.

### Cited Findings
- Apptainer 1.1.0: "Apptainer no longer installs a setuid-root portion by default"; squashfuse/fuse2fs drivers mount SIF without setuid; `--fakeroot` "extended to work without /etc/subuid mappings" via a "root-mapped unprivileged user namespace"; "Made the --fakeroot option be implied when an unprivileged user builds a container". Latest series on the changelog: 1.6.x. 1.5.x added PRoot bundling "to preserve file ownership during unprivileged builds" and `apptainer build --data`. `apptainer overlay create` supports `--sparse`. — [Apptainer CHANGELOG](https://github.com/apptainer/apptainer/blob/main/CHANGELOG.md)
- Fakeroot ladder (user guide, v1.5): (1) `/etc/subuid`/`/etc/subgid` mapping "Apptainer will use that method first"; (2) "If user namespaces are available without /etc/subuid and /etc/subguid mapping files, Apptainer will map only the root user id to the original unprivileged user"; (3) "If the 'fakeroot' command is available on the host, Apptainer will use it in addition to a root-mapped user namespace"; (4) "If user namespaces are not available but Apptainer has been installed with setuid-root and also the 'fakeroot' command is available, then the fakeroot command will be run by itself." — [Apptainer fakeroot](https://apptainer.org/docs/user/latest/fakeroot.html)
- How to detect user namespaces: "user.max_user_namespaces has to be non-zero"; Debian: "kernel.unprivileged_userns_clone needs to be non-zero"; Ubuntu 24.04+: set "kernel.apparmor_restrict_unprivileged_userns to zero". Subuid ranges: "Apptainer requires that a range of at least 65536 IDs is used for each mapping." "The default installation of Apptainer does not include a setuid-root component." — [Apptainer admin: user namespaces](https://apptainer.org/docs/admin/latest/user_namespace.html)
- Network/parallel filesystems (admin installation guide): "Lustre, GPFS, and PanFS do not have sufficient upperdir or lowerdir overlay support" for some features "and do not support --fakeroot"; with `--overlay`/`--writable-tmpfs` on a sandbox on those filesystems "fuse-overlayfs will be used"; "SIF containers on Lustre, GPFS, and PanFS will work correctly"; network filesystems "only support a single uid for each user … the fileserver will deny many operations, with 'permission denied' errors"; metadata problems arise "when sandbox images are stored on network filesystems, making it better … to use SIF images instead of sandbox images"; for parallel steps "use apptainer pull to create a local SIF image first". — [Apptainer admin: installation](https://apptainer.org/docs/admin/latest/installation.html)
- Cache/tmp: "The cache is created at $HOME/.apptainer/cache by default" (`APPTAINER_CACHEDIR` overrides); temp "defaults to /tmp", honours `TMPDIR`, `APPTAINER_TMPDIR` overrides both; "The temporary directory used during a build must be on a filesystem that has enough space to hold the entire container image, uncompressed."; tmpfs `/tmp` "may limit the size of container you can build". — [Apptainer build environment](https://apptainer.org/docs/user/latest/build_env.html)
- `--sandbox`: "a writable (ch)root directory called a sandbox, for interactive development"; persistent changes need `--writable`; `apptainer build alpine.sif docker://alpine` and other registries supported. — [Apptainer build a container](https://apptainer.org/docs/user/latest/build_a_container.html)
- CVE-2026-48785 (cited by the prior analyses) is real: prior to 1.5.1 `Image.AuthorizedPath` used prefix matching on `limit container paths`; "Installations that do not use setuid mode or do not configure limit container paths are not affected"; CVSS 4.8. — [OSV CVE-2026-48785](https://osv.dev/vulnerability/CVE-2026-48785)
- Slurm's container guide (26.05) names Charliecloud, rootless Docker via `scrun`, Enroot and Pyxis, Podman, Sarus, Shifter, and Singularity/Apptainer as integrations, and native OCI `--container` support (needs `oci.conf` on compute nodes). — [Slurm containers guide](https://slurm.schedmd.com/containers.html)
- Site inventory:
  - OSC: "As of June 21st, 2022, Singularity is replaced with Apptainer"; "You can use Podman or Apptainer/Singularity directly on all clusters"; "Don't run on a login node if the container will be performing heavy computation"; `export APPTAINER_CACHEDIR=$TMPDIR`; `apptainer build --fakeroot myimage.sif mydef.def`. — [OSC containers HOWTO](https://www.osc.edu/resources/getting_started/howto/howto_use_docker_and_apptainersingularity_containers_at_osc)
  - TACC: `module load tacc-apptainer`; "The Apptainer module is currently only available on compute nodes at TACC." — [Containers@TACC](https://containers-at-tacc.readthedocs.io/en/latest/singularity/01.singularity_basics.html)
  - FASRC (updated 6 Mar 2026): "on the FASRC clusters we have enabled rootless podman"; "Podman containers can also be executed as part of a normal batch job"; images default to `/tmp/container-user-<uid>/storage` so "containers will only exist for the duration of the job"; "Besides Podman containers FASRC also supports Singularity." — [FASRC Podman](https://docs.rc.fas.harvard.edu/kb/podman/)
  - Sherlock: "Enroot and Pyxis are available on Sherlock and work alongside Apptainer"; `srun --container-image ./debian+12.sqsh python3 my_script.py`; cache "under $SCRATCH/.enroot by default". — [Sherlock Enroot](https://www.sherlock.stanford.edu/docs/software/containers/enroot)
  - Penn PARCC: Pyxis "integrates with Enroot to enable seamless container execution inside SLURM jobs"; `srun --container-image=docker://ubuntu:22.04 cat /etc/os-release`. — [PARCC Containers](https://parcc.upenn.edu/training/software/containers/)
  - LUMI (non-US, cited in prior analyses): "The singularity build command, in general, requires some level of root privileges, e.g. sudo or fakeroot, which are disabled on LUMI for security reasons"; unprivileged PRoot builds "do NOT require any root privileges". — [LUMI containers](https://docs.lumi-supercomputer.eu/software/containers/singularity/)
  - NERSC podman-hpc (non-university, the reference Podman-on-HPC deployment). — [NERSC podman-hpc](https://docs.nersc.gov/development/containers/podman-hpc/overview/)
  - Rootless Podman at scale: concurrent jobs sharing an image store hit database-locking errors. — [Podman discussion #24999](https://github.com/containers/podman/discussions/24999)
- WSU: `module load apptainer/1.2.2` builds and execs unprivileged sandboxes (local observation, not in WSU public docs). WSU's public KB has no Apptainer/Singularity article that the search index surfaced.

### Inferences
- Detection order that costs nothing on a login node: `command -v apptainer singularity podman enroot ch-run shifter`; `module -t avail 2>&1 | grep -iE 'apptainer|singularity|podman|enroot'` (Lmod `-t` prints one per line); `srun --help 2>&1 | grep -q container-image` to detect Pyxis; `sysctl -n user.max_user_namespaces` and `test -r /etc/subuid && grep -c "^$USER:" /etc/subuid` to predict which fakeroot rung applies. None of these run a container.
- Because WSU's home is Panasas and Apptainer's admin guide names PanFS as lacking overlay and fakeroot support, the WSU practice of keeping the sandbox and cache off home (CephFS `/rs/...` or node-local `/tmp`) is not a local quirk; it is what the Apptainer documentation prescribes for any Lustre/GPFS/PanFS home. Portable rule: build/pull into `$TMPDIR` (node-local), keep the *runtime* image as a SIF on shared storage, use a sandbox only where the site's shared storage is not one of those three.
- An "Apptainer-first, Podman-second, Pyxis-if-`--container-image`-exists" runtime adapter covers every US university page found. Shifter and Charliecloud can be left as named-but-unimplemented backends.

### Gaps
- No US-university page was found documenting Shifter or Charliecloud as a supported runtime; their university prevalence is unmeasured here.
- Apptainer versions installed per site were mostly not printed on the pages fetched (OSC's HOWTO shows none; WSU 1.2.2 is a local observation; Slurm's guide references Singularity 4.1.3 for native OCI mode).
- The Apptainer *user* guide's fakeroot page does not repeat the network-filesystem warning; it is in the admin installation guide only, so users reading only the user guide will miss it.

## Dimension 3 — Internet egress from compute nodes

### Takeaway
Egress is the least uniform dimension: of the sites with an explicit statement, OSC routes all compute-node egress through NAT (allowed), Great Lakes and NC State block it by default and offer an HTTP proxy (Great Lakes auto-configures one at login), Princeton and TAMU offer proxy *modules* (Princeton "pre-approved cases" only), FASSE forces a filtering proxy, and WSU, TACC, Expanse, Delta, Sherlock, Pitt, ICER and YCRC do not document a compute-node egress policy on the pages reachable. Claude Code needs `api.anthropic.com`, `claude.ai`, `platform.claude.com` (and `downloads.claude.ai` for updates), honours `HTTPS_PROXY`/`NO_PROXY`, and does not support SOCKS.

### Cited Findings
- Claude Code required hosts (table, "Network access requirements"): `api.anthropic.com` (API, WebFetch domain check, feature flags, telemetry), `claude.ai` (claude.ai account authentication), `claude.com` (sign-in redirect page), `platform.claude.com` ("OAuth token exchange, refresh, and revocation also go to this host for claude.ai accounts, so both Console and claude.ai sign-ins require it"), `mcp-proxy.anthropic.com`, `downloads.claude.ai` (native installer, auto-updater, version checks), `storage.googleapis.com` (plugin metadata; installer before 2.1.116), `registry.npmjs.org` (plugins, `npx` MCP servers, npm installs), plus optional `github.com`, `raw.githubusercontent.com`, two Datadog intake hosts, `code.claude.com`. ### Inferences
- A worker must probe egress *from inside a job*, not from the login node (OSC and NC State show the two can differ). A cheap probe is `curl -sS -m 10 -o /dev/null -w '%{http_code}' https://api.anthropic.com/` plus the same for `https://platform.claude.com/` and `https://claude.ai/`, once with and once without the inherited `https_proxy`; record which combination returns an HTTP code. Because Claude Code refuses SOCKS, an `ssh -D` tunnel (the UMich alternative) is not usable; only HTTP CONNECT proxies are.
- Sites fall into four egress classes the config schema should name: `direct` (OSC, WSU-observed), `http-proxy-auto` (Great Lakes: env vars already set at login and inherited by `sbatch --export=ALL` but *not* by OOD's default `--export=NONE`), `http-proxy-module` (TAMU, Princeton: needs `module load` inside the job script), `none` (NC State). The adapter must propagate `https_proxy`/`no_proxy` explicitly into the container (`apptainer exec --env` or `APPTAINERENV_https_proxy`) because `--export=NONE`, `--cleanenv`, and the OOD default all strip it.
- OAuth sign-in from inside a job is a second egress dependency distinct from API traffic: `platform.claude.com` handles token exchange even for claude.ai accounts, so a proxy allowlist containing only `api.anthropic.com` will pass a pre-authenticated worker and fail a fresh login.

### Gaps
- No explicit compute-node egress statement was found for WSU, TACC, Expanse, Delta, Sherlock, Anvil, Pitt, ICER or YCRC in the pages reachable; "not documented" is the finding, not "allowed".
- The proxy hostnames/ports and the exact environment variables set by Great Lakes' auto-proxy, Princeton's `proxy/default` and TAMU's `WebProxy` were not retrievable (pages blocked automated fetch).

- Module system: every site that named one named Lmod (Expanse explicitly; TACC, OSC, Sherlock, FASRC use `module load` with Lmod semantics). Treat both the same: `module load <name>` inside the job script, never at adapter level.
- Node-local temp must be discovered per site, in this order: `$SLURM_TMPDIR` if set (Compute Canada convention; not seen at any US site here), `$TMPDIR` if it points under a node-local path, else Expanse-style `/scratch/$USER/job_$SLURM_JOB_ID`, else `/tmp`. WSU's `$TMPDIR` is the reference case. Everything the worker writes as IPC (sockets, lock files) should go to `/dev/shm` because WSU's cleaner and FASRC's per-job `/tmp` both demonstrate that `/tmp` is reclaimed on a schedule the job does not control.
- Login-node rules converge on three prohibited things a naive worker design would do: long-lived processes (WSU 20-process cap; Great Lakes 1 CPU-hour; OSC 20 CPU-minutes), tight polling (FASRC ≥60 s; TACC "every few minutes"), and running servers or workflow engines on the login node (Expanse names both). The abstraction must therefore run *nothing persistent* on the login node: one `sbatch`, then poll at ≥60 s intervals from the client side over SSH, or better, have the job itself write status to shared storage so the client reads a file rather than calling `squeue`.

- Which sites run Tcl Environment Modules rather than Lmod was not established; no sampled page named Tcl modules.
- Idle-session policies for OOD interactive apps were not found on any of the sampled pages.

## Dimension 5 — Node.js availability and glibc; why a container is the safe route

### Takeaway
Claude Code's native binary is what matters, not Node: the documented Linux floor is Ubuntu 20.04+/Debian 10+ (glibc 2.31/2.28) with separate musl builds, and Node's own official binaries require glibc ≥ 2.28, so a CentOS 7 host (2.17) cannot run either natively. RHEL/Rocky 8 and 9 ship Node 18/20/22/24 as application streams with short lifecycles, so even on modern hosts the system Node is a moving target; a container pins the userland and sidesteps both problems.

### Cited Findings
- Claude Code system requirements: "Ubuntu 20.04+", "Debian 10+", "Alpine Linux 3.19+", "4 GB+ RAM, x64 or ARM64", "internet connection required". Native installer: `curl -fsSL https://claude.ai/install.sh | bash`. npm: "As of v2.1.198, the npm package requires Node.js 22 or later … the package downloads a native binary that doesn't use your Node.js at runtime." "The installed claude binary does not itself invoke Node." Binaries: `linux-x64`, `linux-arm64`, `linux-x64-musl`, `linux-arm64-musl` (plus darwin/win32). Native installs live at `~/.local/bin/claude` → `~/.local/share/claude/versions/`. — [Claude Code setup](https://code.claude.com/docs/en/setup)
- Troubleshooting names the failure modes: "Error loading shared library" → "Wrong binary variant for your system"; "On Linux, check for missing shared libraries. If ldd shows missing libraries, you may need to install system packages."; a glibc/musl mismatch section ("Output mentioning GNU libc or GLIBC means glibc"). — [Claude Code troubleshoot install](https://code.claude.com/docs/en/troubleshoot-install)
- Node.js platform floor (main branch BUILDING.md): Linux x64/arm64 Tier 1 = "kernel >= 4.18, glibc >= 2.28" (examples Ubuntu 20.04, Debian 10, RHEL 8); "Binaries produced on these systems are compatible with glibc >= 2.28 and libstdc++ >= 6.0.25 (GLIBCXX_3.4.25)"; the only glibc 2.17 row is the experimental 32-bit x86 tier. — [Node.js BUILDING.md](https://github.com/nodejs/node/blob/main/BUILDING.md)
- RHEL application streams (Node.js rows): RHEL 8 — Node 18 (Nov 2022 → Apr 2025), 20 (Nov 2023 → Apr 2026), 22 (Jan 2025 → Apr 2027), 24 (Nov 2025 → Apr 2028); RHEL 9 — 18 (→ Apr 2025), 20 (→ Apr 2026), 22 (Nov 2024 → Apr 2027), 24 (Nov 2025 → Apr 2028). — [Red Hat Application Streams Life Cycle](https://access.redhat.com/support/policy/updates/rhel-app-streams-life-cycle)
- Sampled host OSes: Expanse "Rocky Linux" — [Expanse User Guide](https://www.sdsc.edu/systems/expanse/user_guide.html); Delta "Red Hat 9" — [Delta docs](https://docs.ncsa.illinois.edu/systems/delta/en/latest/index.html); WSU login node CentOS 7 (local observation; the prior analyses state glibc 2.17).
- Claude Code updates itself: "Native installations automatically update in the background"; `DISABLE_AUTOUPDATER=1` stops the check, `DISABLE_UPDATES` blocks all update paths; updates need `downloads.claude.ai`. — [Claude Code setup](https://code.claude.com/docs/en/setup); [network configuration](https://code.claude.com/docs/en/network-config)

### Inferences
- The container is required on CentOS 7 (glibc below every documented floor) and *advisable* everywhere else because (a) sites do not guarantee a system Node at all, (b) RHEL streams retire every ~2.5 years, and (c) Claude Code's auto-updater rewrites `~/.local/share/claude/versions/` under a running worker unless disabled — inside an image with `DISABLE_AUTOUPDATER=1` the version is pinned and reproducible.
- The container image's base must itself satisfy glibc ≥ 2.28 (Ubuntu 22.04/Debian 12 do); the host kernel matters less than glibc because Apptainer shares the host kernel. Node ≥ 4.18 kernel floor is also met by CentOS 7's 3.10 only through Node's *experimental* tier, another reason to keep Node out of the host path entirely.
- A worker image built once from `docker://node:22` (or a Debian base plus the native installer) and pinned by `claude.ai/install.sh | bash -s <version>` gives the same binary on every site; `~/.claude` (credentials, settings) must be bind-mounted from persistent shared storage, not baked in.

### Gaps
- No Anthropic page states a numeric minimum glibc for the native binary; the floor is expressed only as distribution versions.
- CentOS 7 = glibc 2.17 is taken from the prior analyses, not re-verified against a primary source in this pass.
- The system Node version on CentOS 7 (EPEL) was not checked; irrelevant once the container is mandatory there.

### Inferences
- The industry template is "job-script template + three commands (submit/status/cancel) + id regex + a connection file written by the job" (OOD, Snakemake cluster-generic, dask-jobqueue all do exactly this). OOD adds two things worth copying: `submit_host` (run the CLI over ssh on a different host) and `bin_overrides` (wrap a site's non-standard `sbatch`).
- What they gave up: Nextflow, Snakemake and Dask keep a *driver process alive on the login node* for the workflow's lifetime, which is precisely what Expanse ("hosts for running workflow management tools") and WSU (20-process cap) forbid; OOD solves this by being a site-installed service; Globus Compute by running a persistent endpoint that needs its own egress; VS Code tunnels by moving the server into the job and using Microsoft's relay. A Claude Code worker should follow the tunnel/OOD pattern (server inside the job; a connection record on shared storage), not the Nextflow pattern.
- OOD's `/rnode/` proxy is only usable where an admin has set `rnode_uri` (default `null`) and `host_regex` admits compute-node names; a portable tool must detect this at runtime (HTTP GET to `/rnode/<host>/<port>/` returning 404 vs 502 vs 200) and fall back to SSH port-forward or a file inbox. The OOD "Job Composer" is a UI app, not a documented REST API for third parties; nothing in the OOD docs fetched exposes job submission over HTTP to an external client.

### Gaps
- Nextflow's per-executor caveats (LSF per-job vs per-slot memory, condor "incubating") were not retrievable from the new docs site; only the executor list was.
- dask-jobqueue's submit/cancel command internals and status detection are not described on the API page fetched (they are in source).
- Whether any US university OOD instance enables `rnode_uri` was not checked; the prior analyses assume it.

## Key question A — Minimal adapter interface and its reach

### Takeaway
Six calls — `submit(script) → id`, `status(id) → {PENDING|RUNNING|DONE|FAILED|UNKNOWN, node}`, `cancel(id)`, `attach(id)` (best-effort), `node_tmp()`, `runtime_exec(image, cmd, binds, env)` — plus two discovery calls (`detect_scheduler()`, `detect_runtime()`) cover Slurm, PBS Pro and LSF with the commands documented above, and every sampled US university except NC State (LSF, still covered) runs Slurm; a university census by scheduler does not exist in the public record found.

### Cited Findings
- Slurm mapping: `sbatch --parsable` → id; `squeue -h -j <id> -o '%T|%N'` or `squeue --json` (≥21.08); `sacct -P -j <id> --format=State,NodeList` after completion; `scancel`; `srun --jobid=<id> --overlap --pty bash`; `$TMPDIR`/`--tmp`. — [sbatch](https://slurm.schedmd.com/sbatch.html); [squeue](https://slurm.schedmd.com/squeue.html); [sacct](https://slurm.schedmd.com/sacct.html); [srun](https://slurm.schedmd.com/srun.html); [21.08 NEWS](https://raw.githubusercontent.com/SchedMD/slurm/slurm-21.08/NEWS)
- PBS mapping: `qsub` → id on stdout; `qstat -f -F json <id>` (`-x` for finished); `qdel`; `qsub -I` (interactive submit, not attach). — [qsub man](https://raw.githubusercontent.com/openpbs/openpbs/master/doc/man1/qsub.1B); [qstat JSON design](https://openpbs.atlassian.net/wiki/spaces/PD/pages/37158917/PP-483:+PP-484:+PP-485:+Enhance+output+of+qstat+to+make+it+more+admin+and+script+friendly)
- LSF mapping: `bsub` (text "Job <N> is submitted"); `bjobs -o 'jobid stat exec_host' -json`; `bkill`; `bsub -I`/`-Is`. — [bjobs -json](https://www.ibm.com/docs/en/spectrum-lsf/10.1.0?topic=options-json); [bsub -I](https://www.ibm.com/docs/en/spectrum-lsf/10.1.0?topic=options-i)
- Precedent for exactly this interface: Snakemake `cluster-generic` (submit/status/cancel commands) — [cluster-generic](https://snakemake.github.io/snakemake-plugin-catalog/plugins/executor/cluster-generic.html); OOD adapter with `bin`, `submit_host`, `bin_overrides` — [OOD Slurm adapter](https://osc.github.io/ood-documentation/latest/installation/resource-manager/slurm.html); PSI/J executors Slurm/PBSPro/LSF/Cobalt/Flux — [PSI/J](https://psij-python.readthedocs.io/en/stable/)
- Reach evidence: Slurm ~65% of Top500 (vendor) — [SchedMD](https://www.schedmd.com/); all ACCESS compute resources sampled (Stampede3, Expanse, Delta, Anvil) and all campus clusters sampled except NC State run Slurm (citations in Dimension 1).

### Inferences
- Recommended abstraction (three layers):
  1. **Site profile** (static JSON, one per university, generated once): `scheduler` (slurm|pbs|lsf|sge|htcondor), `submit_host`, `bin_dir`, `partition_cpu`, `partition_gpu`, `qos_requeue`, `account`, `max_walltime`, `node_tmp_var` (`TMPDIR`|`L_SCRATCH`|literal path), `ipc_dir` (`/dev/shm`), `shared_state_dir` (CephFS/scratch path), `runtime` (apptainer|singularity|podman|pyxis), `runtime_module`, `image_store` (SIF path on shared storage; sandbox only if permitted), `cache_dir` (node-local), `egress` (direct|http-proxy-auto|http-proxy-module|none), `proxy_env` or `proxy_module`, `ood_base_url`, `ood_rnode_enabled`, `login_node_rules` (max processes, poll interval floor).
  2. **Scheduler adapter** (one small shell/Python module per scheduler): the six calls above, each a single command template plus an id/status regex, with a text-output path first and JSON second.
  3. **Job template** (one file, ERB/Jinja like OOD/dask): header directives from the profile; body always the same: `cd $node_tmp`; stage SIF; export proxy env; `apptainer exec --bind $shared_state_dir,$ipc_dir --env DISABLE_AUTOUPDATER=1 … claude …`; write `connection.json` (`host`, `port`, `pid`, `started_at`) to `$shared_state_dir` (the OOD connection-file pattern); trap `SIGTERM`/`--signal` to flush state.
- Percentage reach cannot be stated from a survey; the defensible statement is "Slurm alone covers every US campus cluster sampled here except one LSF site, and Slurm+PBS+LSF covers all of them." That is 12 of 12 sampled, not a population estimate.

### Gaps
- A population-level percentage of US university clusters by scheduler is not available from CASC, ACCESS or Top500 pages reached; Top500 over-represents national labs.
- Grid Engine and HTCondor adapters are specified from man pages only; no US university running them as the primary scheduler was confirmed in this pass.

## Key question B — Discovery without admin help and without heavy login-node work

### Takeaway
Everything needed can be discovered with `command -v`, `module -t avail`, `sysctl -n`, reading environment variables and one short probe job; the only facts that require a job are compute-node egress, `$TMPDIR` location/size and whether user namespaces work on compute nodes (which can differ from the login node).

### Cited Findings
- Scheduler CLIs to test for: `sbatch`/`squeue`/`scontrol` (Slurm) — [sbatch](https://slurm.schedmd.com/sbatch.html); `qsub`/`qstat` (PBS and SGE share names; PBS `qstat -F json` and SGE `qsub -terse` disambiguate) — [qsub PBS](https://raw.githubusercontent.com/openpbs/openpbs/master/doc/man1/qsub.1B); [qsub SGE](http://gridscheduler.sourceforge.net/htmlman/htmlman1/qsub.html); `bsub`/`bjobs` (LSF) — [bjobs -json](https://www.ibm.com/docs/en/spectrum-lsf/10.1.0?topic=options-json); `condor_submit`/`condor_q` (HTCondor) — [condor_q](https://htcondor.readthedocs.io/en/latest/man-pages/condor_q.html)
- Runtime detection facts: Apptainer default cache `$HOME/.apptainer/cache`, temp `/tmp`/`$TMPDIR`/`APPTAINER_TMPDIR` — [build env](https://apptainer.org/docs/user/latest/build_env.html); user-namespace sysctls (`user.max_user_namespaces`, `kernel.unprivileged_userns_clone`, `kernel.apparmor_restrict_unprivileged_userns`) — [admin user namespaces](https://apptainer.org/docs/admin/latest/user_namespace.html); Pyxis adds `--container-image` to `srun` — [NVIDIA/pyxis](https://github.com/NVIDIA/pyxis); TACC makes the Apptainer module available only on compute nodes, so `module avail` on a login node can be *negative while the runtime exists* — [Containers@TACC](https://containers-at-tacc.readthedocs.io/en/latest/singularity/01.singularity_basics.html)
- Egress must be probed from a job: OSC NAT — [OSC firewall](https://www.osc.edu/documentation/knowledge_base/firewall_and_proxy_settings); NC State no external network — [NC State](https://hpc.ncsu.edu/QuickStart/LinuxCluster.php); Great Lakes proxy auto-set at login — [ARC internet-from-nodes](https://arc.umich.edu/document/internet-from-nodes/); Claude Code's own first-run check targets `api.anthropic.com` and `platform.claude.com` — [network configuration](https://code.claude.com/docs/en/network-config)
- Temp conventions: WSU `$TMPDIR` "created by Slurm on the compute node's local hard drive" — [WSU FAQ](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20229); Sherlock `$L_SCRATCH` — [Sherlock storage](https://www.sherlock.stanford.edu/docs/storage/); Expanse `/scratch/$USER/job_$SLURM_JOB_ID` — [Expanse](https://www.sdsc.edu/systems/expanse/user_guide.html); FASRC Podman storage under `/tmp/container-user-<uid>` cleaned after the job — [FASRC Podman](https://docs.rc.fas.harvard.edu/kb/podman/)
- Login-node budgets a discovery script must respect: WSU 20 processes — [WSU policies](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20254); OSC 20 CPU-minutes — [OSC](https://www.osc.edu/supercomputing/login-environment-at-osc); FASRC ≥1 min between scheduler polls — [FASRC](https://docs.rc.fas.harvard.edu/kb/responsibilities/)

### Inferences
- Two-phase discovery. **Phase 1 (login node, <1 s CPU, no network):** `command -v` for the nine CLIs; `module -t avail 2>&1` (Lmod) piped through grep for apptainer/singularity/podman/enroot; `srun --help | grep -c container-image`; `sysctl -n user.max_user_namespaces`; `env | grep -iE '^(https?_proxy|no_proxy|TMPDIR|SLURM_TMPDIR|SCRATCH|L_SCRATCH)='`; `sinfo -h -o '%P|%l|%a'` once (one scheduler call) to list partitions and max times; read `/etc/os-release` and `ldd --version | head -1`. **Phase 2 (one 5-minute probe job on the default partition):** print `$TMPDIR`, `df -h $TMPDIR /dev/shm`, `id`, `sysctl -n user.max_user_namespaces`, `apptainer --version`, `apptainer exec docker://alpine true` (tests registry egress and user namespaces together), and `curl -m 10 -o /dev/null -w '%{http_code}\n' https://api.anthropic.com/ https://platform.claude.com/ https://claude.ai/` with and without the inherited proxy variables. Write the result as the site profile draft.
- `module avail` is necessary but not sufficient (TACC hides the module on login nodes); `command -v` on the login node is likewise not sufficient (WSU forbids running it there). The probe job is therefore not optional; it is the only authoritative source for runtime, egress and temp.
- Documentation-driven profile generation (the prior analyses' "upload the university wiki to an LLM" idea) is a reasonable *seed* but must be overwritten by the probe job, because for eight of the twelve sites here the documentation was silent on at least one of egress, runtime version or temp size.

### Gaps
- No site documents an official, user-runnable "what is available here" command; discovery remains heuristic.
- Whether `srun --overlap` steps are permitted (some sites restrict step launch into running jobs via prolog/cgroup policy) can only be tested per site; no sampled documentation addresses it.

## Key question C — Which Wayne State specifics are idiosyncratic and which are the norm

### Takeaway
The norm: Slurm; Apptainer; Lmod; a node-local `$TMPDIR` erased at job end; a parallel/network home filesystem where Apptainer says not to put sandboxes or fakeroot writes; a hard login-node rule; VPN-gated OnDemand. The outliers: a CentOS 7 login node in 2026 (Delta is on RHEL 9, Expanse on Rocky), a *blanket* ban on container commands on the login node (TACC comes closest by hiding the module; OSC permits light container use), and Panasas home specifically (Lustre/GPFS are the common parallel filesystems, but Apptainer's guidance treats PanFS identically).

### Cited Findings
- WSU specifics from public pages: "no more than 20 processes on Warrior"; `$TMPDIR` erased at job end; `/tmp` and `/wsu/tmp` cleaned monthly. — [WSU policies](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20254). OnDemand: "you must use the Wayne State University Virtual Private Network (VPN)" to reach `https://ondemand.grid.wayne.edu/`. — [WSU Connect to Grid OnDemand](https://tech.wayne.edu/kb/high-performance-computing/hpc-tutorials/500191). Login node purpose-limited to submissions, status and transfers. — [WSU Intro to Slurm](https://tech.wayne.edu/kb/high-performance-computing/hpc-tutorials/500260)
- WSU specifics from local observation (not in WSU public docs): CentOS 7 login node; `apptainer/1.2.2` module; C&IT's 2026-09-28 instruction that nothing container-related runs on `warrior` and nothing of ours lives under its `/tmp`; compute nodes have internet; Panasas home with 4.3 TB soft quota; CephFS group volume; `/tmp` cleaner deleting multiprocessing sockets mid-job; `/dev/shm` for IPC.
- Norm comparators: node-local temp deleted at job end — Sherlock `$L_SCRATCH` "deleted at job end" ([Sherlock storage](https://www.sherlock.stanford.edu/docs/storage/)), Expanse per-job scratch ([Expanse](https://www.sdsc.edu/systems/expanse/user_guide.html)), FASRC Podman storage cleaned after the job ([FASRC Podman](https://docs.rc.fas.harvard.edu/kb/podman/)); login-node ceilings at OSC, Pitt, Delta, ICER, Great Lakes, FASRC, TACC (Dimension 4); VPN-gated access at Pitt ([Pitt access](https://crc.pitt.edu/requesting-new-account/accessing-cluster)) and Yale ([YCRC policies](https://research.computing.yale.edu/services/high-performance-computing/hpc-policies)); OS on peers: Delta RHEL 9 ([Delta](https://docs.ncsa.illinois.edu/systems/delta/en/latest/index.html)), Expanse Rocky ([Expanse](https://www.sdsc.edu/systems/expanse/user_guide.html)).
- Container commands on login nodes: TACC "The Apptainer module is currently only available on compute nodes" ([Containers@TACC](https://containers-at-tacc.readthedocs.io/en/latest/singularity/01.singularity_basics.html)); OSC "Don't run on a login node if the container will be performing heavy computation" (implying light use is tolerated) ([OSC HOWTO](https://www.osc.edu/resources/getting_started/howto/howto_use_docker_and_apptainersingularity_containers_at_osc)); NERSC builds on login nodes with podman-hpc ([NERSC](https://docs.nersc.gov/development/containers/podman-hpc/overview/)).
- Filesystem: Apptainer names "Lustre, GPFS, and PanFS" together as lacking overlay support and fakeroot ([Apptainer admin installation](https://apptainer.org/docs/admin/latest/installation.html)).
- Apptainer 1.2.x vs current: the changelog's newest series is 1.6.x; 1.5.x added PRoot bundling and `--data` builds; CVE-2026-48785 fixed in 1.5.1 (setuid mode only). — [CHANGELOG](https://github.com/apptainer/apptainer/blob/main/CHANGELOG.md); [OSV](https://osv.dev/vulnerability/CVE-2026-48785)

### Inferences
- Design for WSU's constraints and the result is portable *by construction*: a worker that never runs containers on the login node, keeps IPC in `/dev/shm`, keeps sandboxes/caches off the home filesystem and treats `/tmp` as ephemeral will also satisfy TACC, Sherlock, FASRC, Expanse and OSC. The one WSU constraint that does *not* generalise is CentOS 7's glibc, and the container already absorbs it.
- The WSU-specific things the profile must carry, none of which is exotic: partition names (`reqp` + `--qos=requeue`, `gmsap`/`gvohp`), the CephFS path, the `-D` submit-dir rule for `#SBATCH --output`, `afterany` over `afterok`, and the VPN prerequisite for OnDemand.
- Apptainer 1.2.2 is two minor series behind; nothing in the fakeroot ladder used by the worker depends on ≥1.3, but PRoot-based unprivileged builds (LUMI's escape hatch) are a 1.5 feature WSU does not have, so image *builds* should happen off-site or in the job with `--fakeroot` rung 2/3.

### Gaps
- WSU's public KB does not state the login-node OS, the Slurm version, the Apptainer version, compute-node egress policy or home quota; all are local observations.
- Whether other US campus login nodes remain on EL7 in 2026 was not surveyed; only two peers' OS versions were captured.

## Key question D — Where acceptable-use policies draw the line on long-running "worker" jobs and browser automation

### Takeaway
No sampled policy mentions browser extensions or browser-driven automation at all; the lines actually drawn are (1) nothing persistent or heavy on login nodes, (2) scheduler polling no faster than roughly once a minute, (3) no servers or workflow engines on login nodes (Expanse), and (4) soft discouragement of jobs over a week (Yale). A worker that is a normal batch job, polled at ≥60 s, with all persistence in the job, is inside every line found.

### Cited Findings
- FASRC: "If you are using code to submit jobs, please pause at least 0.5 to 1 seconds between sbatch commands."; do "not poll more frequently than once a minute"; `watch` "limited to polling no more frequently than every minute for commands that talk to the scheduler." — [FASRC Customs](https://docs.rc.fas.harvard.edu/kb/responsibilities/)
- TACC: "That script you wrote to poll job status should probably do so once every few minutes rather than several times a second." "Do not run research applications on the login nodes; This includes frameworks like MATLAB and R, as well as computationally or I/O intensive Python scripts." — [TACC Good Conduct](https://docs.tacc.utexas.edu/basics/conduct/)
- Expanse: do not use login nodes "as hosts for running workflow management tools … or as servers providing other services accessible to the Internet." — [Expanse](https://www.sdsc.edu/systems/expanse/user_guide.html)
- YCRC: "Jobs running for longer than one week are discouraged." — [YCRC HPC Policies](https://research.computing.yale.edu/services/high-performance-computing/hpc-policies)
- WSU: "no more than 20 processes on Warrior"; violation → deletion, temporary suspension, then ban. — [WSU policies](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20254)
- OSC: 20 CPU-minute shell limit on login nodes. — [OSC](https://www.osc.edu/supercomputing/login-environment-at-osc). Great Lakes (search excerpt): 1 CPU-hour per process on login nodes. — [Great Lakes Policies](https://documentation.its.umich.edu/arc-hpc/greatlakes/policies). ICER: dev-node processes over 2 CPU/GPU hours killed. — [ICER](https://docs.icer.msu.edu/development_nodes/). Pitt: 1 core / 8 GB per user on login nodes. — [Pitt](https://crc-pages.pitt.edu/user-manual/hardware_profiles/login/)
- Precedent that long-running interactive servers *inside jobs* are sanctioned: OOD batch-connect apps (Jupyter/RStudio/code-server) are exactly that — [OOD interactive apps](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive.html); VS Code tunnels are documented as an approved pattern at UCR, OSU, FASRC and Biowulf when launched from a compute node (Dimension 6 citations).
- OOD's own proxy hardening is relevant to a browser client: since 4.1 the portal strips `Authorization`/OIDC headers and `mod_auth_openidc_session*` cookies before proxying to the interactive app. — [ood_portal.yml](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html)

### Inferences
- The policy risk is not the worker's *duration* (sites run day-long OOD and tunnel sessions) but its *client behaviour*: a browser extension that calls `squeue` over SSH every few seconds, or keeps an SSH session with a background loop on `warrior`, breaks FASRC's and TACC's polling rules and WSU's 20-process cap. Reading a status file the job writes to shared storage, on a ≥60 s timer, is compliant everywhere sampled.
- Expanse's prohibition on login-node "servers providing other services accessible to the Internet" is the closest any policy comes to the prior analyses' design; it forbids the inbox-daemon-on-login-node variant and is silent on a server inside a job behind OOD's proxy, which is what OOD itself does.
- Yale's one-week guidance and Slurm partition `--time` caps mean the worker must be *resumable*: state on shared storage, requeue-safe (`--requeue`, `--signal` before the wall-time kill), and a client that re-submits rather than one job that runs forever.

### Gaps
- No US university policy page found addresses browser-extension automation, AI agents, or third-party API egress from jobs; absence of a rule is not permission, and WSU's C&IT has already shown (2026-09-28 message) that undocumented behaviour on the login node draws direct intervention.
- Maximum wall times per site were not systematically captured; they are in scheduler config (`sinfo -o %l`) rather than policy pages for most sites.

## Prior analyses (arch.txt, protocols.txt): which claims in the "generalized containerized backend" sections held up

### Takeaway
The OOD proxy mechanics (`/node/` vs `/rnode/`, `host_regex`, 4.1 header/cookie stripping), OOD's `--export=NONE` default, slurmrestd's JWT/stateless nature, `--fakeroot`'s dependence on user namespaces with subuid *or* root-mapped fallbacks, sparse EXT3 overlays, network-filesystem UID-mapping failures, LUMI's disabled fakeroot, and CVE-2026-48785 are all confirmed by primary sources. Not confirmed or overstated: "hundreds" of OOD sites (it is over 2,100 organisations), slurmrestd dating to 20.11 as the origin (the REST page ties 20.11 to plugins and 21.08 to OpenAPI; treat "20.11+" as roughly right), and the implicit assumptions that `rnode_uri` is enabled anywhere by default (it is `null` by default) and that a REST endpoint is something a user can "detect and use" (no sampled site exposes one).

### Cited Findings
- Held up: `/node/` "full and untouched" path vs `/rnode/` "ONLY the path portion"; `host_regex` allowlist; `node_uri`/`rnode_uri` default `null`; `strip_proxy_headers`/`strip_proxy_cookies` added in 4.1 with `mod_auth_openidc_session*` defaults. — [OOD Connection View](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/view.html); [ood_portal.yml](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html)
- Held up: OOD Slurm "defaults to issuing CLI commands with the --export flag set to NONE". — [OOD Slurm adapter](https://osc.github.io/ood-documentation/latest/installation/resource-manager/slurm.html)
- Held up: slurmrestd JWT auth, "stateless", run as unprivileged user. — [Slurm REST](https://slurm.schedmd.com/rest.html)
- Held up with nuance: `--fakeroot` uses `/etc/subuid`/`/etc/subgid` *first* but also works without them via a root-mapped namespace or the `fakeroot` command; so "if fakeroot is unsupported fall back to a sandbox" is only needed when user namespaces themselves are off. — [Apptainer fakeroot](https://apptainer.org/docs/user/latest/fakeroot.html)
- Held up: network filesystems "only support a single uid for each user … 'permission denied'"; Lustre/GPFS/PanFS lack overlay support and fakeroot; prefer SIF over sandbox on them. — [Apptainer admin installation](https://apptainer.org/docs/admin/latest/installation.html)
- Held up: `apptainer overlay create` with `--sparse`. — [CHANGELOG](https://github.com/apptainer/apptainer/blob/main/CHANGELOG.md)
- Held up: LUMI disables `sudo`/`fakeroot` builds; PRoot builds are the sanctioned alternative. — [LUMI](https://docs.lumi-supercomputer.eu/software/containers/singularity/)
- Held up: CVE-2026-48785 exists, affects setuid mode only, fixed in 1.5.1. — [OSV](https://osv.dev/vulnerability/CVE-2026-48785)
- Corrected: OOD adoption is "Over 2,100 organizations worldwide", not "hundreds". — [openondemand.org](https://openondemand.org/)
- Corrected: Apptainer's default install has had *no* setuid component since 1.1.0, so "HPC grids strictly rely on … setuid" framing is out of date; the modern default is unprivileged user namespaces. — [CHANGELOG](https://github.com/apptainer/apptainer/blob/main/CHANGELOG.md); [admin user namespaces](https://apptainer.org/docs/admin/latest/user_namespace.html)
- Corrected: WSU's `$TMPDIR` is a Slurm-created node-local directory, not "/tmp mapped to $TMPDIR". — [WSU Grid FAQs](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20229)

### Inferences
- The prior architecture's central bet — route the browser to a FastAPI server in the job through OOD `/rnode/` with session cookies — depends on two admin-controlled settings (`rnode_uri` non-null; `host_regex` admitting compute nodes) and on OOD ≥4.1 *stripping* the very cookies the design says the browser will send; the design must therefore not rely on cookies reaching the backend (the prior text already notes this) and must have a non-OOD path (SSH port-forward or file inbox) for the sites where `rnode_uri` is null.
- The "Dynamic Institution Configuration Schema" idea survives, but as a seed document overwritten by the probe job described in Key question B; for the majority of sampled sites the documentation did not contain the egress, runtime-version or temp-size facts the schema needs.

### Gaps
- Whether ondemand.grid.wayne.edu enables `rnode_uri` was not tested here (requires an authenticated request from the WSU VPN).
- The prior analyses' claim that "many legacy … clusters disable unprivileged user namespaces" is plausible (Apptainer's docs note Ubuntu 24.04 disables them by default) but no US university page sampled states its user-namespace policy either way.
