# Prior art and comparables: connecting a consumer LLM chat surface to institutional compute, and browser extensions that orchestrate remote workers (as of 2026-09-28)

Scope: six areas requested by the coordinator — (1) browser extensions adding tools/remote execution to claude.ai, ChatGPT, Gemini; (2) remote MCP bridges and how personal machines reach claude.ai; (3) university and national-lab HPC assistants; (4) agentic coding tools inside HPC jobs; (5) 2023–2026 literature on LLM agents orchestrating HPC; (6) commercial "bring your own compute" vendors and academic pricing. Every status claim is dated. Abandoned or stale projects are marked. Secondary sources are marked as such.

Prior analyses read first: `arch.txt` ("Architecture and Implementation Blueprint: Cross-Browser Orchestration of HPC Grid Workers via LLM Interface Interception") and `protocols.txt` ("Cross-Browser Orchestration of HPC Workloads via LLM Interface Interception"). Their precedent check is under Key Question 1.

## Key Question 1 — Has anyone shipped, and kept in a browser store, an extension that intercepts claude.ai or chatgpt.com prompts and reroutes them to private compute? What happened to it?

### Takeaway
No. As of 2026-09-28 there is no evidence of any store-listed extension that intercepts a claude.ai or chatgpt.com prompt, aborts the vendor request, and answers from private compute. What does exist in stores is a different, weaker class: extensions that inject MCP tool-calling into the chat page (the model still answers from the vendor; the extension executes tool calls locally and pastes results back). Those remain listed but are small (hundreds to ~10,000 users), one of the two claude.ai-specific ones is stale since April 2025, and the largest (MCP SuperAssistant) deliberately does not support claude.ai. The two prior analyses cite no shipped precedent for their interception design; their only extension citation is a chat-export tool.

- 2026-05-13: Anthropic announced that from 2026-06-15 Agent SDK, `claude -p`, GitHub Actions and third-party tools would draw from a separate monthly credit ($20 Pro, $100 Max 5x, $200 Max 20x) — [Zed blog](https://zed.dev/blog/anthropic-subscription-changes); [claudefa.st](https://claudefa.st/blog/guide/development/agent-sdk-credit). Secondary sources report Anthropic paused this on 2026-06-15 and that those surfaces continue to draw from subscription limits "for now" — [digitalapplied.com](https://www.digitalapplied.com/blog/anthropic-claude-credit-overhaul-june-15-2026) (secondary; the Help Center statement itself was not retrieved).

**Store-listed extensions that touch claude.ai or chatgpt.com**
- **MCP SuperAssistant** (Saurabh Patel). MIT; 2.6k GitHub stars; Chrome Web Store 10,000 users, 4.4/5 from 39 ratings, v0.6.0, last updated 2026-02-09; Firefox add-on also listed. Mechanism: a local proxy on port 3006 (SSE `/sse`, Streamable HTTP `/mcp`, WebSocket) plus a content script that watches the chat DOM for tool-call blocks the model was prompted to emit, executes them, and inserts results back into the conversation. Supported sites: ChatGPT, Gemini, Perplexity, Grok, AI Studio, OpenRouter, DeepSeek, T3 Chat, GitHub Copilot, Mistral, Kimi, Qwen, Z Chat. **claude.ai is not supported.** The model still answers from the vendor; the extension never intercepts or reroutes the prompt — [GitHub](https://github.com/srbhptl39/MCP-SuperAssistant); [Chrome Web Store](https://chromewebstore.google.com/detail/mcp-superassistant/kngiafgkdnlkgmefdafaibkibegkcaef).
- **MCP for claude.ai** (Daniel Nakov). 603 users, one 5-star rating, last updated **2025-04-25** (stale 17 months as of 2026-09-28; treat as abandoned). "Connect Claude AI to local models, tools, and APIs using a simple server management interface." Still listed — [Chrome Web Store](https://chromewebstore.google.com/detail/mcp-for-claudeai/jbdhaamjibfahpekpnjeikanebpdpfpb?hl=en-US).
- **MCP Bridge for Claude.ai** (Fojle Rabbi). 346 users, no ratings, v1.0.2, last updated 2026-02-27, 507 KiB. Injects MCP tools into claude.ai's UI "after the interface mounts" via message passing and port channels; OAuth 2.0 PKCE; AES-256-GCM local credential storage; SSRF/URL-validation claims. Still listed — [Chrome Web Store](https://chromewebstore.google.com/detail/mcp-bridge-for-claudeai/ekjbhmnilcbfjmldknfkbipmkoeebnkg).
- **durapensa/claude-chrome-mcp**: the inverse direction — lets Claude Desktop/Claude Code drive claude.ai tabs in Chrome as an MCP server. Not store-listed; GitHub only; status not archived as of the search — [GitHub](https://github.com/durapensa/claude-chrome-mcp).
- **Superpower for ChatGPT**: the most-installed ChatGPT UI-injection extension, live on the Chrome Web Store as of 2026-09-03 with an unbroken release history since December 2022, because it was rebuilt on Manifest V3; it adds folders/search/export, not remote execution — [GitHub](https://github.com/saeedezzati/superpower-chatgpt); [Chrome Web Store](https://chromewebstore.google.com/detail/superpower-chatgpt/amhmeenmapldpjdedekalnfifgnpfnkc).
- Chrome Web Store removed every remaining Manifest V2 extension on 2026-08-31 (MV2 had stopped running in Chrome 138 on 2025-07-24); MV2 items can no longer update or be reinstalled — [9to5Google, 2026-07-08](https://9to5google.com/2026/07/08/google-chrome-will-remove-older-manifest-v2-extensions-in-august/); [gHacks, 2026-09-01](https://www.ghacks.net/2026/09/01/manifest-v2-is-dead-as-chrome-web-store-permanently-purges-legacy-extensions/).
- MV3 policy: "All of your extension's logic must be part of the extension package. You can no longer load and execute remotely hosted files"; `eval`/`new Function` on arbitrary strings prohibited outside sandboxed iframes; fetching remote JSON configuration is allowed — [Chrome for Developers, Improve extension security](https://developer.chrome.com/docs/extensions/develop/migrate/improve-security).
- **ChatGPT desktop reroute precedent (not a browser extension):** "opencodex" is described as a local compatibility layer on 127.0.0.1:10100 that accepts Responses-API-style requests from the ChatGPT desktop app's Codex feature and forwards them to other providers; it "does not turn the whole ChatGPT app into an offline local-LLM client" — [WindowsForum article](https://windowsforum.com/news/chatgpt-desktop-codex-routes-to-local-llms-via-opencodex.445023/) (secondary; fetch returned 403).
- **Anthropic's own extension, Claude in Chrome:** generally available 2026-08-26 on all paid plans (Pro, Max, Team, Enterprise), Google Chrome only, signs in with the Claude account, can read pages, click, type, fill forms using existing logins, and "intervene if it detects that you are on a high-risk website" — [Claude Help Center, 2026-08-26](https://support.claude.com/en/articles/12012173-get-started-with-claude-in-chrome); [Anthropic publisher page](https://chromewebstore.google.com/publisher/anthropic/u308d63ea0533efcf7ba778ad42da7390). Claude Code can also drive Chrome through this extension — [Claude Code docs: Use Claude Code with Chrome](https://code.claude.com/docs/en/chrome).

### Inferences
- The interception design in the two prior analyses has no shipped ancestor. Every store-surviving extension in this space either (a) adds features to the page without touching the model call (Superpower), or (b) injects tool-execution around a vendor-answered response (SuperAssistant, the two claude.ai MCP bridges). Aborting the vendor request and forging Anthropic's SSE event stream is a step none of them took, and it collides with three Consumer Terms clauses (automated access, reverse engineering, "bypassing any of our systems") plus the 2026 enforcement pattern against unofficial harnesses.
- A forged-stream design also breaks claude.ai's own state: the conversation would exist only in the DOM, not in Anthropic's server-side history, so refresh, mobile app, search and Projects would all lose it. The prior analyses do not address this.
- The tiny user counts (346 and 603) and the stale 2025 listing suggest claude.ai injection extensions have found no market, consistent with Anthropic shipping first-party alternatives (custom connectors in 2025, Remote Control in February 2026, Claude Science SSH hosts in June 2026) that make injection unnecessary.

### Gaps
- No Chrome Web Store takedown record was found for any claude.ai-injecting extension; absence of evidence, not evidence of absence. Store review histories are not publicly browsable beyond current listing metadata.
- The Help Center statement pausing the June 15 Agent SDK credit was not retrieved directly; only secondary reporting.
- Firefox AMO listings for MCP SuperAssistant and the claude.ai bridges were not fetched (user counts and review histories there unknown).
- Whether Anthropic has ever enforced the Terms against a purely client-side UI-injection extension (as opposed to unofficial API harnesses) could not be determined.

## Key Question 2 — Which pattern actually works today for "my private worker appears inside claude.ai": Remote Control, custom connector (remote MCP), or something else, and what do users report about reliability?

### Takeaway
Three first-party patterns exist and two of them (Remote Control; Claude Science SSH hosts) are the ones that reach a personal or institutional machine without any inbound port. Remote Control (GA on Pro/Max/Team/Enterprise since February 2026) shows a running Claude Code session at claude.ai/code and is confirmed working over SSH+tmux on headless Linux, but it is not a chat.claude.ai tool: local MCP servers are not exposed to ordinary claude.ai chats and Anthropic closed the request to do so as "not planned". Custom connectors (remote MCP) do appear inside ordinary chats, but require a publicly reachable HTTPS endpoint and carry a documented 10–30% spurious tool-call failure rate with duplicate issues open from April to June 2026 and no Anthropic root-cause response.

### Cited Findings

**Remote Control**
- Connects claude.ai/code or the Claude iOS/Android app to a Claude Code session running on the user's machine; filesystem, MCP servers, tools and project configuration stay local; images and files can be sent from the browser or phone — [Claude Code docs: Remote Control](https://code.claude.com/docs/en/remote-control).
- Plans: Pro, Max, Team, Enterprise; API keys not supported; Team/Enterprise require an Owner to enable it; unavailable through Bedrock, Google Cloud Agent Platform, Microsoft Foundry, any `ANTHROPIC_BASE_URL` other than `api.anthropic.com`, or an enterprise apps gateway — [same](https://code.claude.com/docs/en/remote-control).
- Transport: "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports on your machine ... it registers with the Anthropic API and polls for work"; multiple short-lived single-purpose credentials — [same](https://code.claude.com/docs/en/remote-control).
- Transcript storage: "While Remote Control is connected, the session transcript, including your messages, Claude's responses, and tool activity, is stored on Anthropic servers"; organizations with Zero Data Retention cannot enable it; HIPAA-configured organizations are incompatible — [same](https://code.claude.com/docs/en/remote-control).
- Server mode: `claude remote-control` with `--capacity` (default 32 concurrent sessions), `--spawn worktree|same-dir|session`, `--permission-mode`, `--sandbox`; interactive mode `claude --remote-control`; sessions can be resumed for about four hours after the server stops — [same](https://code.claude.com/docs/en/remote-control).
- Limitation stated by Anthropic: "To keep a session running on a remote machine after you disconnect from SSH, start it inside `tmux` or `screen`"; server mode gives up after roughly 10 minutes of network outage — [same](https://code.claude.com/docs/en/remote-control).
- Trusted Devices (beta): per-device enrolment plus 18-hour re-auth with platform biometrics or passkey, applying only to Remote Control — [same](https://code.claude.com/docs/en/remote-control).
- Independent confirmation: Remote Control "confirmed working on headless Linux VM via SSH + tmux" (Debian 12, Claude Code v2.1.62, February 2026) — [anthropics/claude-code#29479](https://github.com/anthropics/claude-code/issues/29479); launch write-up 2026-02-25 — [Simon Willison](https://simonwillison.net/2026/Feb/25/claude-code-remote-control/).
- **Not a claude.ai chat tool:** feature request "Claude.ai should use Remote Control's MCP tunnel" (opened 2026-02-28; NIST 800-171-conscious small business with a local ChromaDB MCP server) was **closed as not planned**, labelled `invalid`, with no maintainer response; the user's line: "The secure tunnel already exists. My Claude.ai conversations just can't use it." — [anthropics/claude-code#29486](https://github.com/anthropics/claude-code/issues/29486).
- Field report from a neurology HPC group (March 2026): Claude Desktop over SSH "occasionally crashes or freezes" and "struggled with reliable connection" for intensive HPC work; the CLI in JupyterLab is the fallback — [wanggroup.org, Using Claude on the HPC](https://wanggroup.org/hpc/docs/claude-on-hpc/).

**Custom connectors (remote MCP inside ordinary claude.ai chats)**
- "Your MCP server must be reachable over the public internet from Anthropic's IP ranges. Servers hosted on a private corporate network, behind a VPN, or blocked by a firewall won't connect"; local stdio servers configured in `claude_desktop_config.json` "aren't available in Cowork or claude.ai"; Free users get one connector; on Team/Enterprise only Owners add connectors — [Claude Help Center: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp); protocol support (SSE and Streamable HTTP; authless and OAuth; 3/26 and 6/18 auth specs) — [claude.com/docs connectors](https://claude.com/docs/connectors/custom/remote-mcp).
- Reliability: issue #469 (opened 2026-06-19, open) reports "10–30% of tool calls in a typical session" failing while the server logs 200 OK with valid JSON-RPC, error messages replaced by a generic "An error occurred during tool execution", "Session terminated" errors permanently killing tool use in a conversation, and sessionless servers rejected; reproduced on Railway, Render, Netlify, Hostinger, EC2 and custom VPS; "No public acknowledgment of root cause"; duplicates #143, #199, #214, #227, #326, #374, #380 (April–June 2026) — [anthropics/claude-ai-mcp#469](https://github.com/anthropics/claude-ai-mcp/issues/469); [#227](https://github.com/anthropics/claude-ai-mcp/issues/227); [#1026](https://github.com/anthropics/claude-ai-mcp/issues/1026).
- Tunnel specifics: ngrok free-plan interstitial requires an `ngrok-skip-browser-warning` header, which breaks MCP App widget rendering — [anthropics/claude-ai-mcp#53](https://github.com/anthropics/claude-ai-mcp/issues/53); users report identical failures via Tailscale Funnel and Cloudflare Quick Tunnel with zero inbound requests logged — [#1026](https://github.com/anthropics/claude-ai-mcp/issues/1026). Anthropic's own troubleshooting page says to "expose your server through a publicly-routable endpoint, such as a cloud host with a public IP, a public reverse proxy, or a tunnel" — [Troubleshooting connectors](https://claude.com/docs/connectors/building/troubleshooting).
- How-to guides for exposing a laptop MCP server to claude.ai use ngrok or cloudflared and state that only MCP requests traverse the tunnel — [LocalCan blog](https://www.localcan.com/blog/test-local-mcp-server-in-claude-ai).
- Cloudflare shipped the remote-MCP toolkit on 2025-03-25: `workers-oauth-provider` (OAuth 2.1 provider that issues its own tokens rather than passing upstream tokens through), `McpAgent` on Durable Objects, `mcp-remote`, and an AI Playground client — [Cloudflare blog, 2025-03-25](https://blog.cloudflare.com/remote-model-context-protocol-servers-mcp/); [workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider). Cloudflare One also offers "MCP server portals" that put private MCP servers behind Access policies — [Cloudflare One docs](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/).
- `mcp-remote` (MIT; Glen Maddern; ~333 commits) is the *opposite* direction: it lets a stdio-only local client (Claude Desktop, Cursor) call a remote HTTP server; it does not expose a local server to claude.ai — [geelen/mcp-remote](https://github.com/geelen/mcp-remote).
- ChatGPT equivalent: Developer mode gives "full MCP client support for all tools, both read and write" to Pro, Plus, Business, Enterprise and Education accounts on the web; any remote Streamable HTTP or SSE server, OAuth or none; OpenAI calls it "powerful and dangerous" and puts vetting on the user — [OpenAI Help Center](https://help.openai.com/en/articles/12584461-developer-mode-apps-and-full-mcp-connectors-in-chatgpt-beta); [OpenAI developer docs](https://developers.openai.com/api/docs/guides/developer-mode).

**Anthropic-run alternatives that reach a machine you control**
- **Claude Science SSH hosts** (beta since 2026-06-30 on macOS/Linux, later Windows; Pro, Max, Team, Enterprise): "Connect a machine you can reach over SSH (a lab workstation or an HPC login node) so Claude can run jobs on it"; uses `~/.ssh/config` and `ssh-agent`, "installs nothing on the host itself"; a read-only probe records CPUs, GPUs, CUDA, conda/modules/Apptainer, scratch dirs, whether `sbatch` exists and Slurm partitions; jobs go via `sbatch`; every job shows a "Run this job on `<host>`?" card approved Once / This conversation / This project / Global; default 30-minute timeout; outputs over ~100 MB stay on the host; Warning: "Remote jobs run outside the sandbox, as your user on the host, with access to everything your account can read and write there"; Team/Enterprise admins can disable SSH hosts — [Claude Science docs: Remote compute clusters](https://claude.com/docs/claude-science/remote-compute-clusters); [Claude Science overview](https://claude.com/docs/claude-science); launch [Anthropic news](https://www.anthropic.com/news/claude-science-ai-workbench); date [Neowin](https://www.neowin.net/news/anthropic-launches-claude-science-a-dedicated-app-for-scientists/); Linux requires bubblewrap ≥ 0.8.0 and unprivileged user namespaces — [Claude Science docs](https://claude.com/docs/claude-science).
- BioTeam (2026-06-30, updated July 2026) proxied AWS SSM over the native Claude Science SSH connector to reach private Slurm clusters (ParallelCluster tested; PCS anticipated) and published reusable skills — [BioTeam blog](https://bioteam.net/blog/tech/connecting-compute-to-claude-science/); [bioteam/claude-science-hpc-integrations](https://github.com/bioteam/claude-science-hpc-integrations).
- **Self-hosted environments** (public beta, Team and Enterprise only, off by default): a runner "running on hosts inside your network" polls `api.anthropic.com` outbound, claims cloud sessions started from claude.ai/code or the apps, clones a GitHub repo and spawns Claude Code; "Anthropic never connects into your network"; sessions authenticate with an Anthropic-issued session-scoped OAuth token; unavailable with Zero Data Retention; inference cannot go through Bedrock/Vertex/Foundry or an LLM gateway; runner requeues if it stops polling for ~60 s; Kubernetes and Compose recipes provided — [Claude Code docs: Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments).
- Anthropic's own comparison table lists Dispatch, Remote Control, Channels, Slack, Self-hosted environments and Scheduled tasks as the six "not at your terminal" modes — [Remote Control docs](https://code.claude.com/docs/en/remote-control).

### Inferences
- For the stated product goal ("surface a Claude Code session to claude.ai"), Remote Control is the only first-party mechanism that does exactly that on Pro/Max, and it needs no inbound port, so it survives HPC firewalls. Its costs are: transcript stored at Anthropic (a policy question for CUI/PHI sites), the `claude` process must stay alive (tmux on a compute node, or a Slurm job that wraps it), and it must talk to `api.anthropic.com` directly (no institutional LLM gateway).
- Custom connectors are the wrong primitive for a per-user private worker: they demand a public HTTPS endpoint (so an OOD `/rnode/` proxy behind SSO cannot serve as the target — Anthropic's servers have no session cookie), and their 10–30% failure rate is documented and unaddressed.
- Self-hosted environments are the institutional pattern (one runner fleet, sessions routed by picker) but are Team/Enterprise only and assume a GitHub repo checkout, not an arbitrary scratch directory.
- Claude Science is the closest shipped analogue to the whole product idea (Anthropic UI → user's HPC login node → `sbatch`, with approval cards and a probe of partitions). Its design choices — install nothing on the host, run as the user's own account, per-job approval scope, explicit "outside the sandbox" warning, admin kill-switch — are the ones an institutional worker framework will be compared against.

### Gaps
- No quantitative reliability data for Remote Control on HPC compute nodes (only one headless-VM confirmation and one anecdotal desktop-app complaint).
- Whether Remote Control's registration/polling survives Slurm preemption/requeue and `SIGTERM` was not documented anywhere found.
- Whether Self-hosted environment runners can be launched as Slurm jobs (rather than under Kubernetes/Compose) is not addressed in the docs retrieved; the deploy page's "known issues" was not fetched.
- Claude Science's Windows availability date and whether SSH hosts are available on Pro (vs. only Team/Enterprise) were not separately confirmed beyond the requirements page listing Pro/Max/Team/Enterprise for the app as a whole.

## Key Question 3 — What do the university and national-lab assistants do about authentication and job execution, and which execute anything on the user's behalf versus only advising?

### Takeaway
Almost all of them advise only. Of the deployed systems found, exactly one university assistant reads live cluster state (University of Kentucky, over SSH, behind CILogon SSO, on-premises models) and still does not execute; NCSA's Delta "HPC-GPT" is a site-managed OpenCode CLI that checks Slurm status and files tickets; ALCF's AskALCF queries live job/machine status through an "HPC Operation MCP" and runs an autonomous support pipeline whose only writes are human-reviewed pull requests to documentation. No center was found that submits jobs on the user's behalf from a chat surface. The centers that do let agents act (TACC, Aalto, JHPCE) do so by letting the user run Claude Code/Codex themselves, on compute nodes, under written conduct rules.

### Cited Findings

**Advisory (RAG) assistants**
- **ACCESS Q&A Tool**: RAG over ACCESS documentation; answers questions, queries XDMoD usage metrics, and helps submit a support ticket or a security-incident report "through a guided form"; "Responses are AI-generated and may not always be accurate" — [ACCESS Support](https://support.access-ci.org/tools/access-qa-tool). On 2026-03-30 ACCESS also published nine public, mostly authless MCP servers at `mcp.access-ci.org` (compute resources, system status, software discovery, XDMoD, allocations, NSF awards, events, announcements, affinity groups) for Claude Desktop, claude.ai and Claude Code; the per-user XDMoD analytics server needs a personal token and "isn't currently compatible with Claude.ai connectors"; read-only — [ACCESS announcement, 2026-03-30](https://support.access-ci.org/announcements/connect-your-ai-assistant-access-ci).
- **University of Kentucky CCS HPC Support Assistant**: CILogon SSO with LinkBlue credentials; "real-time partition info, GPU availability, and queue status via SSH"; "all models in this assistant's pipeline run on CCS on-premises resources"; answers only, no job submission; not certified for HIPAA/PII/FERPA/export-controlled/CUI data — [chat.ccs.uky.edu](https://chat.ccs.uky.edu/).
- **LLNL**: LivChat/LivAI endpoints (commercial models via a lab API gateway, key via ServiceNow, "CUI only, no PII/classified", $500/user/year default cap) and LLamaMe (on-prem open models across Collaboration, Restricted and Secure zones, 20 req/min, keys expire every 30 days); self-hosting is the fallback and needs ISSO coordination; no agentic-tool guidance on the page — [HPC @ LLNL, Using LLMs in Livermore Computing](https://hpc.llnl.gov/about-livermore-computing/ai-ml-lc/using-llms-livermore-computing). LLNL expanded Claude for Enterprise to about 10,000 scientists in July 2025 — [insideHPC, 2025-07](https://insidehpc.com/2025/07/ai-for-science-livermore-lab-expands-deployment-of-anthropic-ai/).

### Inferences
- Institutions have converged on a split: the *center-run* assistant is read-only (RAG, live queue reads, ticket filing), and *acting* is delegated to the user's own agent process under the user's own account, on compute nodes, with the user named as responsible. A product that lets the center-run surface execute would be the first of its kind in this set and should expect the same objections that produced the TACC/Aalto rules.
- Authentication in the center-run assistants is campus SSO (CILogon at UKY) or none (ACCESS public MCP). Live cluster reads are done by the assistant's own service account over SSH (UKY) or an MCP server (ALCF), not with the user's credentials. This is the opposite of the prior analyses' plan to ride the user's OOD session cookie.
- NCSA's choice to ship an *OpenCode CLI module* rather than a web chatbot is notable: the assistant runs where the user already is (a login shell), with the user's identity, and the only write is a ticket.

## Key Question 4 — What did the HPC-agent papers find about failure rates and safety, and what mitigations do they recommend (sandboxing, approval gates, audit logs)?

### Takeaway
The measured picture (2025–2026) is: high accuracy on constrained translation tasks (982/1,000 Slurm-to-Flux specs validated), high but not perfect agreement on a real scientific workflow (18 of 19 completed runs matched the reference; 2 of 21 produced nothing), and persistent low-level misbehaviour — hallucinated flags after the agent had correctly identified that no equivalent existed, fixed `sleep` polling instead of event subscription, and unrequested extra pipeline steps. The security literature frames the core problem as the "hijacked authorized agent": every command is authenticated and permitted, yet not what the user asked, and existing HPC controls (SSO, POSIX, accounting, per-agent logs) cannot see the difference. Recommended mitigations are task-scoped authority, source/trust metadata on context, egress control, a validator or adversarial second agent before execution, event-driven rather than polled job monitoring, and read-only inputs with a separate writable working directory.

### Cited Findings

**Reliability measurements**
- Sochat & Milroy (LLNL), "Descriptive Execution of HPC Applications and Workflows" (submitted 2026-07-11), using their `fractale` framework with Google Gemini and MCP tools: scaling study of 5 apps × 5 sizes = 25 studies, 125 app-iteration combinations, with deployment failures (Kripke on odd node counts); job translation 982 of 1,000 Slurm specs translated to Flux and validated, with the agent reporting "1033 times no analogous translation, 237 missing parameters, 62 unknown directives"; of 76 generated Slurm commands 63 executed and 13 had erroneous cpu-bind flags; variant-calling workflow 21 runs attempted, 19 usable, "18 of 19 completed runs agreed with the reference call set exactly", the one divergence added an unrequested filtering step — [arXiv 2607.10081](https://arxiv.org/abs/2607.10081); full text [HTML](https://arxiv.org/html/2607.10081).
- Same paper, failure modes: agents "more often chose to call an explicit sleep function between job executions" than subscribe to events; in affinity translation the agent identified a missing parameter and then "hallucinated an incorrect affinity flag" anyway; processor-affinity flags were the most common error; oversight was "a human able to observe but largely not intervene" with no approval gates; the Snakemake run used "a read only data input directory ... alongside a read and write working directory" with automatic rollback of failed steps — [arXiv 2607.10081 HTML](https://arxiv.org/html/2607.10081).
- Same paper, recommendations: "a Slurm validator tool or an adversarial agent approach where one agent derives a command and a second is required to scrutinize it"; force agents to "subscribe to events" rather than fixed waits; give agents "a tool that exposes a model or database of previously successful runs"; evaluate scientific output by content against a reference rather than by file names; caveat that results are "conditioned on a single model and version, a fixed prompt design, and a particular tool set" — [arXiv 2607.10081 HTML](https://arxiv.org/html/2607.10081).
- DREAMS (July 2025): an "HPC LLM agent" reads job lists, proposes resource requests, submits through `pysqa` to Slurm and monitors status on an AMD 9654 CPU cluster; this is an agent that does submit jobs, inside a domain-specific DFT pipeline — [arXiv 2507.14267](https://arxiv.org/pdf/2507.14267).
- Agentic orchestration of HPC applications in cloud (container build, Kubernetes deploy, scaling study) — [arXiv 2607.02925](https://arxiv.org/html/2607.02925); SC Workshops '25 reference architecture for lineage-aware agents interacting with live workflow data — [arXiv 2509.13978](https://arxiv.org/pdf/2509.13978); an autonomy loop for dynamic job time-limit adjustment — [arXiv 2505.05927](https://arxiv.org/pdf/2505.05927); LLM reasoning for multi-objective HPC job scheduling — [arXiv 2506.02025](https://arxiv.org/pdf/2506.02025).
- SC25 workshop artifact "Understanding Reliability Bottlenecks in LLM Agents for HPC I/O Telemetry Analysis" (Egersdoerfer, U. Delaware) exists — [Zenodo](https://zenodo.org/records/21520996); numbers were not retrievable from the artifact page. SC25 workshop sessions included "Evaluating the Efficacy of LLM-Based Reasoning for Multiobjective HPC Job Scheduling" and "The (R)evolution of Scientific Workflows in the Agentic AI Era" — [SC25 workshop sessions](https://sc25.supercomputing.org/proceedings/workshops/workshop_sessions.html).
- Earlier domain-adaptation work (not agents): HPC-GPT (LLaMA fine-tuned on HPC QA; SC '23 workshops) — [arXiv 2311.12833](https://arxiv.org/abs/2311.12833); LM4HPC — [arXiv 2306.14979](https://arxiv.org/abs/2306.14979).
- General (non-HPC) agent failure studies report roughly 50% task completion across representative tasks — [arXiv 2508.13143](https://arxiv.org/pdf/2508.13143) (not HPC-specific; included for scale only).

**Security and acceptable-use analysis**
- Jie Li (Texas Tech), "Trusted Credentials, Untrusted Behavior: Benchmarking LLM-Agent Security in HPC" (position paper, submitted 2026-07-20): the "hijacked authorized agent problem" — instructions embedded in logs, tool descriptions, shared files or peer messages redirect an agent while "all resulting commands remain authenticated and permitted for the user's account". Five attack surfaces: shared-filesystem poisoning (READMEs, caches, result files persisting across jobs), scheduler/log injection (poisoned stdout/stderr steering job submission to burn allocation), tool/module/MCP-manifest poisoning, cross-project data leakage via multi-project accounts, and multi-agent staged exfiltration — [arXiv 2607.18485](https://arxiv.org/abs/2607.18485); full text [HTML](https://arxiv.org/html/2607.18485).
- Same paper, why current controls fail: SSO cannot tell a requested action from an injected one; POSIX permissions "do not encode task boundaries"; scheduler accounting "cannot detect whether use was requested or induced"; user/process separation stops inter-user but not intra-session hijack; filesystem/network auditing cannot flag disclosure through an approved channel such as the LLM API call itself; per-agent action logging "records actions without determining if they follow task intent" — [arXiv 2607.18485 HTML](https://arxiv.org/html/2607.18485).
- Same paper, seven mitigations: task-scoped authority; source/trust metadata retained on every piece of context (user instruction vs file vs tool output vs peer message); egress control on agent-to-model traffic; shared-filesystem hygiene (limit/label stale cross-user content in scratch and cache paths); tool/module trust checks covering descriptions and MCP manifests; scheduler-aware containment against allocation burn; cross-agent correlation for staged disclosure. Proposed benchmark TaskBound pairs tasks with explicit policies and deterministic oracles (AgentDojo-style), with Slurm-specific actions and project-scoped filesystem policies, scoring task completion, redirection rate, and defense cost — [arXiv 2607.18485 HTML](https://arxiv.org/html/2607.18485).
- Related runtime-policy work cited alongside it: a policy-governed harness for embeddable tool-using agents — [arXiv 2608.13574](https://arxiv.org/pdf/2608.13574); mandatory access control against privilege escalation in agent systems — [arXiv 2601.11893](https://arxiv.org/pdf/2601.11893).
- Practitioner tooling failures on clusters: Claude Code's bash tool fails on Slurm compute nodes with `EACCES: permission denied, mkdir '/run/user/<uid>'` because compute nodes lack systemd user sessions and the tool ignores `XDG_RUNTIME_DIR` (v2.1.19; opened 2026-01-26; **closed as not planned**) — [anthropics/claude-code#21026](https://github.com/anthropics/claude-code/issues/21026); WebAssembly out-of-memory on a Slurm login node under `ulimit -v` (opened 2025-02-26; auto-closed) — [anthropics/claude-code#144](https://github.com/anthropics/claude-code/issues/144). OpenAI Codex CLI's Landlock+seccomp sandbox is "not supported in this environment" on older kernels/WSL, forcing users to `--dangerously-bypass-approvals-and-sandbox` — [openai/codex#1039](https://github.com/openai/codex/issues/1039); [Codex sandbox implementation notes, 2026-04-08](https://codex.danielvaughan.com/2026/04/08/codex-sandbox-platform-implementation/).
- PEARC '25 (Columbus, 2025-07-20..24) featured a Best Student Poster on "A Pre-Processing Framework for Securing LLM-RAG Interfaces Against Information Leakage" and an open-source LLM stack workshop (LiteLLM) about avoiding vendor walled gardens — [PEARC25](https://pearc.acm.org/pearc25/); [OSC press](https://www.osc.edu/press/osc_research_earns_top_honors_at_annual_pearc_conference); [Dartmouth workshop page](https://rcweb.dartmouth.edu/~d20964h/2025-07-21-pearc25-llm-workshop/litellm/).

### Inferences
- The failure signature that matters for a worker framework is not gross task failure but *quiet deviation*: an added filter step, a hallucinated flag after a correct "no equivalent" finding, or `sleep` loops that a queue admin will read as polling abuse (which Aalto already prohibits). A validator step and a second-agent review, both recommended by LLNL authors, are cheap and address exactly these.
- Li's analysis implies that per-user session cookies or SSH keys (as in the prior analyses and Claude Science) are *sufficient for identity and insufficient for intent*: the audit log will show the user did it. A worker framework that wants institutional acceptance needs a task manifest (what this job may read/write/submit) that is checkable independently of the agent, and an egress allowlist.
- No paper found reports an actual security incident on a production HPC system caused by an LLM agent; the literature is threat modelling plus benchmarks. That is a gap the coordinator should state plainly rather than fill.

### Gaps
- No published incident report of an LLM agent causing damage or data leakage on a production HPC system was found.
- No paper measured Slurm job-script generation accuracy as a standalone benchmark; the closest is the Slurm-to-Flux translation result above.
- The SC25 I/O-telemetry reliability paper's numbers were not retrievable.
- No study of transcript-storage or egress policy compliance for agent tools on CUI/HIPAA clusters was found beyond the vendor docs (Remote Control excluded under ZDR/HIPAA; Self-hosted environments excluded under ZDR).

### Inferences
- For a per-user worker tool at a university, the precedents that were accepted have one of two shapes: free core plus a paid institutional governance tier (Coder, OOD-plus-support), or a central site licence whose per-seat price collapses with volume ($144–$240/seat-year at UC Davis; ~$39/seat-year implied at USC). Per-user monthly developer pricing ($20–$125) is accepted only when the individual or a PTA pays.
- Because Remote Control and Claude Science both require a Pro/Max/Team/Enterprise seat and forbid API-key auth, a worker framework built on them inherits Anthropic's seat model; the framework itself can only add value on the institutional side (deployment, policy, audit), which is exactly where Coder charges.
- Every BYO-compute vendor hides academic pricing behind contact-sales; an open licence for the worker framework with a paid support/governance tier would match the norm rather than break it.
