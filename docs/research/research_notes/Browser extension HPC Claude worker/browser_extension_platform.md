# Browser-extension platform facts for a cross-browser MV3 extension that talks to Open OnDemand and surfaces a remote Claude Code worker (state as of 2026-09-28)

Scope note. Everything below is about the browser platforms and stores. Open OnDemand proxy behaviour, Slurm and the Claude side are other researchers' areas and are mentioned only where a browser rule bears on them. Sources were read on 2026-09-28; where a document is dated, the date is given. "BCD" means MDN browser-compat-data, read from the raw JSON in the mdn/browser-compat-data repository, which is what the MDN compatibility tables render.

## Which toolchain gives one codebase for all four browsers with the least risk, and what does Safari packaging really require?

### Takeaway
WXT is the only cross-browser MV3 toolchain that is both actively maintained in 2026 and targets Chrome, Firefox, Safari and Edge from one codebase; Plasmo has had no release or commit since May 2025 and still labels Firefox MV3 experimental, and mozilla/webextension-polyfill was archived on 2026-07-30 because Chrome 148 ships the `browser.*` namespace natively. Safari packaging still needs a Mac with Xcode or Apple's new web-based packager in App Store Connect, and in every case an Apple Developer Program membership; the CLI was renamed from `safari-web-extension-converter` to `safari-web-extension-packager`.

### Inferences
- The lowest-risk stack is WXT + TypeScript, writing to `browser.*` with Promises, no polyfill, `minimum_chrome_version: 148` (or a one-line `globalThis.browser ??= chrome` guard if older Chrome must be served). WXT already emits the Firefox `background.scripts` event page and the Chrome/Edge service worker from one entry file; Safari gets the MV2 or MV3 build and then Apple's packager.
- Plasmo should not be chosen for a new project in 2026: 16 months without a release, "alpha" self-description, Firefox MV3 experimental, and its own messaging package (`@plasmohq/messaging`, last published 2025-06-20 per the npm registry) would become an unmaintained dependency.
- "Plain MV3" (hand-written manifest, esbuild/Vite) is viable now that all four browsers expose `browser.*`, but you then hand-maintain two manifests (Firefox `scripts`, Chrome/Edge `service_worker`, Safari either) and the Firefox source-zip requirement; WXT does that for free.
- Safari is a separate release track regardless of toolchain: a Mac with Xcode (or the App Store Connect packager and its Xcode Cloud minutes), an Apple Developer Program membership, an app record, TestFlight for beta, and App Store review. The Apple documentation now says Developer ID + notarization outside the Mac App Store is possible; because DTS said the opposite as recently as 2021 and developers still reported failure in January 2024, this route must be tested on current macOS before it is promised to a university.

### Gaps
- The Apple membership fee is not on the "Choosing a Membership" page fetched; no primary source captured for the annual price.
- No primary source captured for Xcode/macOS minimum versions required by the current packager (the page fetched does not list them).
- Whether the Developer-ID-outside-App-Store path actually loads without "Allow unsigned extensions" on Safari 26 was not verified empirically or in a dated Apple change note.
- WXT's Safari support (does its `safari` target produce an MV3 background that Safari's `preferred_environment` honours?) was not tested; only its documentation was read.

## Permissions: optional_host_permissions and runtime host requests for user-entered domains, activeTab, cookies, scripting, storage, alarms, webRequest limits

### Takeaway
User-entered university hosts can be handled with `optional_host_permissions: ["https://*/*"]` (Chrome 102+, Firefox 128+, Safari 15.5+) plus `permissions.request({origins:[...]})` from a click handler; MV3 `webRequest` is observational only in Chrome (blocking is reserved for policy-installed extensions), Safari's `webRequest` is macOS-only and non-blocking, and Safari's per-site permission model prompts the user on each new site anyway.

### Cited Findings
- Chrome: four declaration keys, `permissions`, `optional_permissions`, `host_permissions`, `optional_host_permissions`; host permissions are what allow "`fetch()` requests from service workers", reading tab URL/title/favicon, programmatic content-script injection, `webRequest` monitoring, `cookies` access and `declarativeNetRequest` modification — [Chrome: Declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)
- Chrome `permissions.request()`: "Permissions must be requested from inside a user gesture, like a button's click handler"; hosts not known at build time can be requested if `optional_host_permissions` contains `"https://*/*"`; a prompt is shown only when the new grant "results in different warning messages than the user has already seen and accepted" — [Chrome: chrome.permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions)
- BCD: `optional_host_permissions` Chrome 102, Firefox 128, Safari 15.5 (MV3 only); `host_permissions` Chrome 88, Firefox 109, Safari 15.4 — [BCD optional_host_permissions.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/optional_host_permissions.json); [BCD host_permissions.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/host_permissions.json)
- MDN `optional_host_permissions`: enables "runtime requests for access ... for the APIs in your extension that read or modify host data, such as `cookies`, `webRequest`, and `tabs`"; users may opt in/out from the Firefox Add-ons Manager Permissions tab; use `permissions.getAll()`, `onAdded`, `onRemoved` — [MDN: optional_host_permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_host_permissions)
- MDN `permissions.request()`: "The extension can only make the request inside the handler for a user action"; an `origins` request may name a subset of a declared pattern (declared `"*://mozilla.org/"` allows requesting `"https://developer.mozilla.org/"`); one prompt for all requested permissions, all-or-nothing; grants persist across upgrade and disable/enable — [MDN: permissions.request](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/permissions/request)
- BCD note for Safari `permissions.request`: "Requesting `<all_urls>` or `*://*/*` origins will grant permission to request specific origin patterns and automatically prompt the user for access to any visited website via the extension's access popover in the toolbar" — [BCD permissions.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/permissions.json)
- Safari's model: when the user visits a page the extension has not been granted, Safari badges the toolbar item and the user picks "a single use, for the day, or for all websites"; permission status per site is Ask/Allow/Deny; "In Safari 17 and later, when you grant access to an extension for a specific web site, that grants the extension access to the site across all profiles, private browsing, and browsing without a profile"; Apple says "Prioritize using `activeTab`, host permissions, and `optional_permissions`; only use `<all_urls>` if there is no other option" — [Apple: Managing Safari web extension permissions](https://developer.apple.com/documentation/safariservices/managing-safari-web-extension-permissions)
- Firefox MV3: in Firefox 126 and earlier host permissions were not granted at install; "Firefox 127+: Host permissions listed in `host_permissions` and `content_scripts` are displayed in the install prompt and granted on installation", and users can revoke them at any time — [Extension Workshop: MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)
- `activeTab` (Chrome): temporary access to the active tab after the user clicks the action, picks a context-menu item, uses a `commands` shortcut or accepts an omnibox suggestion; allows `scripting` injection, reading URL/title/favicon and intercepting main-frame-origin requests; revoked when "the user navigates away or closes the tab" (same-origin navigation keeps it); shows no install warning — [Chrome: activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)
- `cookies` API needs the `"cookies"` permission plus host permission for the site; pattern scope matters (`http://*.example.com/` cannot read secure cookies; `*://*.example.com/` can) — [MDN: cookies API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/cookies)
- `webRequest` in MV3 Chrome: "As of Manifest V3, the `"webRequestBlocking"` permission is no longer available for most extensions", only for "Policy installed extensions"; otherwise the API is observational and "unchanged and available for normal use"; `webRequestAuthProvider` is needed for `onAuthRequired`; Google points to `declarativeNetRequest` — [Chrome: chrome.webRequest](https://developer.chrome.com/docs/extensions/reference/api/webRequest)
- Safari `webRequest`: "Not supported in iOS"; "`BlockingResponse` not supported. Blocking requests not supported"; `webRequestBlocking` "Not supported. Use `permissions.webRequest` instead for macOS only" — [Apple: Assessing browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility); BCD gives Safari `webRequest` from Safari 18 — [BCD webRequest.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/webRequest.json)
- `alarms` (Chrome): "Chrome limits alarms to at most once every 30 seconds but may delay them an arbitrary amount more. That is, setting `delayInMinutes` or `periodInMinutes` to less than 0.5 will not be honored and will cause a warning"; BCD: from Chrome 117 at most 500 alarms per extension — [Chrome: chrome.alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms); [BCD alarms.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/alarms.json)
- `scripting` API: Chrome 88 (MV3), Firefox 102, Safari 15.4; Safari does not support `injectImmediately` — [BCD scripting.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/scripting.json); [Apple: Assessing browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)

### Inferences
- Manifest shape that works in all four: `permissions: ["storage","alarms","scripting","activeTab"]`, `host_permissions: ["https://claude.ai/*"]` only if claude.ai integration is a declared feature, `optional_host_permissions: ["https://*/*"]`, and a settings page where the user types `ondemand.<university>.edu` and clicks "Connect", which calls `browser.permissions.request({origins:["https://ondemand.<university>.edu/*"]})`. Store the granted origin; re-check with `permissions.contains` at startup because Firefox and Safari users can revoke per site.
- Do not request `cookies` unless the extension must read cookie values; the network path (fetch/WebSocket with host permission) carries cookies without it (next section), and `cookies` adds a store-review question.
- `webRequest` buys nothing here: MV3 cannot block, and there is no need to observe portal traffic.

### Gaps
- Chrome's own docs do not state the minimum Chrome version for `optional_host_permissions`; the "102" figure comes from BCD only.
- Whether Safari honours `optional_host_permissions` at runtime the same way as Chrome (versus its own per-site prompt) was not verified beyond the BCD note.

## Does a background fetch or WebSocket to https://ondemand.<university>.edu carry the user's session cookies once the host permission is granted?

### Takeaway
In Chrome/Edge, yes: Chrome documents that a request from an extension to a host it has permission for "is treated as same-site", so even `SameSite=Strict` session cookies are sent, provided the request is made with `credentials: "include"` (fetch defaults to `same-origin`, and the extension origin is not the portal's) and third-party cookies are not blocked; WebSocket handshakes always use credentials mode `include`. Firefox and Safari have no equivalent documented guarantee: Firefox extension pages are exempt from partitioning but the fetch case is not spelled out, and Safari developers report cookies are sent only from the default profile. A content script running on the portal's own origin sidesteps all of this because its requests are first-party page requests.

### Cited Findings
- Chrome: "Requests from an extension to a third-party are treated as same-site if the extension has host permissions for the third-party. This means `SameSite=Strict` cookies can be sent. Note that this only applies to network requests, not access through `document.cookie` in JavaScript, and does not apply if third-party cookies are blocked." Also: cookies set on `chrome-extension://` pages are always `SameSite=Lax`; "Third-party cookies are never blocked even in subframes if the top-level page for a given tab is a `chrome-extension://` page"; when an extension embeds a third-party site "that site will use the extension origin as the partition key" — [Chrome: Storage and cookies](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)
- Chrome: "A script executing in an extension service worker or foreground tab can talk to remote servers outside of its origin, as long as the extension requests host permissions"; content scripts "initiate requests on behalf of the web origin that the content script has been injected into and therefore content scripts are also subject to the same origin policy"; the doc recommends doing cross-origin requests in the service worker and warns "be careful to guard against malicious web pages" when doing so on a content script's behalf — [Chrome: Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)
- Fetch credentials mode: `same-origin` "Only send and include credentials for same-origin requests. This is the default"; `include` "Always include credentials, even for cross-origin requests" — [MDN: Request.credentials](https://developer.mozilla.org/en-US/docs/Web/API/Request/credentials)
- WebSocket handshake: in "establish a WebSocket connection" the request's credentials mode "is `include`" and its mode is `websocket` — [WHATWG WebSockets Standard](https://websockets.spec.whatwg.org/)
- Chromium-extensions list, 2023-01-11 (developer report, no Chromium-staff reply captured): "if I have proper HOST permissions for the site I'm calling with fetch, then the cookies from the main browser are indeed included in the request -- they just aren't shown anywhere in dev tools"; the poster's earlier `chrome.cookies.get`/`set` workaround was found unnecessary — [Cookies in Service Worker](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/RMUtNEhR0R8)
- Chrome third-party cookie policy: Google announced on 2025-04-22 that it will not roll out a standalone third-party-cookie prompt and is keeping the existing settings, i.e. third-party cookies remain on by default in Chrome (Incognito blocks them) — secondary reporting of the Privacy Sandbox post: [OneTrust](https://www.onetrust.com/blog/google-drops-plans-for-third-party-cookie-choice-prompt-in-chrome/); [AdExchanger](https://www.adexchanger.com/data-privacy/google-isnt-launching-a-user-choice-prompt-for-third-party-cookies-in-chrome/)
- Firefox partitioning (Total Cookie Protection, default from Firefox 103): "Extension pages (moz-extension:- URLs) cannot be partition keys, so iframes in extension documents use unpartitioned storage"; the `cookies` API works with unpartitioned storage by default and takes `partitionKey.topLevelSite` to reach partitioned cookies — [MDN: cookies API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/cookies)
- Firefox content scripts: in MV3 "Content scripts are subject to the same CORS policy as the page they are running within. Only backend scripts have elevated cross-domain privileges"; requests "happen in the context of the page, so they are made to a relative URL"; `content.fetch()` is MV2-only — [MDN: Content scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts)
- Safari, developer report March 2025 (macOS 15.4 beta 3, feedback FB15307169, no Apple reply): `fetch(url, {credentials:'include'})` from the extension with host permission sends cookies in the default "Personal" profile but not from a non-default Safari profile — [Apple Developer Forums thread 776558](https://developer.apple.com/forums/thread/776558); related reports [thread 783498](https://developer.apple.com/forums/thread/783498), [thread 764389](https://developer.apple.com/forums/thread/764389)
- Safari's compatibility page says nothing about cookie handling for extension-initiated requests; it lists `cookies.onChanged` as unsupported — [Apple: Assessing browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)

### Inferences
- Chrome/Edge background path: `fetch("https://ondemand.u.edu/rnode/...", {credentials:"include"})` and `new WebSocket("wss://ondemand.u.edu/...")` from the service worker will carry the OOD/`mod_auth_openidc` session cookie after the runtime host grant, unless the user has blocked third-party cookies (Chrome's stated exception) — Incognito profiles are the common case where that is true.
- The portal-origin content-script path is browser-independent: a content script injected into `https://ondemand.<university>.edu/*` making same-origin `fetch`/`WebSocket` calls is a first-party request in every browser (Chrome's and MDN's "acts as the page" rule), so the cookie question disappears; the cost is that a portal tab must exist and the calls are subject to the portal page's CORS/CSP as any page request is. This is the safer default for Firefox and Safari, with the service-worker path as a Chrome/Edge optimisation.
- For Safari, treat background-fetch cookies as unreliable (profile-dependent per developer reports, and untestable without a Mac in this project) and design around the content-script path or an explicit re-login in an extension-opened tab.

### Gaps
- No Chromium bug or design doc was found that says precisely what happens to host-permission requests when the user's "Block third-party cookies" setting is on; Chrome's doc only says the same-site treatment "does not apply". Needs an empirical test in a profile with third-party cookies blocked.
- No Mozilla document was found stating whether a background/event-page `fetch` with host permission sends the target's unpartitioned first-party cookies under Total Cookie Protection; the cookies-API text implies extension contexts are unpartitioned, but the network case is not stated.
- No Apple document describes cookie attachment or ITP treatment for extension-initiated background requests; the only evidence is developer forum reports.
- Whether a content script on the portal origin is exempt from the page's `connect-src` CSP for its own fetches was not verified for any browser.

## Can the extension hold a WebSocket to the portal for minutes to hours from the background, or must a page stay open?

### Takeaway
Chrome/Edge: yes from the service worker, but only if a message crosses the socket at least every 30 seconds (Chrome 116+ resets the idle timer on WebSocket send/receive; 20 s pings are the documented pattern). Firefox: the event page is killed after 30 s without an extension event or API call, WebSocket traffic is not documented as resetting that timer, and ports do not keep it alive; the documented options are alarms, extension-API calls, or (still allowed) an MV2 persistent background. Safari: MV3 backgrounds are non-persistent with no published lifetime rule. Across all four, the robust design is a reconnecting socket plus server-side tolerance, and a UI page (side panel on Chrome/Edge, sidebar on Firefox, popup on Safari) when the user is actively watching.

### Cited Findings
- Chrome termination rules: "After 30 seconds of inactivity. Receiving an event or calling an extension API resets this timer"; "When a single request, such as an event or API call, takes longer than 5 minutes to process"; "When a `fetch()` response takes more than 30 seconds to arrive"; Chrome 110: API calls reset timers; Chrome 114: "Sending a message with long-lived messaging keeps the service worker alive"; Chrome 116: "Sending or receiving messages across a `WebSocket` in an extension service worker resets the service worker's idle timer"; Chrome 109: messages from an offscreen document reset the timers; Chrome 120: alarms minimum period 30 s "to match the service worker lifecycle" — [Chrome: The extension service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

- Firefox 121 (Bugzilla 1844041, RESOLVED FIXED): any extension API call now postpones termination of the non-persistent background page, matching Chrome 110 — [Bugzilla 1844041](https://bugzilla.mozilla.org/show_bug.cgi?id=1844041)

- Safari: "With manifest version 3, all background pages are nonpersistent"; iOS requires `persistent: false` — [Apple: Assessing browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility); iOS 17.4–17.6 developer report of extension service workers being killed after about 30 s, with a 17.6 beta note "Fixed an issue where Safari Web Extension background pages would stop responding after about 30 seconds" — [Apple Developer Forums thread 758346](https://developer.apple.com/forums/thread/758346); Safari 26.6 fixed accumulating "web extension service worker registration database files" — [WebKit Features for Safari 26.6](https://webkit.org/blog/18178/webkit-features-for-safari-26-6/)

- Firefox has `sidebar_action` (Firefox 54+; not Chrome, Edge or Safari) and Chrome's `sidePanel` "is not compatible with `sidebarAction`"; BCD: `side_panel`/`sidePanel` Chrome 114, Firefox none, Safari none — [MDN: sidebarAction](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sidebarAction); [BCD side_panel.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/side_panel.json)

### Inferences
- Chrome/Edge: a service-worker WebSocket with an application-level ping every ≤20–25 s (both directions count) will hold for hours; the 5-minute single-event cap does not apply to socket traffic. Store connection state in `storage.session` so a killed worker can resume.
- Firefox: WebSocket frames do not appear anywhere in Mozilla's list of idle-timer resets; the safe pattern is to call a cheap extension API on each received frame (Firefox 121+ resets the timer on any API call) or run an alarm, and to expect the socket to die when the timer expires. Alternatively ship the Firefox build as MV2 with a persistent background, which WXT emits by default (`firefox-mv2`) and Firefox still accepts.
- Safari: assume the background dies after tens of seconds; do the long-lived work from the popup while it is open, or from a content script on the portal tab, and reconnect on wake.
- The prior analyses' preference for SSE over WebSocket is backwards for a Chrome service worker: Chrome kills the worker "when a `fetch()` response takes more than 30 seconds to arrive" and lists no streaming-body exception, whereas WebSocket traffic is an explicit keepalive since Chrome 116. If SSE is used, it should be consumed from a page (side panel/popup/portal content script), not the worker.

### Gaps
- No Mozilla source states whether WebSocket send/receive resets the Firefox idle timer (neither MDN nor the three bugs mention WebSockets). Needs a test in Firefox 140+.
- Safari's background idle timeout value and what resets it are undocumented by Apple.
- Whether Chrome counts a streaming `fetch` body (SSE chunks) as activity is not stated in the lifecycle doc.
- No documentation states whether a Chrome/Edge side-panel page keeps executing when the panel is collapsed versus closed.

## Storage of small secrets: chrome.storage.local vs session, encryption expectations, what stores forbid

### Takeaway
Extension storage is not encrypted at rest (MDN says so outright; Chrome's doc steers "sensitive user data" to `storage.session`, a 10 MB in-memory area cleared on browser restart or extension reload). The Chrome Web Store's user-data policy requires user data to be "stored at rest using a strong encryption method such as RSA or AES", so any durable token in `storage.local` must be encrypted by the extension itself, and the cleanest design keeps no durable secret at all and relies on the portal session cookie.

### Cited Findings
- Chrome quotas: `storage.local` 10,485,760 bytes ("5 MB in Chrome 113 and earlier"), raised by `unlimitedStorage`; `storage.session` 10,485,760 bytes ("1 MB in Chrome 111 and earlier"), "cleared if the extension is disabled, reloaded, updated, and when the browser restarts", "By default, it's not exposed to content scripts" (`setAccessLevel`); for `storage.sync`: "If you're working with sensitive user data, instead use storage.session" — [Chrome: chrome.storage](https://developer.chrome.com/docs/extensions/reference/api/storage)
- MDN: "Note: The storage area is not encrypted and shouldn't be used for storing confidential user information." — [MDN: storage API](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage)
- `storage.session`: in memory, cleared when the browser stops, 10 MB, not exposed to content scripts unless `setAccessLevel` — [MDN: storage.session](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/session); BCD: Chrome 102, Firefox 115, Safari 16.4; `setAccessLevel` Chrome 96 (session; all areas from Chrome 140), Firefox none, Safari 17.1 (session only) — [BCD storage.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/storage.json)
- Safari: `storage.sync` "implemented, but syncing not supported"; local limit 5 MB unless `unlimitedStorage` (unlimited from Safari 16); `storage.session` from 16.4 — [Apple: Assessing browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)
- Service workers cannot use Web Storage: "Local Storage and Session Storage are not" available — [Chrome: Storage and cookies](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)
- Chrome Web Store user-data handling: user data includes "Authentication information (such as logins, password, and authentication cookies), Website content and resources, Form data, Web browsing activity ..., Personal communications, and User-generated content"; it must be transmitted "over a secure connection (e.g. HTTPS, WSS) and stored at rest using a strong encryption method such as RSA or AES" — [Chrome Web Store: User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)
- Edge: "User-sensitive data must be encrypted by using proper mechanisms such as SSL, and must not be transported via insecure channels"; "must keep authentication information secure"; "must only use modern and secure cryptography methods to collect, store, or transmit personal information" (§1.2, §1.5.5) — [Edge Add-ons developer policies](https://learn.microsoft.com/en-us/legal/microsoft-edge/extensions/developer-policies)
- Firefox AMO: "Before an add-on may transmit personal information, it must clearly describe, and the user must affirmatively consent" — [Firefox Add-on Policies](https://extensionworkshop.com/documentation/publish/add-on-policies/)

### Inferences
- Keep per-session material (worker URL, compute node host/port, one-time tokens) in `storage.session`; keep only non-secret configuration (portal hostname, granted origin, UI prefs) in `storage.local`. If a durable secret is unavoidable, encrypt it with WebCrypto before writing to `storage.local`; the key-at-rest problem is not solved by any extension API, so the honest design is "no durable secret", authenticating through the portal's own session.
- Firefox has no `setAccessLevel`, so content scripts cannot read `storage.session` there; route content-script needs through messaging rather than shared storage.

### Gaps
- Chrome's current storage page no longer carries an explicit "not encrypted" sentence; the sensitive-data advice is only in the `storage.sync` paragraph. Whether Chrome encrypts `storage.local` on disk is undocumented (the platform's LevelDB is not encrypted by Chrome; not sourced here).

## Messaging between popup, service worker, content scripts and an optional side panel

### Takeaway
`runtime.sendMessage`/`runtime.connect` are the only cross-browser transport; Chrome 148 finally lets `onMessage` listeners return a Promise in both namespaces (Firefox and Safari already did). Long-lived ports keep a Chrome worker alive per message (Chrome 114) but do not keep a Firefox event page alive. A side panel exists on Chrome 114+ and Edge, a different sidebar API on Firefox, and none on Safari; offscreen documents are Chrome-only.

### Cited Findings
- Chrome 148: `runtime.onMessage` listeners "return a `Promise` directly to send an async response" in either namespace; `return true` still works — [Chrome: Transition to browser namespace](https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace)
- Chrome 114: long-lived messaging keeps the service worker alive; Chrome 109: offscreen-document messages reset timers — [Chrome: service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)
- Firefox: "Message ports cannot prevent an event page from shutting down"; `runtime.onSuspend` listeners are time-limited — [MDN: Background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts)
- Side panel availability: Chrome 114 / Edge (documented with the same `chrome.sidePanel` API and `"sidePanel"` permission) / Firefox `sidebar_action` only / Safari none — [Chrome: chrome.sidePanel](https://developer.chrome.com/docs/extensions/reference/api/sidePanel); [Edge sidebar guide](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/sidebar); [MDN: sidebarAction](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sidebarAction); [BCD side_panel.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/manifest/side_panel.json)
- Offscreen documents talk to the rest of the extension only through `runtime` messaging — [Chrome: chrome.offscreen](https://developer.chrome.com/docs/extensions/reference/api/offscreen)
- Content scripts making network calls on the page's behalf should go through the background, guarding "against malicious web pages" — [Chrome: Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)
- WXT emits the correct background form per browser (service worker vs scripts) from one entry — [WXT: Targeting Different Browsers](https://wxt.dev/guide/essentials/target-different-browsers)

### Inferences
- Architecture that survives all four: a typed message bus over `browser.runtime` (request/response with Promise-returning listeners; a `Port` for streaming worker output), a UI surface chosen per browser at build time (side panel on Chrome/Edge, `sidebar_action` on Firefox, popup or an extension tab on Safari), and background state in `storage.session` so any UI can re-attach after the background restarts.
- Because Firefox closes ports on idle, the UI must treat `port.onDisconnect` as routine and reconnect; because Safari has no side panel, the persistent-UI case there is a pinned extension tab.

### Gaps
- No source was captured on Safari's behaviour for `runtime.connect` ports across background unloads.

## Store policies that could reject or remove the extension, review durations, and unlisted or enterprise distribution

### Takeaway
The Chrome Web Store will scrutinise three things in this design: the wildcard `optional_host_permissions` (broad host access triggers in-depth review and must be justified per permission), reading or altering content on claude.ai (that is "website content"/"personal communications" user data, so a privacy policy, prominent in-product disclosure and affirmative consent are mandatory), and anything that looks like executing code fetched from the grid (remote code is banned in MV3 on Chrome and Edge and always on AMO). Reviews: Chrome "a few days ... up to a few weeks", AMO "up to 24 hours" for signing (longer if picked for manual review), Edge "up to seven business days", Apple undocumented here. Every store also offers a hidden/unlisted channel with the same review; enterprise force-install works on Chrome/Edge/Firefox but non-store extensions can only be forced on domain-joined or MDM-managed machines.

### Cited Findings
- Chrome Web Store single purpose: "An extension must have a single purpose that is narrow and easy to understand"; the FAQ allows a purpose defined by "a narrow focus area or subject matter" or "a narrow browser function", with a shopping extension having both an action button and host access as a compliant example; "We assume your extension utilizes each of the permissions it requests. Excessive permissions unrelated to your extension's single purpose will be viewed as enabling unrelated functionalities" — [CWS Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies); [CWS Quality Guidelines FAQ](https://developer.chrome.com/docs/webstore/program-policies/quality-guidelines-faq)
- Remote code (MV3): "The full functionality of an extension must be easily discernible from its submitted code"; external resources "must not contain any logic"; executing fetched strings or building an interpreter for remote commands are violations — [CWS Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies)
- Privacy: "If your Product handles any user data, then you must post an accurate and up to date privacy policy"; Limited Use: data only "necessary for the extension's disclosed single purpose"; "Prior to installation, it must prominently disclose what user data will be collected" and obtain "affirmative and informed consent"; permissions: "Request access to the narrowest permissions necessary" — [CWS Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies)
- User-data FAQ: extensions cannot "clip or scrape content from a website that the user visits ... capturing data from a web page" without meeting disclosure and consent requirements; disclosure must be "in a prominent way" in the product UI, and the user must take "a specific action clearly agreeing" — [CWS User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)

- Firefox enterprise `ExtensionSettings`: `installation_mode` of `force_installed` "Automatically installs the extension and prevents it from being removed by the user" and requires an `install_url` (AMO `latest.xpi` URL or a `file:///` path; Firefox re-installs when the XPI version changes); `normal_installed` allows the user to disable — [mozilla/policy-templates docs](https://mozilla.github.io/policy-templates/#extensionsettings)
- Safari review and enterprise: distribution is App Store (or Developer ID + notarization per the current Apple doc) after Apple Developer Program enrolment; the packager submits through App Store Connect review — [Apple: Distributing your Safari web extension](https://developer.apple.com/documentation/safariservices/distributing-your-safari-web-extension); Safari 18 added "Management of extension enabled state, private browsing state, and website access on managed devices" for MDM-managed macOS/iOS — [WebKit Features in Safari 18.0](https://webkit.org/blog/15865/webkit-features-in-safari-18-0/)

### Inferences
- What would trip Chrome review for this design, in order of likelihood: (1) `optional_host_permissions: ["https://*/*"]` without a precise justification ("the user enters their own university's Open OnDemand hostname; access is requested at runtime for that one origin only") and without the extension visibly refusing to work until a host is granted; (2) a content script or MAIN-world script on claude.ai that reads prompts or replaces `fetch` — that is "website content"/"personal communications" and also arguably alters a site's behaviour, so it needs an in-product consent screen before first use, a privacy policy URL, and matching data-usage checkboxes; (3) any path by which the grid returns JavaScript that the extension executes (banned as remote code; commands must be data interpreted by shipped code, and "building an interpreter for remote commands" is itself named as a violation, so keep the command vocabulary small and declarative); (4) a purpose statement that reads as two products (Claude chat modification + HPC job control). Phrase the single purpose as one narrow function, e.g. "run and monitor a Claude Code session on your university's Open OnDemand cluster from the browser", and make every permission map to a sentence in that description.
- Compliant phrasing seen in the store docs: per-permission justifications that name the user-facing feature ("`storage`: remembers the portal hostname you enter"; "`alarms`: reconnects to your running job"; "host permission for the hostname you enter: sends job requests to your university portal with your existing login"), a privacy policy that says what is read from claude.ai and that nothing is sent anywhere but the user's own university host, and a remote-code answer of "No".
- Unlisted CWS + Hidden Edge + AMO unlisted-signed XPI gives a private distribution to a university without waiving review; force-install via policy is realistic only on university-managed machines, and even then non-store items need AD/AAD/MDM enrolment on Windows/macOS. Personal laptops (students) therefore need a store-hosted item. Safari has no private channel short of TestFlight (Apple Developer Program) or the App Store.

### Gaps
- Apple App Store review duration for a Safari web-extension app was not sourced.
- No CWS policy text was found that directly addresses an extension modifying another service's page behaviour (patching `fetch` on claude.ai); whether reviewers treat that as "deceptive" or as ordinary page modification is a judgment call, and Anthropic's own terms for claude.ai automation are outside this brief.
- AMO's median human-review time for listed add-ons was not found; only the 24-hour signing statement.

- Confirmed: content scripts in MV3 are subject to the page's CORS/same-origin policy, so a MAIN-world or isolated script on claude.ai cannot itself call the university host and must relay to the background (or to a content script on the portal origin) — [MDN: Content scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts); [Chrome: Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)
