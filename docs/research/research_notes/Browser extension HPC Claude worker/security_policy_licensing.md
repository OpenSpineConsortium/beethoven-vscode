## Q0. Which claims in arch.txt / protocols.txt held up?

### Takeaway
The cookie mechanics held up; the security conclusions drawn from them did not. A service-worker `fetch` with `credentials: 'include'` does ride the OOD session cookie, but that makes the extension a bearer of the user's portal identity for the life of the session, and nothing in the OOD documentation supports the claim that the proxy "confirms the user is authorized to access the specific backend compute node". The claude.ai fetch-hijack design is barred by Anthropic's Consumer Terms; Remote Control is the sanctioned equivalent.

### Cited Findings
- Claim (a) "the browser automatically attaches the active OOD session cookies to the outbound payload" — HELD UP for Chrome: "Requests from an extension to a third-party are treated as same-site if the extension has host permissions for the third-party. This means `SameSite=Strict` cookies can be sent." Caveat in the same document: "this only applies to network requests, not access through `document.cookie` in JavaScript, and does not apply if third-party cookies are blocked." — [Chrome: Storage and cookies](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)
- Claim (a′) "at no point does the browser extension ... read, copy, or store a password, OAuth token, or SSH key" — TRUE AS STATED BUT MISLEADING. Chrome's own guidance identifies the consequence: "If developers' accounts are compromised, an attacker could push malicious code directly to all users." — [Chrome: Stay secure](https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure). The December 2024 campaign shows what a bearer-of-session extension yields: compromised extensions "Harvested authentication tokens and session cookies" and targeted "OpenAI API keys, ChatGPT session tokens, Facebook Business credentials". — [Sekoia](https://www.sekoia.com/blog/targeted-supply-chain-attack-against-chrome-browser-extensions)
- Claim (b) "The OOD proxy validates the cookie, confirms the user is authorized to access the specific backend compute node" — NOT SUPPORTED. The reference documents `host_regex` as "The regular expression used as a allowlist for allowing a user to reverse proxy to a given host", default `"[^/]+"` ("Allow proxying to all hosts in the world (please change this if you enable this feature)"), and warns "`host_regex` should always have a domain name that your center owns (for security)". No parameter or statement ties a `/rnode/<host>/<port>` request to the requesting user's Slurm jobs. — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html). The reverse-proxy setup page's only security note is a phishing warning: "Failing to add an appropriate regular expression to the Reverse Proxy opens you up to possible phishing attacks." — [Enable Reverse Proxy](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/setup/enable-reverse-proxy.html). Interactive apps carry their own secret: the connection object exposes "the password that the web server expects when authenticating the user", and "It is not safe to submit `password` in a `GET` request as this can appear in logs." — [Connection View](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/view.html)
- Claim (c) "OOD 4.1 `strip_proxy_cookies` strips `mod_auth_openidc_session` before proxying, so state must ride in the JSON body" — HELD UP. Default for `strip_proxy_cookies`: "Strip `mod_auth_openidc_session` cookies"; `strip_proxy_headers` by default "Removes numerous authentication-related headers including Authorization and OIDC claims". — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html); introduced "as a security measure against possibly leaking sensitive data to interactive applications". — [v4.1 release notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.1-release-notes.html)
- Session lifetime the extension inherits: `oidc_session_inactivity_timeout` and `oidc_session_max_duration` default `28800` seconds (8 hours). — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html)
- Claim (d) "a CustomEvent whose type is a secret UUID ensures only scripts possessing the exact secret key can listen" — NOT A SECURITY BOUNDARY. Chrome: "hostile web pages may manipulate parts of the DOM the content script depends on" and "Do not send sensitive data (e.g. secrets from the extension, data from other web origins, browsing history) to content scripts." — [Chrome: Stay secure](https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure). OWASP lists "Prototype-based Data Skimming – Malicious prototype pollution stealing data from extension scripts" and "DOM-based Data Skimming" as extension vulnerability classes. — [OWASP Browser Extension Vulnerabilities Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Browser_Extension_Vulnerabilities_Cheat_Sheet.html)
- Claim (e) MAIN-world interception of claude.ai's fetch with mocked SSE responses — BARRED BY ANTHROPIC'S TERMS. Consumer Terms (effective October 8, 2025) prohibit use "To access the Services through automated or non-human means, whether through a bot, script, or otherwise", "To decompile, reverse engineer, disassemble, or otherwise reduce our Services to human-readable form", and state "You also must not abuse, harm, interfere with, or disrupt our Services". — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms). The prior terms report already quotes the Claude Code legal page: developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" ([Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance), quoted in `Ashley terms of service constraints.md`).
- The sanctioned equivalent exists: Remote Control "connects claude.ai/code or the Claude app ... to a Claude Code session running on your machine"; "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports on your machine. When you start Remote Control, it registers with the Anthropic API and polls for work." Requirements: "available on Pro, Max, Team, and Enterprise plans. API keys are not supported." — [Remote Control](https://code.claude.com/docs/en/remote-control)
- Claim (f) `host_regex` typically restricts to the centre's domain — HELD UP (see (b)); the example in the docs is `host_regex: '[\w.-]+\.my_center\.edu'`. — [Enable Reverse Proxy](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/setup/enable-reverse-proxy.html)

### Inferences
- Because the proxy authenticates the portal user and not the job owner, the worker must carry its own per-job secret (the interactive-app pattern): generate a random token inside the batch job, deliver it to the extension over an OOD-authenticated channel, and have the worker reject any request without it. Since OOD strips OIDC headers by default, the worker cannot rely on a `REMOTE_USER`-style header either.
- Because the OIDC session dies at 8 hours by default, the extension mints no long-lived credential; that is the strongest single point in its favour under MFA policies (Q2). It also means the worker job will outlive the session and the extension must re-acquire access after re-login rather than cache anything.
- Because cookies are withheld when third-party cookies are blocked, the design must be tested in Firefox strict ETP and in Safari (ITP), and must fail loudly with a "sign in to your portal tab" message rather than silently.
- Dropping the claude.ai hijack removes the extension's need for any claude.ai host permission, which is the largest single reduction of the attack surface and of store-review friction: the extension then talks to exactly one origin, the user's portal.

### Gaps
- I found no OOD document that states in words that the proxy does or does not check job ownership; the conclusion rests on the absence of any such parameter in the reference and on the per-app password pattern. A question on the OOD Discourse would settle it.
- Whether Safari's background-page requests carry first-party cookies for a granted host under ITP was not verified.

## Q1. What is the responsible design so a stolen or malicious build cannot silently run commands on thousands of clusters, and what do stores and universities expect to see?

### Takeaway
The realistic adversary is not a browser exploit but a compromised publisher account, API key or dependency that ships a malicious update, which Chrome auto-installs; three incidents in 2024–2025 used exactly that path. Mitigations that are required by the stores (no remote code, least permissions, 2-step verification, in-UI disclosure, reviewable source with reproducible build for Mozilla) should be paired with mitigations that are customary or self-imposed (runtime per-site host permission, no `cookies` permission, local audit log, signed kill-list, pinned and attested builds, a worker-side per-job token). Universities can already confine the extension by policy (`runtime_blocked_hosts`).

### Inferences
- Design that survives a stolen build: (i) no install-time host permission; declare `optional_host_permissions: ["https://*/*"]` and request the single portal origin from a button click, so a malicious update inherits access to one origin per user, not to "all sites"; (ii) no `cookies` permission (the cookie is used, never read); (iii) no content script on claude.ai and, ideally, none on the portal either — talk to the portal from the service worker only, which removes the DOM-injection and prototype-skimming classes entirely; (iv) one chokepoint function for every portal request that writes an append-only local audit record (timestamp, endpoint, job id, byte count) the user can view and export, nothing of which leaves the device; (v) a daily fetch of a signed JSON kill-list (data, therefore permitted under the remote-code rule) verified with an Ed25519 public key in the bundle; a revoked version refuses to send commands and tells the user; (vi) release pipeline with lockfile + `npm ci`, actions pinned by commit SHA, provenance from a hosted builder (SLSA L2 at minimum), reproducible-build instructions (already required by Mozilla) published for all stores, and a publisher account with a hardware key and no third-party OAuth grants (the Cyberhaven vector) and no long-lived store API keys in CI (the Trust Wallet vector); (vii) worker-side per-job token (Q0) so that even a request that reaches the proxy with a valid session cannot drive another user's worker.
- What a university security office will ask to see, judging from the enterprise controls above and Q5: the exact host list and permission list (so `runtime_allowed_hosts` can be set), the privacy policy, the source repository and build instructions, the signing key and revocation mechanism, and a statement that the extension never stores a credential.
- The kill-list server is the one piece of vendor infrastructure the design cannot avoid; it must be treated as sensitive as the publisher account (same hardware-key rule), and the extension must fail safe (keep working offline on the last good list, refuse only on a verified revocation) so that an outage of a one-person vendor does not strand a university.

## Q2. Is using the user's OOD session from an extension "credential sharing" under typical AUPs, or the user's own use? Quote the words.

### Takeaway
None of the nine policies read defines sharing as anything other than giving credentials to another person; an extension acting inside the same authenticated browser session is the user's own use, and every cluster that has written an AI-agent policy (NERSC, USC, Utah, Aalto) makes the user answerable for what the agent does. The live constraint is not "sharing" but institutional approval: Wayne State says third-party AI bots are not approved, and Utah bans autonomous agents outright.

### Inferences
- "Credential sharing" in every AUP read means transfer to another human ("other individuals", "anyone else", "another person's computer account"). Software the user installs, running in the user's own browser profile against the user's own session, is on the same footing as the portal's own JavaScript or a Jupyter session launched through OOD. It becomes third-party access only if the vendor's code exfiltrates the session, at which point the AUP clause that bites is the user's responsibility clause ("Users are responsible for all activities conducted under their account"), not the sharing clause. That is an argument for the Q1 design, not against the product.
- The extension does not touch the MFA approval step (the user completes Duo on the portal; the extension reuses the resulting 8-hour session), so UConn-style prohibitions on "automated systems that intend to interfere with the approval component" are not triggered. Worth stating in the documentation in those words.
- The binding questions are approval and mode of operation: at Wayne State the extension is a "third-party AI bot" until C&IT approves it; at Utah a worker in a batch job driven from a browser must be presented as a supervised, approved agent (Claude Code is on their module list; an unattended loop would fall under the OpenClaw ban). The product should ship in "supervised" mode by default — every command shown and approved in the Remote Control UI — and document that.
- WSU's grid policy is silent on services in jobs; running a worker inside a Slurm allocation is compliant with the only rule it states (nothing on Warrior). Long-running-service rules elsewhere (UMD's `srun ... bash` clause) target reservation without work; a worker that idles should stop itself, and the extension should expose the idle timeout.

- No US university statement that a browser extension acting through OOD is, or is not, permitted was found; OOD-specific guidance on third-party clients appears not to exist.

## Q3. What happens when a worker touches restricted data (FERPA, HIPAA, export-controlled, IRB), what must the extension say and refuse, and where do Remote Control transcripts live?

## Q4. What must the vendor promise about data (and refuse to collect) to pass Chrome Web Store, AMO and Safari review, and a university security questionnaire?

### Takeaway
All three stores require a privacy policy, in-product disclosure and consent before any collection, encryption in transit, and a declared data inventory; Firefox now enforces the inventory in the manifest for every new extension since November 3, 2025. The cleanest position is to collect nothing server-side except licence activation records, keep audit logs and portal hostnames on the device, and declare that; GDPR attaches if EU users are offered the product, CCPA will not at this scale, and Michigan still has no comprehensive privacy statute but does have breach-notice law.

### Inferences
- Data inventory that passes all three stores and reads well on a HECVAT: collected off-device = licence activation (key id, AccessID or its hash, extension version, timestamp, coarse platform) and, if the prior report's opt-out crash pipeline is kept, crash reports with the five vendor guardrails already specified there; processed on-device only = portal hostnames (as permission grants), job ids, the audit log, the Remote Control pairing data. Portal hostnames and AccessIDs identify a person and institution, so they are personal data under GDPR and "personally identifiable information" under Chrome's list; if they never leave the device they still require the privacy policy and in-UI disclosure (Chrome's local-processing rule) but not a server-side retention regime.
