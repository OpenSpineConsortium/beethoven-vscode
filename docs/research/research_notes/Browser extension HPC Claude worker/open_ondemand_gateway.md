# Open OnDemand as the university-agnostic browser gateway to a Claude Code worker on an HPC cluster

State as of 2026-09-28. Primary sources are the `OSC/ondemand` repository (branch `master` read on 2026-09-28, and tagged releases `v2.0.32`, `v3.0.3`, `v3.1.14`, `v4.1.0`, `v4.2.5`), the 4.2.0 documentation at osc.github.io, and Discourse threads answered by the OnDemand maintainers. Latest releases on GitHub: v4.2.5 (2026-09-24), v4.1.7 (2026-08-31), v4.2.4 (2026-08-25), v4.0.11 (2026-04-29), v4.2.0 (2026-04-15) — [GitHub releases](https://github.com/OSC/ondemand/releases).

Wherever a claim rests on reading code rather than running it, that is stated. Wherever a claim rests on a search-engine snippet rather than a fetched page, that is stated.

Vocabulary used below: **PUN** = per-user NGINX, the process OOD starts as the Linux user to run their Passenger apps. **Dashboard** = the Rails app at `/pun/sys/dashboard` (Files, Active Jobs, Interactive Apps, Projects live inside it). **Job Composer** = the separate legacy Rails app at `/pun/sys/myjobs`. **Shell** = the Node app at `/pun/sys/shell`.

## Q0. Which OOD claims in the two prior analyses (arch.txt, protocols.txt) held up?

### Takeaway
Their reverse-proxy description is essentially right (URI shapes, `host_regex`, `ood_portal.yml`, Lua handlers, WebSocket pass-through, 4.1 cookie/header stripping, `--export=NONE`). Their authentication story is right for a content script on the OOD origin and only partly right for a service worker (cookies yes, but Rails CSRF Origin checking rejects non-GET writes from an extension origin). Their claim that the extension can "extract the compute host and port from the URL string of the active OOD session" is unsupported: there is a cleaner, documented file path for that. Neither analysis examined the Shell WebSocket, the Files API, or job-submission endpoints at all.

### Cited Findings (claim by claim)
- CLAIM "`/node/<host>/<port>/<path>` forwards the full path; `/rnode/…` strips the prefix" — **HELD**. `ood_portal.yml` reference: `node_uri` "will reverse proxy to the given host and port using the **full** URI path"; `rnode_uri` "using the **relative** URI path", both default `null` — [ood_portal.yml reference (4.2.0)](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html). Apache template: `<LocationMatch "^<%= @node_uri %>/(?<host><%= @host_regex %>)/(?<port>\d+)">` vs `<LocationMatch "^<%= @rnode_uri %>/(?<host><%= @host_regex || "[^/]+" %>)/(?<port>\d+)(?<uri>/.*|)">` and the comment `#=> http://HOST:PORT/index.html` for rnode — [ood-portal.conf.erb](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/templates/ood-portal.conf.erb). Lua: `conn.uri = uri or r.uri or '/'` — [node_proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/node_proxy.lua).
- CLAIM "`host_regex` in `ood_portal.yml` restricts targets" — **HELD**, with a correction: the default is `"[^/]+"`, i.e. *all* hosts including external ones, and the docs warn "Wildcards like `.` should be avoided" — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html); example file: "Default: '[^/]+' (allow reverse proxying to all hosts, this allows external hosts as well)" — [ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml).
- CLAIM "mod_ood_proxy with Lua scripts (proxy.lua) tunnels HTTP and WebSocket" — **HELD**. `if r.headers_in['Upgrade'] then protocol = use_ssl and "wss://" or "ws://"` — [ood/proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/ood/proxy.lua).
- CLAIM "OOD 4.1 introduced `strip_proxy_cookies` / `strip_proxy_headers`, stripping `mod_auth_openidc_session`" — **HELD**. Both "Since 4.1"; `strip_proxy_cookies` default `["mod_auth_openidc_session_\\d+", "mod_auth_openidc_session"]`; `strip_proxy_headers` default begins `["Authorization", "OIDC_CLAIM_sub", …, "OIDC_access_token", "OIDC_access_token_expires"]` — [ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml); [v4.1 release notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.1-release-notes.html).
- CLAIM "the browser's existing OOD session cookies authenticate the proxy request; `credentials: 'include'` from the service worker attaches them" — **PARTLY HELD**. Apache auth directives are applied inside each `/node`, `/rnode`, `/pun`, `/nginx` Location (`<%- @auth.each do |line| -%>`) — [ood-portal.conf.erb](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/templates/ood-portal.conf.erb). Chrome: "Requests from an extension to a third-party are treated as same-site if the extension has host permissions for the third-party. This means `SameSite=Strict` cookies can be sent. Note that this only applies to network requests, not access through `document.cookie` in JavaScript, and does not apply if third-party cookies are blocked." — [Chrome: Storage and cookies](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies). What the analyses missed: Rails CSRF in the dashboard (see Q2) rejects non-GET requests whose `Origin` is not the OOD origin.
- CLAIM "the extension extracts the compute `<host>` and `<port>` from the URL string of the active OOD session" — **NOT SUPPORTED**. Interactive-session connection info lives in `connection.yml` under the session's staged directory, readable through the Files API (Q4); the dashboard's session card links are rendered server-side from that file — [batch_connect/session.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/models/batch_connect/session.rb).
- CLAIM "OOD uses hundreds of research computing centers" — **UNDERSTATED**. "Over 2,100 organizations worldwide" — [openondemand.org](https://www.openondemand.org/); "As of December 2023, it was in use at nearly 1,700 RC service providers in nearly 100 countries" — [Chalker et al., PEARC '24 (NSF PAR copy)](https://par.nsf.gov/servlets/purl/10538354).
- CLAIM "OOD drives Slurm through CLI `sbatch` with `--export=NONE` by default" — **HELD**. `call("sbatch", *args, env: env, stdin: str.to_s)`; `args.concat ["--export", export_arg(env, script.copy_environment?)]`; comment "we default to export NONE, but SLURM defaults to ALL" — [ood_core slurm.rb](https://github.com/OSC/ood_core/blob/master/lib/ood_core/job/adapters/slurm.rb).
- CLAIM "SSE passes through the OOD Apache proxy; set `X-Accel-Buffering: no`" — **UNVERIFIED**. No OOD source or doc found that discusses SSE buffering through `mod_proxy`; `X-Accel-Buffering` is an NGINX header and the front proxy is Apache (the PUN is NGINX but is not in the `/node` path). The dashboard itself sets `X-Accel-Buffering: no` only for remote-file streaming — [files_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/files_controller.rb).
- CLAIM "host_regex example `'[\w.-]+\.wayne\.edu'`" — this is the documentation's `'[\w.-]+\.my_center\.edu'` pattern with the domain substituted; Wayne State's actual value is not public — [Enable reverse proxy docs](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/setup/enable-reverse-proxy.html).

### Inferences
- The architecture the analyses propose (extension → OOD cookie session → `/rnode/` → FastAPI in a compute job) is feasible on sites where the admin has set `rnode_uri` (or `node_uri`) and a `host_regex` that matches compute nodes. On sites where it is `null` (the default), nothing about the extension can substitute for it; the Shell WebSocket becomes the only transport (Q1).

### Gaps
- Neither analysis, nor any source found, addresses Firefox or Safari extension cookie behaviour toward OOD; everything below about extension contexts is Chrome-documented only.

## Q1. How does the Shell app WebSocket work, and is driving it from an extension realistic and stable across versions?

### Takeaway
The socket is `wss://<ood>/pun/sys/shell/ssh/<host>[/<abs dir>]?csrf=<token>`, no subprotocol; the client sends JSON text frames `{"input": "..."}` and `{"resize": {"cols": N, "rows": N}}`, the server sends raw PTY bytes as text frames, and the server side is an `ssh <host>` spawned inside the user's PUN on the OOD web node. The framing has not changed from 2.0 to 4.2.5. Three gates decide admission: a per-process CSRF token scraped from the shell page, an Origin comparison that a `chrome-extension://` origin bypasses by construction, and a host allowlist. Defaults kill an idle socket after 5 minutes and any socket after 1 hour.

### Cited Findings
**Routing and page**
- Express routes: `router.get(['/', '/ssh'], … res.redirect(req.baseUrl + '/ssh/default'))` and `router.get('/ssh{*splat}', …)`, mounted at `process.env.PASSENGER_BASE_URI || '/'`; host/dir parsed with `const host_path_rx = '/ssh/([^\\/\\?]+)([^\\?]+)?(\\?.*)?$'`; `hostname = match[1] === "default" ? default_sshhost : match[1]`; `directory = match[2] ? decodeURIComponent(match[2]) : null` — [apps/shell/app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js).
- The app's request URI under the PUN is `/sys/%{name}` beneath `pun_uri` `/pun`, so the page is `/pun/sys/shell/ssh/<host>` — [nginx_stage_example.yml](https://github.com/OSC/ondemand/blob/master/nginx_stage/share/nginx_stage_example.yml) (`app_request_uri: sys: '/sys/%{name}'`), [ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml) (`pun_uri: '/pun'`).
- README URL forms: `/ssh/<host>`, `/ssh/default/<dir>`, `/ssh/<host>/<dir>` — [apps/shell/README.md](https://github.com/OSC/ondemand/blob/master/apps/shell/README.md). The Files JSON exposes the same link shape as `shell_url` (`OodAppkit.shell.url(path: @path.to_s)`) — [files/index.json.jbuilder](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/views/files/index.json.jbuilder).
- The page embeds a fresh token: `res.render('index', { baseURI: req.baseUrl, csrfToken: tokens.create(secret), host: theHost, dir: theDir, … })` where `const tokens = new Tokens({}); const secret = tokens.secretSync();` are created once per Node process — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js).

**Client-side URL and framing**
- URL builder in the page: `var base = document.URL.replace(/^http/, 'ws').replace(/#.*$/, ''); var separator = '?'; if(base.includes('?')){ separator = '&'; } return base + separator + "csrf={{csrfToken}}";` — [views/index.hbs](https://github.com/OSC/ondemand/blob/master/apps/shell/views/index.hbs).
- Socket open: `this.socket = new WebSocket(this.url);` (no subprotocol argument). Input: `this.socket.send(JSON.stringify({ input: str }));`. Resize: `this.socket.send(JSON.stringify({ resize: { cols: columns, rows: rows } }));`. Output: `this.term.io.print(ev.data);`. Close handling: `else if (ev.code === 3146) { … errorDiv.innerHTML = ev.reason; }`; other closes print "Your connection to the remote server has been terminated." Terminal emulator is hterm (`hterm_all_1.92.1.mod_1.js`), not xterm.js — [public/javascripts/ood_shell.2.js](https://github.com/OSC/ondemand/blob/master/apps/shell/public/javascripts/ood_shell.2.js), [index.hbs](https://github.com/OSC/ondemand/blob/master/apps/shell/views/index.hbs).

**Server-side admission**
- `const wss = new WebSocket.Server({ noServer: true });` … `server.on('upgrade', function upgrade(request, socket, head) { wss.handleUpgrade(request, socket, head, function done(ws) { wss.emit('connection', ws, request); }); });` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js).
- In `wss.on('connection', …)`: `token = req.url.match(/csrf=([^&]*)/)[1];` then `authError = detect_auth_error(token, req.origin, custom_server_origin(default_server_origin(req)), host);` then `if (authError) { // 3146 has no meaning, any number between 3000-3999 is fair to use  ws.close(3146, authError); }` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js).
- Gate order and exact reasons: `if (host_allowlist.length == 0) { return "No clusters defined."; } else if (client_origin && client_origin.startsWith('http') && server_origin && client_origin !== server_origin) { return "Invalid Origin."; } else if (!tokens.verify(secret, requestToken)) { return "Bad CSRF Token."; } else if (!helpers.hostInAllowList(host_allowlist, host)) { return \`Host "${host}" not specified in allowlist or cluster configs.\`; }` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js).
- Server-origin derivation: `if (headers['x-forwarded-proto'] && headers['x-forwarded-host']){ origin = headers['x-forwarded-proto'] + "://" + headers['x-forwarded-host'] }`, overridable by `OOD_SHELL_ORIGIN_CHECK` (used only if it `startsWith('http')`; any other value disables the comparison) — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js). Docs: set `OOD_SHELL_ORIGIN_CHECK` to the correct https string or to `off` in `/etc/ood/config/apps/shell/env` if valid connections are denied — [Customizations (4.2.0)](https://osc.github.io/ood-documentation/latest/customizations.html).
- Host allowlist: `OOD_SSHHOST_ALLOWLIST` split on `:`, plus every non-hidden cluster login host: `.filter(config => (config && config.v2 && config.v2.login && config.v2.login.host) && ! (config.v2 && config.v2.metadata && config.v2.metadata.hidden))`, matched with `minimatch(host, value)`; default host = `OOD_DEFAULT_SSHHOST || DEFAULT_SSHHOST`, else the cluster with `login.default`, else the first host alphabetically — [utils/helpers.js](https://github.com/OSC/ondemand/blob/master/apps/shell/utils/helpers.js). Docs describe the allowlist as "colon (:) separated list of GLOBs" and say cluster login hosts not marked hidden are added automatically — [Customizations](https://osc.github.io/ood-documentation/latest/customizations.html).

**What the socket is attached to**
- `cmd = process.env.OOD_SSH_WRAPPER || 'ssh'`; `args = dir ? [host, '-t', 'cd \'' + dir.replace(/\'/g, "'\\''") + '\' ; exec ${SHELL} -l'] : [host];` `term = pty.spawn(cmd, args, { name: termName, cols: 80, rows: 30 });` where `termName = OOD_SHELL_TERM || 'xterm-16color'` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js). Documentation: "the Shell App then forks off an ssh process that connects to a server specified by the administrator (typically a login node)… when the user drops the websocket connection, the ssh process is terminated" — [Shell App docs (1.8, still accurate to the code)](https://osc.github.io/ood-documentation/release-1.8/applications/shell.html).
- Server message handling: `ws.on('message', function (msg) { msg = JSON.parse(msg); if (msg.input) { term.write(msg.input); ws.lastActivity = Date.now(); } if (msg.resize) term.resize(parseInt(msg.resize.cols), parseInt(msg.resize.rows)); });` and output `term.onData(function (data) { ws.send(data, …); ws.lastActivity = Date.now(); });` `term.onExit(… ws.close())`; `ws.on('close', … term.end())` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js).

**Timeouts and ping**
- `const inactiveTimeout = (process.env.OOD_SHELL_INACTIVE_TIMEOUT_MS || 300000); const maxShellTime = (process.env.OOD_SHELL_MAX_DURATION_MS || 3600000); const pingPongEnabled = process.env.OOD_SHELL_PING_PONG ? true : false;` and every 30 s: `if (ws.isAlive === false || inactiveFor > inactiveTimeout || timeUsed > maxShellTime) { return ws.terminate(); } if(pingPongEnabled) { ws.isAlive = false; ws.ping(); }` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js). Documented defaults: `OOD_SHELL_INACTIVE_TIMEOUT_MS` 300000 (5 min), `OOD_SHELL_MAX_DURATION_MS` 3600000 (1 h), `OOD_SHELL_PING_PONG` disabled unless set, all in `/etc/ood/config/apps/shell/env` — [Customizations](https://osc.github.io/ood-documentation/latest/customizations.html); "Shell Ping Pong disabled by default" — [v3.1 release notes](https://osc.github.io/ood-documentation/latest/release-notes/v3.1-release-notes.html).

**Stability across versions (from the tagged sources)**
- v2.0.32: same `msg.input` / `msg.resize.cols|rows` framing and `?csrf=` query, but checks ran in the HTTP `upgrade` handler using `request.headers['origin']` and rejected with `'HTTP/1.1 401 Unauthorized'` plus `'X-OOD-Failure-Reason: invalid origin'` / `'bad csrf token'` / `'host not specified in allowlist or cluster configs'`; no inactivity or max-duration timers — [app.js @ v2.0.32](https://github.com/OSC/ondemand/blob/v2.0.32/apps/shell/app.js).
- v3.0.3: checks moved into the `connection` handler with `req.origin` and `ws.close(3146, authError)`; still no timers — [app.js @ v3.0.3](https://github.com/OSC/ondemand/blob/v3.0.3/apps/shell/app.js).
- v3.1.14, v4.1.0, v4.2.5, master: identical admission logic and framing; timers and ping-pong present from 3.1.14 on — [v3.1.14](https://github.com/OSC/ondemand/blob/v3.1.14/apps/shell/app.js), [v4.1.0](https://github.com/OSC/ondemand/blob/v4.1.0/apps/shell/app.js), [v4.2.5](https://github.com/OSC/ondemand/blob/v4.2.5/apps/shell/app.js). 4.1 added `OOD_SHELL_TERM` and per-connection log prefixes; 4.2 changed nothing in the shell — [v4.1 notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.1-release-notes.html), [v4.2 notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.2-release-notes.html).
- Community reports of the origin check biting behind additional proxies (X-Forwarded-Host mismatch): [Websocket not working behind web proxy](https://discourse.openondemand.org/t/websocket-not-working-behind-web-proxy/3602/5), [Ood v4.1.1, Shell Access failed to launch](https://discourse.openondemand.org/t/ood-v4-1-1-shell-access-failed-to-launch/4770).

**Process model**
- One Passenger process per app per user: `passenger_max_instances_per_app 1;` "Limit app instances to 1 so apps can safely utilize in memory session data"; `passenger_min_instances 0;` "Kill all apps after they idle timeout"; `passenger_pool_idle_time` default 300 — [pun.conf.erb](https://github.com/OSC/ondemand/blob/master/nginx_stage/templates/pun.conf.erb), [nginx_stage_example.yml](https://github.com/OSC/ondemand/blob/master/nginx_stage/share/nginx_stage_example.yml).

### Inferences
- **Driving it programmatically is realistic**: fetch `/pun/sys/shell/ssh/<host>` with the session cookies, regex the inline script for `csrf=`, open `wss://…/pun/sys/shell/ssh/<host>?csrf=<token>` within seconds, send `{"input": "..."}`, read text frames. The framing has been byte-identical from 2.0 through 4.2.5, so a driver written against it is not version-fragile.
- **Token freshness matters**: because `secret` is per Node process and Passenger kills an idle shell process after 300 s, a token scraped minutes earlier can fail with reason "Bad CSRF Token." Always scrape immediately before connecting (an open socket keeps the process alive; the 4.1.1 thread shows sockets surviving while the page is open).
- **Origin from a service worker**: a `chrome-extension://<id>` origin does not `startsWith('http')`, so the "Invalid Origin." branch is skipped by construction; from a content script the Origin is the OOD origin and matches. Separately, in 3.0.3+ the code reads `req.origin` and `default_server_origin(req)` (which indexes `req['x-forwarded-proto']` on the request object rather than `req.headers[...]`), whereas 2.0 read `request.headers[...]`; if both are undefined at runtime the comparison is inert — this is a reading of the source, not a runtime test.
- **The socket has no delivery semantics**: sends are fire-and-forget, there is no per-message ack, output is a raw VT stream (an `exec ${SHELL} -l` prompt, control sequences, `xterm-16color` termcap), and each connection is a brand-new ssh + login shell. Anything long-running must be detached on the far side (tmux/nohup or immediate `sbatch`), because closing the socket runs `term.end()` and ends the ssh session. The 1 h `OOD_SHELL_MAX_DURATION_MS` default terminates the socket regardless of activity; only real input (`msg.input` truthy) or PTY output resets the 5 min inactivity timer — `{"resize":…}` and empty `{"input":""}` do not.
- A non-JSON frame makes `JSON.parse` throw inside the handler; with one process per app per user, a crash there would drop all of that user's shells (inference from `passenger_max_instances_per_app 1`).
- The CSRF token travels in the query string, so it appears in Apache and PUN access logs; treat it as short-lived.

### Gaps
- Whether `req.origin` is populated in the deployed `ws`/Node combination was not run; only the code was read.
- No source states which login host Wayne State's shell connects to; the KB says only "Open a shell of the Grid".

## Q2. Do cookies, Origin and CSRF work from an extension service worker versus a content script on the OOD origin?

### Takeaway
Chrome sends the OOD cookies on extension-initiated requests (including, by the same rule, the WebSocket handshake) when the extension holds host permission for the OOD host. The Origin header differs by context, and that decides what works: the Node shell accepts either; the Rails apps (dashboard, myjobs) reject state-changing requests whose Origin is not the OOD origin, so file writes, uploads and job submissions should be issued from a content script (or an injected page script) on the OOD origin, carrying the page's `X-CSRF-Token`.

### Cited Findings
- Chrome: "Requests from an extension to a third-party are treated as same-site if the extension has host permissions for the third-party. This means `SameSite=Strict` cookies can be sent. Note that this only applies to network requests, not access through `document.cookie` in JavaScript, and does not apply if third-party cookies are blocked." — [Chrome: Storage and cookies](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies).
- Chrome: "A script executing in an extension service worker or foreground tab can talk to remote servers outside of its origin, as long as the extension requests host permissions." and "Content scripts initiate requests on behalf of the web origin that the content script has been injected into and therefore content scripts are also subject to the same origin policy." — [Chrome: Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests).
- Chrome WebSockets in service workers: "Starting with Chrome 116, extension service workers get improved support for WebSockets… you can keep a service worker with a WebSocket connection active by exchanging messages within the 30s service worker activity window", with a keepalive every 20 s — [Chrome: Use WebSockets in service workers](https://developer.chrome.com/docs/extensions/how-to/web-platform/websockets).
- Conflicting community report that cookies were *not* attached to a service-worker `fetch` until re-set via `chrome.cookies.set` — [chromium-extensions: Cookies in Service Worker](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/RMUtNEhR0R8) (anecdotal; contradicts the official page above).
- Rails side: dashboard `ApplicationController` has `protect_from_forgery with: :exception` — [application_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/application_controller.rb); both dashboard and myjobs use `config.load_defaults(7.0)` — [dashboard config/application.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/config/application.rb), [myjobs config/application.rb](https://github.com/OSC/ondemand/blob/master/apps/myjobs/config/application.rb). Rails: `config.action_controller.forgery_protection_origin_check` "controls whether the `Origin` header is checked in addition to the `Referer` header… Starting with version 5.0 the default value is `true`"; `per_form_csrf_tokens` likewise true from 5.0 — [Rails Guides: Configuring](https://guides.rubyonrails.org/configuring.html).
- Evidence that Chrome sends `Origin: chrome-extension://…` on extension POSTs: "the successful POSTs are consistent with Chrome sending the extension origin for POST" while Chromium omits Origin on GET — [mdbase-connect issue #472](https://github.com/mdbase-dev/mdbase-connect/issues/472) (third-party issue tracker; weak source, consistent with the Fetch standard).
- OIDC session cookie properties: name defaults to `mod_auth_openidc_session`; `OIDCCookieHTTPOnly` "When not defined the default is On"; `OIDCCookieSameSite` "When set to "On" (default) or "Lax"… session cookie: Lax"; "Off" or "None" → `None` — [mod_auth_openidc auth_openidc.conf](https://github.com/OpenIDC/mod_auth_openidc/blob/master/auth_openidc.conf). OOD sets `OIDCCookieSameSite <%= @oidc_cookie_same_site %>` — [ood-portal.conf.erb](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/templates/ood-portal.conf.erb); documented default "On" when SSL is not defined and "Off" when it is — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html).
- Content Security Policy: the dashboard emits a CSP only `if Configuration.csp_enabled?` (default off), with `connect_src` from `Configuration.connect_sources` — [content_security_policy.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/config/initializers/content_security_policy.rb). Apache adds `Content-Security-Policy frame-ancestors` (`security_csp_frame_ancestors`, default the servername) and HSTS — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html).

### Inferences
- **Service worker (background)**: GET reads of dashboard JSON, file downloads, and the Shell WebSocket all work with `credentials: 'include'` and host permission (cookies attach; the shell skips a non-http Origin). Non-GET requests to Rails endpoints will fail Rails' Origin check (HTTP 422 `ActionController::InvalidAuthenticityToken`) even with a valid `X-CSRF-Token`, because the request `Origin` is `chrome-extension://…`, not `https://<ood>`.
- **Content script on `https://<ood>/…`**: same-origin fetch with `credentials: 'same-origin'`, `Origin`/`Referer` are the OOD origin, and the page's `<meta name="csrf-token">` (standard Rails; not separately verified in OOD's layout) supplies `X-CSRF-Token`. This is the context for `PUT files/fs`, `POST files/upload`, `POST transfers`, `POST …/session_contexts`, `PUT …/workflows/:id/submit`. A content script can open the Shell WebSocket too (Origin matches).
- If a site turned on the dashboard CSP with a restrictive `connect_src`, a content script's fetches are still governed by the page CSP; the service worker's are not. Default is CSP off.
- For the `/rnode/` path to a user service, none of the Rails CSRF machinery applies; only Apache auth (cookies) and whatever the user's service checks. Note the OIDC cookie and `Authorization` header are stripped before reaching that service on 4.1+ (Q5), so the service must use its own token (query/body/custom header) rather than reading the OOD session.

### Gaps
- Firefox MV3 cookie/host-permission behaviour toward a SameSite=Lax OIDC cookie was not researched.
- Whether OOD's dashboard layout includes the Rails `csrf_meta_tags` helper was not read directly; it is the Rails default and the Files app's uppy uploader must be supplying the token somehow.

## Q3. Files app HTTP/JSON endpoints (dashboard, 3.x–4.x)

### Takeaway
The Files app is a small, stable JSON-capable HTTP surface: `GET files/fs/<abs path>` with `Accept: application/json` lists a directory (fields below); `?download=1` streams a file or a zip of a directory; `PUT files/fs/<abs path>` writes a file body, `?dir=true` makes a directory, `?touch=true` touches; `POST files/upload/fs` is a multipart upload; `POST transfers` copies/moves/removes. Every write needs the Rails CSRF token and is gated by site switches (`upload_enabled`, `download_enabled`, `OOD_ALLOWLIST_PATH`, 10 GB upload cap).

### Cited Findings
- Routes (verbatim): `get 'files/:fs(/*filepath)' => 'files#fs', :defaults => { :fs => 'fs', :format => 'html' }`, `put 'files/:fs/*filepath' => 'files#update', … :defaults => { :fs => 'fs', :format => 'json' }`, legacy `get 'files/api/v1/:fs(/*filepath)'` / `put 'files/api/v1/:fs/*filepath'` ("backwards compatibility with the 'api' routes that OodAppkit provides and are used by File Editor and Job Composer"), `post 'files/upload/:fs' => 'files#upload' … if Configuration.upload_enabled?`, `get 'files', to: redirect("files/fs#{Dir.home}")`, `resources :transfers, only: [:show, :create, :destroy]`, `get 'files/edit/:fs/*filepath' => 'files#edit'`; all under `if Configuration.can_access_files?` — [dashboard routes.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/config/routes.rb). - JSON negotiation: `request.format = 'json' if json_request?` where `json_request?` = `request.headers['HTTP_ACCEPT'].to_s.split(',').include?('application/json')`; directory JSON sets `Cache-Control: no-store`; `?can_download` returns `{ can_download:, error_message: }`; `?download` on a directory streams a zip and on failure `head :internal_server_error` with header `X-OOD-Failure-Reason` ("Third party API requests (from outside of OnDemand) will see this error message…") — [files_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/files_controller.rb).

- Transfers: `POST transfers` reads a JSON body `{command, files, from_fs, to_fs}` → `PosixTransfer.build(action: body_params[:command], files: body_params[:files])`, performs synchronously or `perform_later`, renders `transfers/show` JSON; `GET transfers/:id.json`; `DELETE transfers/:id` cancels — [transfers_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/transfers_controller.rb).
- Limits and switches: `nginx_file_upload_max: '10737420000'` → `client_max_body_size` in the PUN; dashboard `FILE_UPLOAD_MAX` (bytes) — [nginx_stage_example.yml](https://github.com/OSC/ondemand/blob/master/nginx_stage/share/nginx_stage_example.yml), [pun.conf.erb](https://github.com/OSC/ondemand/blob/master/nginx_stage/templates/pun.conf.erb), [Customizations](https://osc.github.io/ood-documentation/latest/customizations.html); 4.1: `OOD_DOWNLOAD_FILE_MAX` default 10 GiB, `OOD_FILE_EDITOR_MAX_SIZE` 12 MiB, `OOD_UNSAFE_RENDER_HTML` — [v4.1 notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.1-release-notes.html); 3.1: `upload-enabled`/`download-enabled` switches and Globus integration — [v3.1 notes](https://osc.github.io/ood-documentation/latest/release-notes/v3.1-release-notes.html); 3.0: rclone remotes (`files/<remote>/…`) and `OOD_ALLOWLIST_PATH` (renamed from `WHITELIST_PATH`) — [v3.0 notes](https://osc.github.io/ood-documentation/latest/release-notes/v3.0-release-notes.html).

### Inferences
- A complete file-based mailbox (write a request JSON with `PUT`, poll a directory listing with `GET … Accept: application/json`, download results with `?download=1`) needs nothing but the dashboard, and works on every 3.x/4.x site that has not disabled Files. It is the lowest-dependency channel available and needs no admin action.
- Directory polling cost: each listing is a Rails request under the user's PUN doing `ls`-style stat calls; poll intervals of a few seconds are reasonable, sub-second is not.

### Gaps
- `transfers/show.json` field names were not fetched.
- Behaviour of `PUT` with a multi-gigabyte body (nginx `client_max_body_size` applies to PUT too, inferred, not tested).

## Q5. What does the reverse proxy require of a service in a compute job, and can a user-started service be reached?

### Takeaway
Yes, if and only if the admin set `node_uri`/`rnode_uri` (both default `null`) and a `host_regex` matching compute-node names; then any authenticated OOD user can reach any TCP port on any matching host. There is no port range, no path allowlist and no check that the caller owns a job on that host. On 4.1+ the OIDC cookies and `Authorization` header are stripped before the request reaches the service, and `X-Forwarded-User` is set by Apache. `/node/` presents the full `/node/<host>/<port>/...` path to the backend; `/rnode/` presents only the remainder. WebSockets are proxied.

### Cited Findings
- Settings and defaults: `host_regex` default `'[^/]+'`; `node_uri` default `null`; `rnode_uri` default `null`; `secure_node_uri`/`secure_rnode_uri` (4.1) "force the upstream connection to use HTTPS or WSS" — [ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml), [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html).
- Recommended regexes: `'[\w.-]+\.my_center\.edu'` (FQDN hosts like `n0001.ten.osc.edu`) or `'(ab|pn|xy)\d+'` (short names); enable by editing `/etc/ood/config/ood_portal.yml`, run `sudo /opt/ood/ood-portal-generator/sbin/update_ood_portal`, restart Apache; "the system administrator must have it enabled" — [Enable reverse proxy](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/setup/enable-reverse-proxy.html), [Connection view](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/view.html).
- Apache blocks (verbatim structure): `<LocationMatch "^<%= @node_uri %>/(?<host><%= @host_regex %>)/(?<port>\d+)">` … auth lines … `RequestHeader edit* Cookie "<%= cookie %>=[^;]+;" ""` for each `strip_proxy_cookies`, `RequestHeader unset <%= header %>` for each `strip_proxy_headers`, `Header edit Location "^[^/]+//[^/]+" ""`, Set-Cookie `Domain` stripped and `Path=<%= @node_uri %>/%{MATCH_HOST}e/%{MATCH_PORT}e` forced, `LuaHookFixups node_proxy.lua node_proxy_handler`. The rnode block differs by the `(?<uri>/.*|)` capture and `Header edit Location "^([^/]+//[^/]+)|(?=/)|^([\./]{1,}(?<!/))" "<%= @rnode_uri %>/%{MATCH_HOST}e/%{MATCH_PORT}e"` — [ood-portal.conf.erb](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/templates/ood-portal.conf.erb).
- Lua handler: maps the user, then `conn.server = host .. ":" .. port; conn.uri = uri or r.uri or '/'`, `r:custom_response(503, "Failed to connect to " .. conn.server)`; no job or ownership lookup — [node_proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/node_proxy.lua). `set_reverse_proxy` sets `r.headers_in['X-Forwarded-Proto']`, `r.headers_in['X-Forwarded-User'] = conn.user or ""`, `r.headers_in['X-Forwarded-Escaped-Uri']`, and switches to `ws://`/`wss://` when `r.headers_in['Upgrade']` is present — [ood/proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/ood/proxy.lua).
- Docs on the two modes: `/node` is "preferred if the web server can be configured with a sub-URI" (Jupyter `base_url`); `/rnode/(_host_)/(_port_)(_path_)` proxies using "ONLY the path portion of the URL request path" and suits servers that "rely **ONLY** on relative links"; connection variables available to `view.html.erb`: `host`, `port`, `password`; example `<a href="/node/<%= host %>/<%= port %>/">` and a `<form action="/node/<%= host %>/<%= port %>/login" method="post">` carrying the password — [Connection view](https://osc.github.io/ood-documentation/latest/how-tos/app-development/interactive/view.html).
- Maintainer guidance for any third-party web app behind OOD (2025-02-20): "boot the app on a port we allocate and set the `port` environment variable", "fix the root URL for the app to not be just `/` but instead be `/node/$host/$port`", "handle any authentication you need by providing the password/credentials in a `<form>`, header or query parameters" — [Discourse 4060](https://discourse.openondemand.org/t/avoid-launching-a-web-browser/4060).
- 4.1 regression report: ttyd stopped working through the proxy in 4.1.1 because "4.1 started to strip these headers when making requests downstream to origin servers" (the `Authorization` header from URL-embedded credentials); fix options were relaxing `strip_proxy_headers` or moving the token into the URL path — [Discourse 4757](https://discourse.openondemand.org/t/the-ttyd-not-working-in-ood-4-1-1/4757).
- Interactive-app `connection.yml` is how OOD itself learns `host`/`port` for a running job — [batch_connect/session.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/models/batch_connect/session.rb).

### Inferences
- A FastAPI/uvicorn worker in a Slurm job listening on `0.0.0.0:<port>` on `<node>` is reachable at `https://<ood>/rnode/<node>/<port>/...` with no path rewriting, or at `/node/<node>/<port>/...` if it mounts itself under that prefix (`--root-path /node/<node>/<port>`). Reachability additionally requires that the OOD web node can open TCP to compute nodes on that port (site firewall), which the docs do not discuss.
- Because anyone authenticated to the same OOD can hit the same URL, the worker must authenticate every request itself (bearer token in a custom header or body; not `Authorization`, which 4.1+ strips by default; not the OIDC cookie, which is stripped). `X-Forwarded-User` is overwritten by Apache's Lua for every proxied request, so the backend can trust it *only* if it also ensures traffic arrives from the OOD host (network-level), otherwise a same-cluster process could set it directly.
- Set-Cookie from the backend is rewritten to `Path=/rnode/<host>/<port>`, so backend session cookies are scoped correctly without effort; `Location` headers are rewritten for redirects, but only absolute-host and root-relative forms (see the regex), so avoid protocol-relative redirects.
- With `host_regex` at its default `[^/]+`, a site is effectively an open proxy to any host reachable from the web node; expect security-conscious sites to have narrowed it, and some to have left `node_uri`/`rnode_uri` unset entirely.

### Gaps
- No OOD document states a port range restriction or per-user authorization for `/node`; absence was confirmed in the code, not in a security advisory.
- Wayne State's `node_uri`/`rnode_uri`/`host_regex` values are not public and were not probed (the portal is VPN-only).

## Q6. The Passenger-app deployment model: what an admin can install versus what a user can do unaided

### Takeaway
Every app runs as the user inside their PUN under Passenger (Ruby, Node, Python supported), from one of three roots: `sys` (admin-installed, root-owned), `usr` (shared apps, admin must create a symlink per sharing user and turn on `OOD_APP_SHARING=1`), `dev` (sandbox apps, admin must create `/var/www/ood/apps/dev/<user>/gateway -> ~/ondemand/dev`). A user with no admin help can install nothing; they can only use what is deployed and run services inside their own jobs.

### Cited Findings
- App roots and URIs: `app_root: dev: '/var/www/ood/apps/dev/%{owner}/gateway/%{name}'`, `usr: '/var/www/ood/apps/usr/%{owner}/gateway/%{name}'`, `sys: '/var/www/ood/apps/sys/%{name}'`; `app_request_uri: dev: '/dev/%{name}'`, `usr: '/usr/%{owner}/%{name}'`, `sys: '/sys/%{name}'`; Passenger env `dev: 'development'`, `usr`/`sys: 'production'` — [nginx_stage_example.yml](https://github.com/OSC/ondemand/blob/master/nginx_stage/share/nginx_stage_example.yml). Per-app NGINX location: `passenger_base_uri <%= app_request_uri %>; passenger_app_root <%= app_root %>; passenger_enabled on;` — [app.conf.erb](https://github.com/OSC/ondemand/blob/master/nginx_stage/templates/app.conf.erb). Runtimes: `passenger_ruby`, `passenger_nodejs`, `passenger_python` — [pun.conf.erb](https://github.com/OSC/ondemand/blob/master/nginx_stage/templates/pun.conf.erb).
- Development mode: `sudo mkdir -p /var/www/ood/apps/dev/<username>; cd /var/www/ood/apps/dev/<username>; sudo ln -s /home/<username>/ondemand/dev gateway`; then the user sees a "Develop" drop-down; users cannot enable this themselves — [Enabling App Development (4.2.0)](https://osc.github.io/ood-documentation/latest/how-tos/app-development/enabling-development-mode.html).
- App sharing: `sudo mkdir -p /var/www/ood/apps/usr/efranz; cd /var/www/ood/apps/usr/efranz; chmod 750 .; ln -s ~efranz/ondemand/share gateway`; dashboard env `OOD_APP_SHARING=1`; "Executable sharing means the app and all its code runs as the user executing it… you should fully trust whoever you enable to do share apps using executable sharing" — [App Sharing (4.2.0)](https://osc.github.io/ood-documentation/latest/how-tos/app-development/app-sharing.html).
- Dashboard gating: `dev_apps` only `if ::Configuration.app_development_enabled?`; `usr_apps` only `if ::Configuration.app_sharing_enabled?` — [application_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/application_controller.rb). Admin routes for dev/usr products (`admin/:type/products`, `create_from_git_remote`) are behind `Authz::AppDeveloperConstraint` — [dashboard routes.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/config/routes.rb).
- Since 4.0 "All files in `/etc/ood/config` must be owned by root" — [v4.0 notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.0-release-notes.html).

### Inferences
- An "OOD app" for the worker (a Passenger app that brokers requests, or an Interactive App whose `form.yml` launches the worker job) is the right long-term shape for sites that partner with the project, but it is an admin deliverable. For the no-admin case, the only user-controlled server is one inside a Slurm job, reached via `/rnode` (if enabled) or driven through the Shell.

### Gaps
- Whether any site exposes a self-service dev-mode toggle was not found; the docs mention "developer by default" as a configuration choice with security implications but no user-facing switch.

## Q8. Authentication front doors, session lifetime, idle timeouts, PUN lifecycle, and rate or session limits

### Takeaway
Apache does all authentication (`auth:` directives in `ood_portal.yml`); the documented options are OpenID Connect via `mod_auth_openidc` with Dex (LDAP/AD) or Keycloak (Duo available as a Keycloak step), Shibboleth, and CAS. The default OIDC session is 8 hours both for inactivity and maximum duration (OOD overrides mod_auth_openidc's 5-minute inactivity default), the cookie is HttpOnly and SameSite=Lax by default. The per-user NGINX starts on first request via `/nginx/init?redir=…`, Passenger kills idle app processes after 300 s, and `nginx_clean` kills PUNs with no active connections. No request-rate limits exist in OOD itself.

### Cited Findings
- "Open OnDemand will not work at all without authentication of some kind"; `auth` is "a list of Apache directives defining how authentication is handled"; default example `AuthType openid-connect` / `Require valid-user` — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html), [ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml). "No Open OnDemand functionality is available without an Apache module and user mapping configured"; Dex is "a very good starting option if you can connect to LDAP or Active Directory"; mapping via Remote User, regex (`user_map_match`), Dex auto config, `user_map_cmd`, file mapping — [Authentication (4.2.0)](https://osc.github.io/ood-documentation/latest/authentication.html).
- Documented providers: [OpenID Connect](https://osc.github.io/ood-documentation/latest/authentication/oidc.html), [Dex](https://osc.github.io/ood-documentation/latest/authentication/dex.html), [Shibboleth](https://osc.github.io/ood-documentation/latest/authentication/shibboleth.html), [Two Factor Auth using Duo with Keycloak](https://osc.github.io/ood-documentation/develop/authentication/duo-2fa-with-keycloak.html); CAS appears in the authentication section listing (search result; page not fetched).
- OIDC session: `oidc_session_inactivity_timeout` default 28800; `oidc_session_max_duration` default 28800; `oidc_state_max_number_of_cookies` "10 true" — [ood_portal_example.yml](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/share/ood_portal_example.yml); rendered as `OIDCSessionInactivityTimeout`, `OIDCSessionMaxDuration`, `OIDCCookieSameSite` — [ood-portal.conf.erb](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/templates/ood-portal.conf.erb). Module defaults for comparison: inactivity "the default is 300 seconds", max duration "the default is 8 hours" — [auth_openidc.conf](https://github.com/OpenIDC/mod_auth_openidc/blob/master/auth_openidc.conf).
- Maintainers on timeouts (2023): web-session timeout is controlled only through auth ("using something like `oidc_session_inactivity_timeout` in `ood_portal.yml`"); `passenger_pool_idle_time` "will kill any idle applications connected to the PUN" but does not end the web session; a site confirmed a 15-minute OIDC inactivity timeout works — [Discourse 2769](https://discourse.openondemand.org/t/inactivity-timeout-for-both-web-page-and-ssh-shell-access-in-openondemand/2769).
- Logout: `/logout` redirects to `logout_redirect`, default `/pun/sys/dashboard/logout`; OIDC example `/oidc?logout=https%3A%2F%2Fondemand.my-center.edu`; Shibboleth `/Shibboleth.sso/Logout?return=…` — [Configure Logout](https://osc.github.io/ood-documentation/latest/authentication/overview/configure-logout.html).
- PUN start: if `<pun_socket_root>/<user>/passenger.sock` is missing, Apache runs `nginx_stage` up to `pun_max_retries` (5) times with an init URL of the form `<scheme>://<host>:<port><nginx_uri>/init?redir=$http_x_forwarded_escaped_uri`, sleeping 1 s between attempts — [pun_proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/pun_proxy.lua); `/nginx/init` "requires a `redir` query parameter" that must start with `pun_uri`, then 302s to it; `/nginx/stop` stops the PUN and returns 200 (or 302 to `redir`) — [nginx.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/nginx.lua). `pun_stage_cmd` default `sudo /opt/ood/nginx_stage/sbin/nginx_stage`; `pun_socket_root` `/var/run/ondemand-nginx` — [ood_portal.yml reference](https://osc.github.io/ood-documentation/latest/reference/files/ood-portal-yml.html).
- PUN cleanup: `nginx_clean` "will kill all per-user NGINX (PUN) processes that do not have active connections"; `-f` forces; since 4.0 it also removes PUNs of disabled users — [nginx_clean (4.2.0)](https://osc.github.io/ood-documentation/latest/reference/commands/nginx-stage/commands/nginx-clean.html). Older docs show the cron `0 */2 * * * root … nginx_stage nginx_clean` in `/etc/cron.d/ood` — [nginx_clean (1.4 docs)](https://osc.github.io/ood-documentation/release-1.4/infrastructure/nginx-stage/commands/nginx-clean.html) (schedule from a search snippet of that page; the 4.2 page no longer prints it).
- Group-change guard: the dashboard restarts the PUN when the user's groups changed (`redirect_to helpers.restart_url(request.fullpath)`), checked at most every 5 minutes — [application_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/application_controller.rb).
- Concurrency ceilings visible in config: `worker_connections 1024` per PUN; `passenger_max_instances_per_app 1`; `client_max_body_size` = upload max — [pun.conf.erb](https://github.com/OSC/ondemand/blob/master/nginx_stage/templates/pun.conf.erb).
- Wayne State's front door: VPN (GlobalProtect) required, then "Enter your AccessID and password. Click Sign In." with no Duo step described — [WSU KB 20239](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20239).

### Inferences
- With defaults, an extension session survives up to 8 hours of activity and 8 hours of inactivity before the OIDC cookie expires; sites that follow the 2769 thread may run 15–60 minute inactivity windows. The extension should treat any 302 to an IdP or a 401 as "re-authenticate in a tab" and must not attempt the login itself.
- A cold PUN adds seconds to the first request (nginx_stage spawn plus a 302 round trip); programmatic clients should follow redirects on GET and pre-warm by fetching `/pun/sys/dashboard/` before issuing POSTs (a POST that lands on a cold PUN is answered with a redirect to `/nginx/init`, losing the body).
- OOD imposes no rate limits, but everything runs under the user's PUN on a shared web node; polling loops should stay at seconds, not milliseconds, out of etiquette rather than enforcement.

### Gaps
- Shibboleth and CAS session lifetimes are set in those modules/IdPs, not in `ood_portal.yml`; no OOD default exists to quote.
- Whether Wayne State layers Duo at the AccessID login page (outside OOD) is not stated in the KB article.

## Q9. What must a site admin have configured for each channel (so the extension can detect and explain a missing piece)?

### Takeaway
Each channel has a distinct, observable failure signature: Shell problems come back as WebSocket close code 3146 with one of four reason strings; Files/Jobs features that are switched off simply have no routes (404); an unconfigured reverse proxy yields an Apache 404 for `/rnode/...`, whereas a configured one with no listener yields a 503 "Failed to connect to host:port".

### Cited Findings
- Shell: requires a non-empty allowlist (clusters with `v2.login.host` or `OOD_SSHHOST_ALLOWLIST`), an ssh from the web node to the target that needs no password, and a passing origin/CSRF check; the four reasons are "No clusters defined.", "Invalid Origin.", "Bad CSRF Token.", `Host "<host>" not specified in allowlist or cluster configs.` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js), [helpers.js](https://github.com/OSC/ondemand/blob/master/apps/shell/utils/helpers.js). Docs: "The shell app does not work out of the box because all SSH hosts have to be explicitly allowed through the allowlist" — [Shell App docs (1.8)](https://osc.github.io/ood-documentation/release-1.8/applications/shell.html); password prompts indicate missing host-based/key auth — [Discourse 1564](https://discourse.openondemand.org/t/shell-app-needs-password-when-ssh-the-login-node/1564) (title only).
- Files: routes exist only `if Configuration.can_access_files?`; upload route only `if Configuration.upload_enabled?`; editor routes only `if Configuration.can_access_file_editor?`; `files_upload_path` is present in the JSON only when uploads are enabled — [routes.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/config/routes.rb), [index.json.jbuilder](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/views/files/index.json.jbuilder).
- Jobs: Projects routes only `if Configuration.can_access_projects?`; Active Jobs only `if Configuration.can_access_activejobs?`; Job Composer is a separate sys app that a site may hide or remove — [routes.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/config/routes.rb), [v4.1 notes](https://osc.github.io/ood-documentation/latest/release-notes/v4.1-release-notes.html). Job Composer index shows "There are no configured hosts that allow you to submit jobs" when `OODClusters.none?` — [workflows_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/myjobs/app/controllers/workflows_controller.rb).
- Reverse proxy: the `<LocationMatch>` blocks are emitted only `<%- if @node_uri -%>` / `<%- if @rnode_uri -%>`; when present but the backend is down the Lua handler installs `r:custom_response(503, "Failed to connect to " .. conn.server)` — [ood-portal.conf.erb](https://github.com/OSC/ondemand/blob/master/ood-portal-generator/templates/ood-portal.conf.erb), [node_proxy.lua](https://github.com/OSC/ondemand/blob/master/mod_ood_proxy/lib/node_proxy.lua).
- Clusters: defined server-side in `/etc/ood/config/clusters.d/*.yml` (`OOD_CLUSTERS` override), read by the shell app and by `OODClusters` — [helpers.js](https://github.com/OSC/ondemand/blob/master/apps/shell/utils/helpers.js), [active_jobs_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/active_jobs_controller.rb).

### Inferences (a detection sequence the extension can run, all GETs)
1. `GET /pun/sys/dashboard/` → 200 HTML means authenticated and PUN up; a 302 to an IdP, a VPN captive page, or a connection error means "log in / connect VPN in a tab".
2. `GET /pun/sys/shell/ssh/default` → 200 with `csrf=` in the inline script means the Shell app is installed; then a probe WebSocket's close reason distinguishes "No clusters defined." (admin never configured a cluster/allowlist) from "Host … not specified" (wrong host) from "Invalid Origin." (site behind an extra proxy; ask the admin to set `OOD_SHELL_ORIGIN_CHECK`).
3. `GET /pun/sys/dashboard/files/fs/<home>` with `Accept: application/json` → 200 JSON means Files works; presence of `files_upload_path` means uploads allowed; 404 means Files disabled.
4. `GET /pun/sys/dashboard/activejobs.json?jobcluster=all&jobfilter=user` → cluster ids appear in `cluster` fields; `errors` names missing clusters.
5. `GET /pun/sys/myjobs/workflows.json` → 200 means Job Composer available; 404 means hidden/removed. `GET /pun/sys/dashboard/projects` → 200/404 for Projects.
6. `GET /rnode/<login-or-compute-host>/1/` → Apache 404 means `rnode_uri` unset or `host_regex` mismatch; 503 "Failed to connect to <host>:1" means the proxy is enabled and the host matched.

### Gaps
- There is no JSON listing of clusters or of `ood_portal.yml` values exposed to users; the extension can only infer them from the probes above.

## Q10. Failure modes and etiquette: is the Shell a login-node shell, and what do sites say about automation?

### Takeaway
Yes: the Shell app is an ssh to an admin-chosen host, "typically a login node", running under the user's PUN on the shared OOD web node. Login-node etiquette therefore applies (edit, compile, submit; do not compute), and the shell's own 5-minute/1-hour defaults make it unsuitable as a persistent transport. The maintainers discourage automating OOD's web endpoints; no university policy specifically addressing scripted use of OOD was found, but every site's login-node policy already bounds what a worker may do there.

### Cited Findings
- Shell = ssh from the web node: `pty.spawn(cmd, args, …)` with `cmd = OOD_SSH_WRAPPER || 'ssh'` — [app.js](https://github.com/OSC/ondemand/blob/master/apps/shell/app.js); "forks off an ssh process that connects to a server specified by the administrator (typically a login node)" — [Shell App docs (1.8)](https://osc.github.io/ood-documentation/release-1.8/applications/shell.html).
- Login-node policies: University at Buffalo CCR: login nodes should not be used for resource-intensive tasks such as running software or compiling code; submit batch or interactive jobs instead — [CCR: Login Node](https://docs.ccr.buffalo.edu/en/latest/hpc/login/) (search summary of the page). NC State: no resource-intensive processes on shared login nodes; use an interactive session on a compute node — [NC State HPC: Login](https://hpc.ncsu.edu/Documents/Login.php) (search summary). LBL Science IT: `.ood0` shared nodes "should be treated like login nodes (that is, intensive computation is not allowed)" — [LBL OOD overview](https://scienceit-docs.lbl.gov/hpc/openondemand/overview/) (search summary). OSC: shared VDI "should not be used for computationally or memory intensive processes"; intensive jobs "will be terminated"; max VDI walltime 24 h — [OSC OnDemand](https://www.osc.edu/resources/online_portals/ondemand).
- Maintainers on automation: internal endpoints "subject to change", "cannot make guarantees on their stability" — [Discourse 4202](https://discourse.openondemand.org/t/integrating-custom-job-submissions-via-ood-api/4202); "not on our roadmap to open any API" — [Discourse 2801](https://discourse.openondemand.org/t/exposing-job-composer-as-a-rest-api/2801).
- Shell defaults: 300000 ms inactivity, 3600000 ms max — [Customizations](https://osc.github.io/ood-documentation/latest/customizations.html). Passenger idle 300 s and one instance per app — [pun.conf.erb](https://github.com/OSC/ondemand/blob/master/nginx_stage/templates/pun.conf.erb), [nginx_stage_example.yml](https://github.com/OSC/ondemand/blob/master/nginx_stage/share/nginx_stage_example.yml). `nginx_clean` kills PUNs without active connections — [nginx_clean docs](https://osc.github.io/ood-documentation/latest/reference/commands/nginx-stage/commands/nginx-clean.html).
- 4.1 header stripping broke a websocket app that relied on `Authorization` — [Discourse 4757](https://discourse.openondemand.org/t/the-ttyd-not-working-in-ood-4-1-1/4757).
- Rails write endpoints raise on CSRF failure (`protect_from_forgery with: :exception`) — [application_controller.rb](https://github.com/OSC/ondemand/blob/master/apps/dashboard/app/controllers/application_controller.rb).
- Wayne State: the KB describes Clusters → "Open a shell of the Grid" with no host named and no usage warning — [WSU KB 20239](https://services.wayne.edu/TDClient/277/Portal/KB/ArticleDet?ID=20239). Wayne State's own etiquette from the project's grid notes (C&IT, 2026-09-28): no container builds or execs on the login node `warrior`, nothing of ours under its `/tmp`; container work only inside Slurm jobs — project `CLAUDE.md` (internal, not a public source).

### Inferences
- The Shell should be used only as a bootstrap channel: open, run one `sbatch` (or `tmux new -d …`) that starts the worker job, read back the job id, close. Anything that keeps a login-node process alive for the extension's benefit (a long `tail -f`, a polling loop) violates both the site etiquette and the shell's own timers.
- Concrete failure signatures to handle: WS close 3146 + reason (admission); WS terminate with no reason after 5 min idle or 60 min total (timers); HTTP 422 on a POST from the wrong Origin or with a stale token (Rails CSRF); 302 to `/nginx/init` or to the IdP (cold PUN / expired session); 503 "Failed to connect to host:port" (worker not listening yet); 404 on `/rnode` (proxy not enabled); 413 on uploads above `client_max_body_size`.
- Because the shell process is one-per-user, a driver bug that sends a non-JSON frame can take down the user's own interactive shells; validate frames client-side.

### Gaps
- No university's acceptable-use page specifically mentioning browser automation of OnDemand was found; policies are written in terms of login-node load.
- Wayne State's `OOD_SHELL_*` timer values and shell target host are unknown (VPN-only portal, not probed).

### Inferences
- "Jobs → compose and submit jobs" on the WSU KB page indicates the Job Composer (`/pun/sys/myjobs`) was present when the article was written; whether WSU has since upgraded to 4.1+ (Project Manager default, Job Composer deprecated) is not public. The presence of five Interactive Apps implies batch connect is configured and, unless they are all VNC apps, that `node_uri`/`rnode_uri` is set (Jupyter and RStudio Server need the proxy) — a strong but unverified indication that `/rnode/` works at Wayne State.
- Given the numbers above and the VPN/IdP variety, "university-agnostic" realistically means: one code path for the Shell WebSocket + Files API (present everywhere), an optional fast path over `/rnode/` where the probe in Q9 succeeds, and per-site knowledge limited to hostname, login host name and whether a VPN is needed.

### Gaps
- No published count of US universities running OOD; the PEARC paper reports global provider counts only, and the project's map is not exposed as a downloadable list.
- Wayne State's OOD version, cluster names in `clusters.d`, shell target host, and proxy settings are not public; confirming them requires an authenticated probe from inside the VPN.
