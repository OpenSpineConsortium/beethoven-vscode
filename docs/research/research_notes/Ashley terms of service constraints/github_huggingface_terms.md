*Retrieved 2026-09-28 from the primary pages named in each citation. Quotations are verbatim as returned by the page fetch; where a page was only partially returned, or a fact rests on a search snippet rather than the page itself, that is marked. Scenario labels used below:
- **(a)** Ashley obtains a GitHub OAuth token through VS Code's built-in `github` authentication provider (scopes `repo`, `workflow`, `read:org`, `gist`), stores it in the OS keychain, copies it to the user's HPC home directory as `GITHUB_TOKEN`/`GH_TOKEN` for the user's own `git`/`gh` and for Claude Code running as the user.
- **(b)** Ashley takes a Hugging Face user access token pasted by the user, stores it the same way, and uses it for dataset downloads and `whoami`.
- **(c)** The vendor's pipeline: Claude Code under the vendor's account, in GitHub Actions, reads diagnostic reports, proposes patches, opens PRs on the vendor's private repository; a human or CI merges.

## Key question 1 — GitHub Terms of Service and Acceptable Use Policies: account security, credential sharing, tokens, automation, API/rate limits; may a user's token be moved by a tool to another machine the user controls?

### Takeaway
The ToS (effective April 27, 2026) binds the *account holder*: one human per login, responsibility for "all content posted and activity that occurs under your Account", and an API clause that reaches "use of the API through a third party product". The only token-sharing prohibition in the ToS text is sharing "API tokens to exceed GitHub's rate limitations". No retrieved GitHub policy text addresses a user's own token being placed on a second machine the same user controls; the constraints that do apply are the one-person-per-login rule, the account-security responsibility, and rate-limit/abuse clauses.

### Inferences
- The retrieved ToS text prohibits (i) more than one *person* using a login and (ii) sharing tokens *to exceed rate limits*. Neither sentence, on its face, addresses one person's own token copied to a second machine (the HPC home directory) and used only under that person's identity. No GitHub policy page retrieved addresses that configuration at all; it is silent, not permissive or prohibitive.
- The ToS assigns responsibility to the user for "all ... activity that occurs under your Account" — so anything Claude Code or `gh` does with the copied token on the HPC is, in ToS terms, the user's activity. Ashley's design (token stays under the user's identity, on storage the user controls) keeps that attribution intact; the user bears the security obligation for the HPC copy.
- §H's "including use of the API through a third party product that accesses GitHub" means the user is bound by the API terms when Ashley (or Claude Code) calls the API with their token; rate-limit and "abuse" determinations are made against the *user's* account, at GitHub's discretion.
- The OAuth-app "encrypt tokens on your back end" guidance is addressed to the OAuth app developer (for the VS Code token, Microsoft), not to a consuming extension; there is no retrieved GitHub text that tells a *consumer* of a token how it must be stored. GitHub's own recommendation to end users ("use GitHub CLI or Git Credential Manager") describes credential storage on the user's machine, which is the pattern Ashley reproduces on the HPC.
- A `repo`-scoped token has the user's full read/write access to every repository they can reach; the scope list is fixed by the token, not narrowable per machine. If the HPC copy is compromised, the exposure is the user's whole repository set, which is the risk the PAT page's "Treat your access tokens like passwords" is aimed at.
- Push protection for a leaked GitHub or HF token inside a *private* vendor repository is not free; it requires GitHub Secret Protection on a Team/Enterprise plan. The pipeline in (c) cannot rely on GitHub to catch a token that slips into a diagnostic report unless that add-on is licensed.

### Gaps
- The AUP page could not be retrieved in full: the fetch returned selected sentences for §§2, 4, 5, 7 and the enforcement paragraph. The complete bullet lists (and any dated "last updated" line) should be read from the page directly.
- I did not find a GitHub statement on whether a single user's 5,000/h primary limit is shared across all OAuth apps authorized by that user (the fetch of the rate-limit page did not confirm the sentence).
- No GitHub policy text was found that speaks to a user's token being relocated to another machine the user controls; the question is unaddressed rather than answered.

## Key question 2 — What is the token issued by VS Code's GitHub authentication provider, may a third-party extension request and use it, and do GitHub's Developer Terms / Marketplace Developer Agreement speak to an extension reusing VS Code's app token?

### Takeaway
The token is a GitHub OAuth user access token issued to VS Code's own OAuth client (client id `01ab8ac9400c4e429b23`, hard-coded in the built-in `github-authentication` extension). VS Code's API exists precisely so extensions can obtain such sessions, gated by a per-extension allow-list and a "The extension '{0}' wants to sign in using {1}." consent prompt. No GitHub document retrieved — ToS, Developer/Marketplace agreements, OAuth-app docs — mentions extensions reusing a host application's OAuth token; the GitHub Marketplace Developer Agreement applies only to products listed on *GitHub* Marketplace.

### Cited Findings

**VS Code authentication API**

- "Namespace for authentication." and "Currently, there are only two authentication providers that are contributed from built in extensions to the editor that implement GitHub and Microsoft authentication: their providerId's are 'github' and 'microsoft'." `getSession` "Get[s] an authentication session matching the desired scopes or satisfying the WWW-Authenticate request." `AuthenticationSession.accessToken` is documented as "The access token." Options include `createIfNone`, `forceNewSession`, `silent`, `clearSessionPreference`, `account`. The docs also state that "getting accounts does not imply that your extension has access to that account or its authentication sessions." — [VS Code API, `authentication` namespace](https://code.visualstudio.com/api/references/vscode-api#authentication)
- The built-in GitHub authentication extension's configuration file contains `gitHubClientId: '01ab8ac9400c4e429b23'` with no client secret defined; a comment notes that client secrets cannot be secured in native clients, so the secret is "not really a secret" and is injected before publication. — [microsoft/vscode `extensions/github-authentication/src/config.ts`](https://github.com/microsoft/vscode/blob/main/extensions/github-authentication/src/config.ts)
- VS Code's consent strings, in `mainThreadAuthentication.ts`: "The extension '{0}' wants to sign in using {1}." and "The extension '{0}' wants you to sign in again using {1}." with an "&&Allow" button; a session is returned only after `this.authenticationAccessService.isAccessAllowed(providerId, session.account.label, extensionId)` passes, and access is recorded with `updateAllowedExtensions(providerId, session.account.label, [{ id: extensionId, name: extensionName, allowed: true }])`. — [microsoft/vscode `src/vs/workbench/api/browser/mainThreadAuthentication.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/api/browser/mainThreadAuthentication.ts)
- (Search-snippet level, from code.visualstudio.com pages, not fetched in full:) as of VS Code 1.97, installing an extension from a third-party publisher shows a publisher-trust dialog, managed with "Extensions: Manage Trusted Extensions Publishers"; per-account extension access is managed from the Accounts menu via "Manage Trusted Extensions". — [Extension runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security); [VS Code API](https://code.visualstudio.com/api/references/vscode-api)

- "GitHub Apps are preferred to OAuth apps"; OAuth app tokens "can be configured to expire after eight hours and can be renewed with a refresh token"; GitHub Apps "act independently of a user" and keep working "even if the person who installed the app on an organization leaves the organization"; GitHub App bot accounts "do not consume a GitHub Enterprise seat". — [Differences between GitHub Apps and OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)

### Inferences
- The token Ashley receives is a user access token for Microsoft's OAuth client, not for an Ashley-owned app. In GitHub's model the "developer" of that OAuth app is Microsoft; GitHub's OAuth-app best-practice guidance (minimal scopes, encrypt at rest, revoke on compromise) is written to that developer. Ashley is a downstream consumer that GitHub's documents do not name.
- VS Code's `authentication.getSession` API is the sanctioned route for an extension to obtain that token; the editor enforces the consent gate (per-extension allow-list plus the "wants to sign in using GitHub" prompt). What the API does *not* do is govern what the extension does with `accessToken` afterwards — the docs describe it only as "The access token." Copying it to a remote host is neither described nor forbidden in the API documentation retrieved.
- Because the token belongs to VS Code's OAuth client, the user's revocation path is GitHub Settings > Applications > Authorized OAuth Apps for the VS Code app, which revokes it for VS Code *and every extension* using that client, including Ashley's HPC copy. Ashley cannot revoke its own copy independently of VS Code's session.
- The GitHub Marketplace Developer Agreement governs products listed on GitHub Marketplace. A VS Code extension distributed through the Visual Studio Marketplace is outside its definition of "Developer Application" unless also listed on GitHub Marketplace; the agreement therefore does not, by its terms, address Ashley. Its §3.2 token clause concerns the *developer's* own subscriber token, not end-user tokens.
- The GitHub App documentation's repeated preference for GitHub Apps with short-lived, fine-grained tokens is the closest thing to GitHub's stated view of what a well-behaved integration looks like. A long-lived `repo`-scoped OAuth token copied to an HPC is the pattern that guidance steers away from, though nothing retrieved prohibits it.

### Gaps
- I could not verify from a primary source the display name of the OAuth app that client id `01ab8ac9400c4e429b23` resolves to in a user's "Authorized OAuth Apps" list (commonly shown as "Visual Studio Code"); the community thread found did not name it. The name should be read from GitHub Settings > Applications directly.
- No GitHub document (ToS, Developer/Marketplace agreements, OAuth docs) was found that addresses an extension reusing a host application's OAuth token. The absence is the finding.
- The Microsoft Visual Studio Marketplace Publisher Agreement, which does govern VS Code extension publishers, was not retrieved and is outside the assigned scope; it may contain data-handling or credential terms that apply to Ashley and should be read separately.
- VS Code's documentation page(s) describing "Manage Trusted Extensions" were located only by search snippet, not fetched; quote them directly before relying on the wording.

## Key question 3 — GitHub's rules for AI-generated contributions and automated pull requests: Copilot coding agent terms, Actions limits and terms, bots opening PRs, attribution (machine users, GitHub Apps), 2025–2026 agent policy

### Takeaway
GitHub has no general "AI-contribution policy" in its site-policy set; the governing texts are the Actions terms (use must relate to the software project; no disproportionate burden), the Actions limits page, repository settings that by default forbid workflows from creating or approving PRs, and the GITHUB_TOKEN recursion rule. GitHub's own coding agent and the third-party (Anthropic, OpenAI) agents act through *GitHub App identities* with author/co-author attribution, an approval gate before workflows run, and no ability to approve or merge — which is GitHub's stated model of what an agent-opened PR should look like.

### Cited Findings

**GitHub Terms for Additional Products and Features — "Last Updated: August 27, 2026"**

- Actions: "Actions and any elements of the Actions product or service may not be used in violation of the Agreement, the GitHub Acceptable Use Policies, or the GitHub Actions service limitations set forth in the Actions documentation." Prohibited uses include "Cryptomining"; "Disrupting, gaining, or attempting to gain unauthorized access to, any service, device, data, account, or network"; "The provision of a stand-alone or integrated application or service offering the Actions product or service...for commercial purposes"; "Any activity that places a burden on our servers, where that burden is disproportionate to the benefits provided to users (for example, don't use Actions as a content delivery network or as part of a serverless application)"; "If using GitHub-hosted runners, any other activity unrelated to the production, testing, deployment, or publication of the software project associated with the repository". — [GitHub Terms for Additional Products and Features, Actions](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features)
- Copilot: "For GitHub Copilot Business and Copilot Enterprise license holders who purchase directly from GitHub, your use of GitHub Copilot is governed by the GitHub Generative AI Services Terms." — [same page, Copilot](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features)
- Previews: "Previews are provided 'AS-IS', 'WITH ALL FAULTS' and 'AS AVAILABLE'. GitHub may change or discontinue Previews at any time without notice." — [same page, Previews](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features)

**GitHub Actions limits (documentation)**

- "Each job in a workflow can run for up to 6 hours of execution time. If a job reaches this limit, the job is terminated and fails."; a workflow run is cancelled at 35 days; "A job matrix can generate a maximum of 256 jobs per workflow run."; "The rate limit for `GITHUB_TOKEN` is 1,000 requests per hour per repository"; queue limit 500 workflow runs per 10 seconds ("When the limit is reached, the workflow runs that were supposed to be triggered by the webhook events will be blocked and will not be queued"); concurrent jobs Free 20 / Pro 40 / Team 60 / Enterprise 500; "Unless otherwise stated, the expected behavior when a limit is reached is that the workflow/job will get cancelled." — [GitHub Actions limits](https://docs.github.com/en/actions/reference/limits)

**Automated PR creation — repository controls and GITHUB_TOKEN behaviour**

- "By default, workflows are not allowed to create or approve pull requests." The control is the setting "Allow GitHub Actions to create and approve pull requests" under "Workflow permissions". GITHUB_TOKEN restricted mode gives "read access for the `contents` and `packages` permissions"; permissive mode gives "read and write access for all permissions". — [Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)
- "When you use the repository's `GITHUB_TOKEN` to perform tasks, events triggered by the `GITHUB_TOKEN` will not create a new workflow run, with the following exceptions: `workflow_dispatch` and `repository_dispatch` events always create workflow runs." This "prevents you from accidentally creating recursive workflow runs. For example, if a workflow run pushes code using the repository's `GITHUB_TOKEN`, a new workflow will not run even when the repository contains a workflow configured to run when `push` events occur." Also: "`pull_request` events with the `opened`, `synchronize`, or `reopened` activity types: when a workflow using `GITHUB_TOKEN` creates or updates a pull request, the resulting `pull_request` event creates workflow runs in an approval-required state". And: "If you do want to trigger a workflow from within a workflow run, you can use a GitHub App installation access token or a personal access token instead of `GITHUB_TOKEN` to trigger events that require a token." — [Trigger a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
- GitHub Changelog, June 11, 2026, "Bot-created pull requests can run workflows if approved": "Previously, pull requests generated by `github-actions[bot]` were not able to run CI/CD workflows." Approval from someone with write access is now required: "Requiring approval is a security measure to ensure generated code does not automatically run workflows which may have access to sensitive information." The post says this "matches the behavior of Copilot-generated pull requests". — [GitHub Changelog 2026-06-11](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/)

**Attribution: machine users vs GitHub Apps**

- "Since this account on GitHub.com won't be used by a human, it's called a *machine user*." **GitHub's own agent and third-party agents — the attribution/approval model GitHub ships**

- Attribution: GitHub's documented, preferred identity for automation is a GitHub App (audit-log visible, no seat, short-lived tokens); a machine user is tolerated ("that is totally cool") but second choice. - The Claude action's `allowed_bots` gate and GitHub's GITHUB_TOKEN recursion rule together address the loop risk a self-triggering maintenance pipeline would otherwise create.

## Key question 4 — GitHub private-repository terms and what may be sent into a repository (diagnostic reports with usernames, hostnames, paths; never tokens)

### Takeaway
GitHub treats private-repository contents as "confidential to you" and lists the narrow circumstances in which its personnel access them. Nothing in the ToS restricts what an owner may store in a private repository beyond the AUP (which prohibits posting "another person's personal information without consent") and the general prohibition on content violating law. Tokens in a repository are a secret-scanning matter: GitHub and Hugging Face tokens are both partner patterns, but push protection in private repositories is a paid feature.

### Cited Findings
- E.1: "Some Accounts may have private repositories, which allow the User to control access to Content." — [ToS §E.1](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)
- E.2: "GitHub considers the contents of private repositories to be confidential to you. GitHub will protect the contents of private repositories from unauthorized use, access, or disclosure in the same manner that we would use to protect our own confidential information of a similar nature and in no event with less than a reasonable degree of care." — [ToS §E.2](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)
- E.3: "You control access to the content of your private repositories. GitHub considers the contents of private repositories to be confidential to you, as set forth in Section E.2, and GitHub personnel will not access private repository content without your consent except in the following circumstances: for security purposes; for automated scanning or manual review for known vulnerabilities, active malware, or other content known to violate our Terms of Service; to assist the repository owner with a support matter; to maintain the integrity of the Service; or to comply with our legal obligations if we have reason to believe the contents are in violation of the law." "You may choose to enable additional access to your private repositories. For example: You may enable various GitHub services or features that require additional rights to Your Content in private repositories." "Additionally, we may be compelled by law to disclose the contents of your private repositories." — [ToS §E.3](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)
- D: "You own Your Content...You grant us and other Users the licenses in Sections D.4–D.8." — [ToS §D](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)
- AUP §2 prohibits content that "violates the privacy of any third party, such as by posting another person's personal information without consent". — [AUP §2](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)
- Secret scanning: GitHub PAT / OAuth / App installation / refresh tokens and "Hugging Face User Access Token" are partner patterns with push protection and validity checks; partner alerts are "Reported directly to secret providers that are part of secret scanning's partner program" and the partner "may revoke it." — [Supported secret scanning patterns](https://docs.github.com/en/code-security/secret-scanning/introduction/supported-secret-scanning-patterns)
- Private organization repositories require "GitHub Secret Protection" "enabled on GitHub Team or GitHub Enterprise Cloud" for secret scanning; public repositories get it "automatically for free". — [About secret scanning](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)

### Inferences
- A vendor-owned private repository may hold diagnostic reports containing the *vendor's own* users' usernames, hostnames and paths as far as GitHub's terms go; the AUP privacy clause is the only text that bears on it, and it is framed around posting a third party's personal information "without consent". Consent from the Ashley user to the diagnostic upload is therefore the relevant fact under GitHub's text (independently of any data-protection law, which is out of scope here).
- E.3 lists automated scanning by GitHub as a circumstance in which private content is read; anything in a diagnostic report is subject to that scanning. This is a reason to keep tokens out (they would be detected and, for partner patterns, reported), and it also means the repository is not a sealed store.
- "Never tokens" cannot be delegated to GitHub on a private repository without a Secret Protection licence; the redaction has to happen in the pipeline before commit.

### Gaps
- The GitHub Privacy Statement (which §H and §E point to) was not retrieved; it may contain statements about GitHub's processing of repository content that bear on diagnostic data.
- Whether GitHub auto-revokes its *own* tokens found in private (as opposed to public) repositories was not confirmed from the pages fetched.

## Key question 6 — Hugging Face rules on storing tokens in third-party tools and on organisation tokens

### Takeaway
HF has no rule addressed to third-party tools that store a user's token; its guidance is to the user (one token per app, fine-grained, secure vault, revoke on leak). Organisation-owned credentials exist only on Enterprise plans (Service Accounts, OAuth token exchange); on other plans every token is a *user* token, and Team/Enterprise organisations can require fine-grained tokens, require admin approval, or revoke a member's token for the organisation's resources.

- Tokens Management is "part of the Team & Enterprise plans" and lets administrators "oversee access tokens within their organization". - Revocation by an org admin (Enterprise): "A revoked token can no longer access the organization's resources, but continues to work elsewhere." "Revocation is permanent at the organization level — there is no un-revoke action." — [Tokens Management](https://huggingface.co/docs/hub/enterprise-tokens-management)
- Organisation-owned credentials: "For automated access that is owned by the organization rather than an individual member, administrators can create Service Accounts and issue fine-grained tokens scoped to your organization's resources." (Enterprise plan and above.) Programmatic issuance: OAuth Token Exchange "allows your backend services to issue scoped tokens for organization members without requiring interactive user consent." (Enterprise.) — [Tokens Management](https://huggingface.co/docs/hub/enterprise-tokens-management)

### Inferences
- HF's own client writes the token in a plain file in the user's home directory; Ashley writing `HF_TOKEN` into the user's HPC home follows the same storage model HF ships, with the same exposure (anyone who can read the home directory holds the token). The keychain copy on the laptop is stronger than HF's default.
- For a user in a Team/Enterprise organisation, a read/write token Ashley stores may be rejected by that organisation's policy even though it works for the user's personal resources; Ashley's `whoami` check does not reveal org-policy status, so a `403` against org datasets is a foreseeable failure the tool should surface rather than treat as a bad token.
- There is no organisation-owned token available to Ashley's users on free/PRO plans; the token Ashley holds is always a personal credential, and org admins on Team/Enterprise can see its name (under approval policy) and cut its org access without the user's action.

### Gaps
- No HF document was found that addresses third-party desktop tools holding user tokens (beyond the general "one token per app" and vault guidance). The absence is the finding.
- The Enterprise Service Accounts page and the OAuth Token Exchange page were referenced but not fetched; details of what a Service Account token can do were not confirmed beyond the sentence quoted.
