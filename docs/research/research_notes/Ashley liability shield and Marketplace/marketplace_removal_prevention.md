## Key Question 1 — The written rules: Publisher Agreement, Participation Policies, Terms of Use, and the manifest fields

### Takeaway
Microsoft's contractual position is unconditional: it "may remove or suspend the availability of any Offering from the Marketplace for any reason or no reason and at any time" (Publisher Agreement §3(g)), and the Participation Policies repeat "for any reason" (§5(a)). The clauses that bite for an extension like the one described are §8(d) (no executable code on the user's environment "beyond what is identified in or may reasonably be expected from the Listing Information"), §8(b)(ii) (a privacy policy is mandatory if the Offering "accesses, collects or transmits any Personal Data"), §6(b) (pre-sale consumer disclosures go "in the Offering description field"), and the Terms of Use Code of Conduct, which forbids "causing unexpected behavior that is not clearly documented at the top of both the package description and package README". The manifest rules are enforced mechanically by `vsce`: `pricing` may only be `Free` or `Trial`, README/CHANGELOG images must be HTTPS and non-SVG, badges must come from an allow-list, and a missing `repository` is a hard stop unless `--allow-missing-repository` is passed.

- For a `pricing: Trial` / BYOL extension, the documents pull in two directions that the publisher should resolve by over-disclosing: BYOL offerings are exempt from the "Terms of Use" delivery requirement (PA §4(c), PP §3(a)(6)), but the Trial label is a promotional SKU whose terms are supposed to carry any subscription restrictions (PP §4). Publishing an explicit EULA link in the listing satisfies both readings.
- The Standard Agreement short link being dead means a publisher who relies on the default terms cannot even show a customer what those terms are; supplying one's own EULA removes that dependency.
- PA §8(d) is the clause under which behaviours (c), (d), (e) and (f) in the brief would be judged. The test is not whether code is launched but whether it is "identified in or may reasonably be expected from the Listing Information" — a disclosure problem, not a prohibition.
- The Terms of Use requirement to document "unexpected behavior ... at the top of both the package description and package README" is the only placement rule that names a position on the page; it applies to publishers because §1 of the ToU makes publishers subject to the Code of Conduct and PA §6(a) incorporates "Documentation".

### Gaps
- The Microsoft Standard Agreement text (the default EULA) could not be retrieved; its aka.ms link is dead and the web-search budget was exhausted before an alternative host was found.
- The Publisher Agreement's face date is June 2021 while the hosted PDF was generated in August 2025; whether any clause changed between the two builds could not be checked (no earlier copy was diffed).
- The `extensionKind`/`virtualWorkspaces` documentation was retrieved only as summary text; exact sentences for those two fields were not captured verbatim.

## Key Question 2 — The 2025-2026 Marketplace security program: scanning, signing, verification, obfuscation policy, name-squatting, and the client-side kill switch

### Takeaway
Microsoft's stated pipeline (June 2025 blog; VS Code docs) is: Defender-class static scan on upload, re-scan shortly after publication and periodic bulk re-scans, sandbox "clean room VM" dynamic detection, secret scanning (blocking since 22 Sep 2025), impersonation blocking (tightened 22 Jul 2026), risk-based publisher-account gating (20 Jul 2026), manual security review of flagged packages, and a one-business-day "Report a Concern" channel; confirmed-malicious extensions are removed, added to the `malicious` list in the client control file (`marketplace.json`, ~700 entries), and VS Code auto-uninstalls them. Microsoft's position on obfuscation since 19 Mar 2025 is that it "absolutely contributes to suspicion" and that "clean, and non-obfuscated code ... is significantly less likely to trigger a false-positive"; no published rule distinguishes minification from obfuscation, and a May 2026 case shows a minified 3.7 MB bundle with dynamic `require()` and `process.env` access being blocked within 24 hours of first publish.

### Cited Findings

### Inferences
- The behaviours in the brief that map directly onto documented flags are: spawning processes (Material Theme's "utility for running child processes"), `curl`/download-and-run patterns in scripts (BigBlack), minified bundles with dynamic `require`/`process.env` (nuBond), platform-specific binaries that fail validation (transitrix), and any bundled secret or `.env` (Wiz; now a hard block). Opening `ssh` and `claude auth login` in a terminal, installing scripts remotely, and calling a publisher-owned error endpoint are all "network to unknown host + child_process" patterns to a static scanner. Nothing in the record suggests these are prohibited; the record suggests they are exactly what draws a manual review, and that the manual review reads the README and repository.
- The nuBond case is the closest analogue to a "minified but not obfuscated" extension and it was blocked. The distinguishing factors a reviewer can check are a source map, a reachable repository, and a build that does not synthesise packages into `node_modules`.
- Because removal is followed by a client-side forced uninstall and a 30-day cooldown that support cited but that no public document describes, the cost of a false positive is a month of downtime plus reputational damage to the publisher id; this argues for pre-empting review rather than litigating after it.

- No Microsoft document defines "obfuscation" or draws the minification line; the March 2025 post explicitly did not.
- The "mandatory 30-day cooldown" cited in issue #2204 is not documented anywhere I could retrieve.
- The OX Security "verified symbol" research (modified VSIX retaining the verified badge) and the MDSec May 2026 "Visual Studio Extensions Revisited" post could not be fetched (domains blocked); Checkmarx's takedown-process post likewise. Their claims are therefore not included.
- Whether publisher (author) signing has shipped could not be confirmed; only the 2022-2023 plan was retrievable.

## Key Question 4 — Practices that keep a listing up, and how appeals actually work

### Takeaway
The publisher-controllable levers that appear in Microsoft's own guidance are: verified publisher domain (kept current), unique name/icon, a reachable repository and README that match the code, an included license/EULA, no secrets in the package, no obfuscation, no unnecessary files, least-privilege publisher membership, and prompt replies to vsmarketplace@microsoft.com. There is no published appeal procedure; the de facto path is email to vsmarketplace@microsoft.com (and vsmagent@microsoft.com) with publisher id, extension id, the action attempted and correlation IDs, plus a public issue on github.com/microsoft/vsmarketplace. Support has cited a "mandatory 30-day cooldown" before reconsidering a blocked publisher, and has told multiple publishers "we do not provide further details".

### Cited Findings

- [PRACTICE] Microsoft's published Do/Don't list (11 Jun 2025): verified publisher; unique display names and images; update repository links and README when forking; include license/EULA; review packaged files for secrets; latest vsce; minimum-privilege roles; audit account members; avoid obfuscation; don't duplicate repository links/logos; don't ship unnecessary code. — [developer.microsoft.com blog](https://developer.microsoft.com/blog/security-and-trust-in-visual-studio-marketplace/)
- [PRACTICE] Appeal channel per blog comments: contact vsmarketplace@microsoft.com with publisher and extension IDs; commenters report "generic policy responses without specific violation details" and a statement that "we will not be reinstat[ing]". — [same, comments](https://developer.microsoft.com/blog/security-and-trust-in-visual-studio-marketplace/)
- [PRACTICE] July 2026 announcements name the fields to include when appealing an automated block: publisher name, attempted action, timestamps/correlation IDs (account block); extension name, publisher name, relationship to the brand (impersonation block); support "will review the case and work with you to determine the appropriate path forward". — [vsmarketplace #2036](https://github.com/microsoft/vsmarketplace/discussions/2036); [vsmarketplace #2042](https://github.com/microsoft/vsmarketplace/discussions/2042)
- [PRACTICE] Observed 2026 outcomes: nuBond — removal 24 h after first publish, two boilerplate replies, three unanswered follow-ups; transitrix — 30-day cooldown observed, then "blocked ... would not be reinstated" with no evidence; hassansayed — no reply. — [issue #2152](https://github.com/microsoft/vsmarketplace/issues/2152); [issue #2204](https://github.com/microsoft/vsmarketplace/issues/2204); [issue #2197](https://github.com/microsoft/vsmarketplace/issues/2197)
- [PRACTICE] A "one-time restore" of a deleted extension name was granted after email in one documented case. — [vsmarketplace #1708](https://github.com/microsoft/vsmarketplace/discussions/1708)
- [RULE] Publishers must "report suspected security events ... at the earliest opportunity" (PA §8(d); PP §6) and "promptly respond" to referred IP claims (PA §3(h)); paid-offering publishers must give Microsoft e-mail and telephone support contacts and "use best efforts to respond to any inquiry received by Microsoft" (PA §6(c)). — [Publisher Agreement](https://cdn.vsassets.io/v/M261_20250904.11/_content/Visual-Studio-Marketplace-Publisher-Agreement.pdf)
- [RULE] `repository` may be omitted only with `--allow-missing-repository`; the docs say `bugs`, `homepage`, `repository` populate the Marketplace "Resources" section; the runtime-security doc tells users to check "Repository, issues tracker, and license availability" before installing. — [vsce package.ts](https://raw.githubusercontent.com/microsoft/vscode-vsce/main/src/package.ts); [Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest); [Extension runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security)
- [PRACTICE] ExtensionTotal counted 2,304 extensions "using another publisher's GitHub repository" as a risk signal, and Microsoft's Don'ts include "Don't duplicate repository links". — [BleepingComputer 2024](https://www.bleepingcomputer.com/news/security/malicious-vscode-extensions-with-millions-of-installs-discovered/); [developer.microsoft.com blog](https://developer.microsoft.com/blog/security-and-trust-in-visual-studio-marketplace/)
- [PRACTICE] Secrets: since 22 Sep 2025 a live secret blocks publication; vsce ships `@secretlint`-based scanning with explicit bypass flags; Wiz's publisher advice is to scan before publishing, exclude `.env` and dotfiles, and review build artefacts. — [vsmarketplace #1442](https://github.com/microsoft/vsmarketplace/discussions/1442); [vsce package.ts](https://raw.githubusercontent.com/microsoft/vscode-vsce/main/src/package.ts); [Wiz](https://www.wiz.io/blog/supply-chain-risk-in-vscode-extension-marketplaces)
- [PRACTICE] Open VSX as a second channel: Eclipse removes for any reason without notice (§3(c)), requires a full data-collection disclosure in the listing (§6), defaults to MIT if no license is given (§4(a)), and since Oct 2025 runs automated scanning at publication and has announced mandatory pre-publish security checks; security contact openvsx@eclipse-foundation.org. — [Open VSX Publisher Agreement](https://www.eclipse.org/legal/documents/eclipse-openvsx-publisher-agreement.pdf); [Eclipse blog Oct 2025](https://blogs.eclipse.org/post/mika%C3%ABl-barbero/open-vsx-security-update-october-2025)
- [PRACTICE] GlassWorm's Open VSX variant weaponised `extensionPack`/`extensionDependencies` to pull a second extension after trust was established, so reviewers now treat late-added dependencies as a signal. — [Socket](https://socket.dev/blog/open-vsx-transitive-glassworm-campaign)
- [PRACTICE] For institutional deployment there is a VS Code Private Marketplace (announced 18 Nov 2025) and the `extensions.allowed` policy, both of which bypass public-listing risk for a known user base. — [VS Code blog](https://code.visualstudio.com/blogs/2025/11/18/PrivateMarketplace); [Enterprise extensions](https://code.visualstudio.com/docs/enterprise/extensions)

### Inferences — a checklist assembled from the findings above (each item traces to a cited source in this file)

Listing and manifest
1. `pricing: "Trial"` (only `Free`/`Trial` are legal values); state the trial length, what happens at expiry, and where the licence is bought, at the top of the README and of the description (ToU CoC v; PP §4 Free Trial row).
2. Ship a LICENSE file and set `license: "SEE LICENSE IN LICENSE"`; link the EULA in the listing even though BYOL is exempt (PA §4(c); ToU §1; Microsoft "Include license/EULA documentation").
3. Publish a privacy-policy URL in the README and as `homepage` or in the description — mandatory because error reports and tokens are Personal Data transmitted to the publisher (PA §8(b)(ii); PP §3(a)(7)).
4. Set `repository`, `bugs`, `homepage`, `qna` to reachable, publisher-owned pages; never reuse someone else's repository; do not use `--allow-missing-repository` (vsce; Microsoft Don'ts; ExtensionTotal heuristic).
5. Declare `capabilities.untrustedWorkspaces` with `supported: false` or `"limited"` and a `description` explaining that the extension opens terminals, runs `ssh`, and installs files on a remote host (workspace-trust guide).
6. Set `extensionKind` deliberately (`ui` if the extension must run on the local machine to reach SecretStorage and the local terminal).
7. Icon: PNG ≥128 px, not SVG; README images HTTPS and non-SVG; badges only from the allow-list; no Microsoft/GitHub logos, and no "Microsoft", "GitHub", "Copilot" in the name (vsce; ToU §10(b)).
8. Add `CHANGELOG.md` and keep the "detailed technical documentation" the Policies require (PP §1(i)).
9. Choose a name and icon that do not resemble Remote-SSH, Claude Code, Anthropic, GitHub or any existing extension; the July 2026 impersonation filter checks "branding, icons, names, URLs".
10. Do not mention or link competing IDEs/editors in the listing or the install flow (PP §3(b)).

Package contents
11. No secrets, `.env`, `mcp.json` with tokens, or build scripts in the VSIX; run the current vsce and do not pass `--allow-package-secrets` (Sep 2025 blocking; Wiz).
12. Minify if you must, but ship source maps, avoid dynamic `require()`, `eval`, `new Function`, `require("inspector")`, and do not generate packages into `node_modules` at build time (nuBond; Material Theme).
13. Keep platform-specific binaries out of the package unless each platform build passes validation; a single failing platform triggered a "Malware" removal (transitrix).
14. Do not add `extensionPack`/`extensionDependencies` in a later update without explaining them in the changelog (GlassWorm transitive loaders).
15. No `*` activation; keep the file count small (vsce warnings).

Behaviour and disclosure
16. Put a "What this extension accesses and does" section at the top of the README and description: Microsoft/GitHub auth providers used, tokens stored in SecretStorage and copied over SSH to the user's own account, terminals that run `ssh` and `claude auth login`, scripts installed remotely, Slurm jobs, the MCP server registered with Claude Code, the opt-out error reporter (endpoint, fields, retention, how to disable), the licence-key check and revocation-list fetch (endpoint, what is sent). This is what PA §8(d) ("identified in ... the Listing Information") and ToU CoC v ("clearly documented at the top of both the package description and package README") require, and what the Open VSX §6 disclosure needs anyway.
17. Every notification the extension shows must be clearly from the publisher, not Microsoft (PP §1(d)); never change Microsoft-managed settings (PP §1(e)).
18. Make error reporting a visible setting, default state stated in the README; consider opt-in for the first release (no rule requires opt-in; PA §8(b)(ii) requires the policy).
19. Fetch the revocation list and post error reports only to a host named in the README, over HTTPS, with no code download; never download-and-execute (BigBlack `curl` pattern; Material Theme child-process flag).

Publisher account and response
20. Verify the publisher domain as soon as the six-month clocks allow, keep the domain registered ("Expired Domain" is a removal category), and never change the publisher display name afterwards (it revokes the badge).
21. Least-privilege members; audit them; use a dedicated PAT or trusted publishing (Microsoft Do's; Wiz PAT leaks).
22. Monitor vsmarketplace@microsoft.com / vsmagent@microsoft.com and the Publishing Portal contact daily; respond the same business day to any Microsoft inquiry (PA §6(c) "best efforts"); report your own security incidents first (PP §6).
23. If removed: email both aliases with publisher id, extension id, version, correlation IDs and a remediation summary; open a public issue on github.com/microsoft/vsmarketplace; expect a 30-day cooldown; do not delete the extension (deleted names are lost — unpublish instead).
24. Publish to Open VSX in parallel with the same README, a stated licence (else MIT applies), and the §6 data disclosure; keep an installable VSIX on your own site with its SHA-256 so users can sideload during any outage.

### Gaps
- No public SLA exists for appeal handling; the 30-day cooldown is undocumented.
- Whether a private (404) `repository` URL is itself a flag is not stated by Microsoft; the evidence is indirect (Microsoft tells users to check the repository; ExtensionTotal flags mismatched repositories; vsce only checks presence, not reachability).
- Reproducible/SHA-pinned builds are not mentioned in any Microsoft document retrieved; they appear only in publisher remediation narratives (transitrix's "build attestations"), and there is no evidence they influenced the outcome.

## Key Question 5 — Trust signals VS Code and the Marketplace show users, and how to obtain them

### Takeaway
The signals are the blue verified-publisher check with the verified domain shown "alongside the publisher name in the VS Code search results, in the extension details, and on the Marketplace website"; install counts; ratings and reviews; Q&A responsiveness; the Resources block (repository, issues, license); the Marketplace signature (checked on install); and, since VS Code 1.97, a first-install publisher-trust dialog. Verification requires an extension on the Marketplace for six months, a domain registered for six months, a DNS TXT record, and a manual review "within 5 business days" covering "track record, content eligibility, legitimacy, trust and positive reputation"; changing the publisher display name revokes it.

### Cited Findings

- [RULE] Prerequisites: "one or more extensions on the VS Marketplace for a minimum of 6 months, and the registration of the domain must also be at least 6 months old." Process: enter the domain on the publisher Details tab, add the TXT record, click Verify; "Once your TXT record has been validated, the Marketplace team will review your request and let you know the result within 5 business days", including "validation of domain, website and extensions prerequisites for track record, content eligibility, legitimacy, trust and positive reputation"; "the Marketplace will add a verified badge to your extension details"; "any changes to the publisher display name will revoke the verified badge." — [Publishing Extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)
- [PRACTICE] Where it shows: the verified domain "will be displayed alongside the publisher name in the VS Code search results, in the extension details, and on the Marketplace website"; the TXT record can be removed after verification. — [vscode issue #127825](https://github.com/microsoft/vscode/issues/127825); [vscode-discussions #29](https://github.com/microsoft/vscode-discussions/discussions/29)
- [PRACTICE] June 2025 blog: the verified badge now carries "higher verification standards requiring 6+ months of good standing". — [developer.microsoft.com blog](https://developer.microsoft.com/blog/security-and-trust-in-visual-studio-marketplace/)
- [PRACTICE] What VS Code tells users to check: "Ratings and community reviews", "Q&A section and publisher responsiveness", "Repository, issues tracker, and license availability", "Verified publisher status with blue check mark and domain verification"; VS Code 1.97+ trust dialog on first install from a third-party publisher; CLI installs do not auto-trust. — [Extension runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security)
- [PRACTICE] Signature: "The Visual Studio Marketplace signs all extensions when they're published. VS Code checks this signature when you install an extension." Users can disable the check with `extensions.verifySignature`. — [Extension runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security); [vscode issue #270269](https://github.com/microsoft/vscode/issues/270269)
- [RULE] Ratings may not be manipulated: "You may not attempt to manipulate rankings, ratings or comments for your Offering or any other Offering" (PA §3(j)); ToU CoC v forbids "download inflation". — [Publisher Agreement](https://cdn.vsassets.io/v/M261_20250904.11/_content/Visual-Studio-Marketplace-Publisher-Agreement.pdf); [Terms of Use](https://cdn.vsassets.io/v/M264_20251020.18/_content/Microsoft-Visual-Studio-Marketplace-Terms-of-Use.pdf)
- [REPORT] The verified badge is a domain-ownership signal, not a code-safety signal: the 2024 Darcula case obtained it with a freshly registered domain (the six-month domain rule postdates that case). — [BleepingComputer 2024](https://www.bleepingcomputer.com/news/security/malicious-vscode-extensions-with-millions-of-installs-discovered/)
- [PRACTICE] A publisher planning ahead can see the clock in practice: one project tracks "verify publisher domain once eligible (~March 2027)". — [grounder issue #118](https://github.com/andrej-kolic/grounder/issues/118)

### Inferences
- A brand-new publisher cannot be verified for six months; during that window the substitutes are a reachable repository, a real support/Q&A channel, an explicit access disclosure, and reviews. Register (or reuse) the publisher and publish a first release early so the six-month clock starts.
- Because the badge is revoked by a display-name change, decide the publisher display name before publishing.

### Gaps
- The OX Security finding on badge retention by modified VSIX packages was not retrievable.
- The exact wording of the VS Code 1.97 trust dialog and of the "Publisher domain verified" tooltip was not captured verbatim.

## Key Question 6 — Third-party browser logins, copying tokens to a remote machine, and how comparable extensions disclose credentials

### Takeaway
No Marketplace document mentions opening a browser for a third-party login, invoking another vendor's CLI (`claude auth login`), or copying tokens to a user-controlled remote host. The applicable rules are general: the behaviour must be "identified in or may reasonably be expected from the Listing Information" (PA §8(d)), a privacy policy is required if Personal Data is transmitted (PA §8(b)(ii)), the publisher warrants it has any consents needed for the Offering "to access any Internet-based ... services" (PA §10(d)), and unexpected behaviour must be documented at the top of the description and README (ToU CoC v). Remote-SSH's own documentation is the model: it says exactly what is installed on the remote host and states that "Passwords and other tokens entered for alternate authentication methods are not saved."

### Cited Findings

- [RULE] PA §8(d): the Offering "must not install or launch executable code on the user's environment beyond what is identified in or may reasonably be expected from the Listing Information". — [Publisher Agreement](https://cdn.vsassets.io/v/M261_20250904.11/_content/Visual-Studio-Marketplace-Publisher-Agreement.pdf)
- [RULE] PA §10(d): warranty of "consents, approvals, or licenses ... required ... for your Offering to access any Internet-based or Microsoft-provided services, if any, to which the Offering enables access". — [same](https://cdn.vsassets.io/v/M261_20250904.11/_content/Visual-Studio-Marketplace-Publisher-Agreement.pdf)
- [RULE] Open VSX §6/§8(a): full disclosure of data collected, purposes, sharing, retention; warranty of no undisclosed collection. — [Open VSX Publisher Agreement](https://www.eclipse.org/legal/documents/eclipse-openvsx-publisher-agreement.pdf)
- [PRACTICE] Remote-SSH documentation: "The extension will install VS Code Server on the remote OS; the server is independent of any existing VS Code installation on the remote OS."; "Passwords and other tokens entered for alternate authentication methods are not saved."; "Using key based authentication is recommended."; communication is "through the authenticated, secure SSH tunnel"; it lists the outbound hosts required (update.code.visualstudio.com, vscode.download.prss.microsoft.com, marketplace.visualstudio.com). — [Remote Development using SSH](https://code.visualstudio.com/docs/remote/ssh)
- [PRACTICE] GitLens Marketplace README: licence split stated in the listing ("All files in or under any directory named 'plus' fall under LICENSE.plus. The remaining files fall under the MIT license."); sign-in framed as "a free GitKraken account opens the Commit Graph on your public repos, and starts your trial if you want it everywhere"; pricing shown as "GitLens Community is free and open-source, forever" and "Start your free 14-day Pro trial — no credit card required"; the README itself has no telemetry section — that lives on GitKraken's security page, which tabulates data per feature (e.g. Launchpad: "URLs of issues and pull requests (for pin/snooze functionality only)"; Cloud Patches: "Patch metadata ... and patch content") with "Encrypted with TLS" in transit and "AES-256" at rest. — [GitLens listing](https://marketplace.visualstudio.com/items?itemName=eamodio.gitlens); [GitLens Security Information](https://help.gitkraken.com/gitlens/gl-security/)
- [PRACTICE] Tabnine's legacy listing (`TabNine.tabnine-vscode`) is marked "Free", says "Tabnine does not onboard new users to this plugin", and shows no privacy or EULA text in the README body. — [Tabnine listing](https://marketplace.visualstudio.com/items?itemName=TabNine.tabnine-vscode)
- [PRACTICE] Example of a small extension's own disclosure language (from a public repo, not a Marketplace policy): it "uses VS Code SecretStorage for account bearer tokens, keeps workspace-session keys in memory, and implements no independent product telemetry". — [BlackHole-core README](https://github.com/qianshe/BlackHole-core)
- [PRACTICE] Microsoft's own scanners treat network calls to hardcoded IPs and "running unknown executables" as risk heuristics (ExtensionTotal counts), and its Do's include "Update repository links and readme". — [BleepingComputer 2024](https://www.bleepingcomputer.com/news/security/malicious-vscode-extensions-with-millions-of-installs-discovered/); [developer.microsoft.com blog](https://developer.microsoft.com/blog/security-and-trust-in-visual-studio-marketplace/)

### Inferences
- Copying a token the user obtained via VS Code's Microsoft/GitHub auth provider into the user's own HPC account is, from the Marketplace's point of view, a disclosure question under §8(d) and a consent question under §10(d) (the token issuers' terms, not Microsoft Marketplace's, govern whether the token may be moved). Anthropic's terms for `claude auth login` were outside this research's scope and were not checked.
- The Remote-SSH pattern — name the remote artefacts (path, what they are, how to remove them) and state what is *not* stored — is the disclosure format a reviewer will already recognise.
- Continue's telemetry page could not be loaded; Codeium's listing was not fetched; no comparator was found that discloses copying credentials to a remote host, so the extension would be first-of-kind on that point and should over-document it.

### Gaps
- No Microsoft policy text on third-party login flows or token relocation exists in the documents retrieved; absence of a rule is the finding.
- Continue (docs.continue.dev/telemetry redirected to an empty page), Codeium, and the current Tabnine listing were not examined.
- The Anthropic Consumer/Commercial terms governing `claude auth login` automation were not researched here.

## Key Question 7 — Pre-sale disclosures, privacy policy and EULA placement for paid/trial offerings

### Takeaway
Three placement rules apply. Pre-sale consumer disclosures required by law go "in the Offering description field" unless elsewhere in the Listing Information (PA §6(b)). The EULA (or a link) "must be delivered to Microsoft for publication as part of the Offering's Listing Information" except for BYOL offerings, and if none is given a non-BYOL offering defaults to the Microsoft Standard Agreement (PA §4(c); ToU §1) — whose link is currently dead. Terms and privacy policy should be "in a prominent location, such as a license file or an embedded readme file" (ToU §1), and any behaviour a user would not expect must be "clearly documented at the top of both the package description and package README" (ToU §4(v)). Free Trial SKUs must carry any subscription restrictions in the publisher's own Terms of Use (PP §4).

### Cited Findings

- [RULE] PA §6(b): pre-sale disclosures "in the Offering description field (unless they are provided elsewhere in an Offering's Listing Information) ... sufficiently prominent as is required by local law"; the listing "may include your full contact information and information about in-Offering purchases". — [Publisher Agreement](https://cdn.vsassets.io/v/M261_20250904.11/_content/Visual-Studio-Marketplace-Publisher-Agreement.pdf)
- [RULE] PA §4(c): own EULA or Microsoft Standard Agreement; default applies to non-BYOL offerings published on or after the Agreement's "Last Updated" date; "Except for BYOL Offerings, any license agreement ... or a link to them, must be delivered to Microsoft for publication as part of the Offering's Listing Information." — [same](https://cdn.vsassets.io/v/M261_20250904.11/_content/Visual-Studio-Marketplace-Publisher-Agreement.pdf)
- [RULE] PA §8(b)(ii): privacy policy mandatory when Personal Data is accessed, collected or transmitted; publisher must inform Customers "including by submitting that policy to us for display to Customers". — [same](https://cdn.vsassets.io/v/M261_20250904.11/_content/Visual-Studio-Marketplace-Publisher-Agreement.pdf)
- [RULE] PP §3(a): Listing Information items "(3) Pricing model", "(4) Link to customer support details" (support required for paid, non-preview offerings), "(6) Terms of Use (unless the Microsoft Standard Contract is elected or the Offering is a BYOL Offering)", "(7) Privacy Policy". — [Participation Policies](https://cdn.vsassets.io/v/M187_20210610.3/_content/Visual-Studio-Marketplace-Participation-Policies.pdf)
- [RULE] PP §4 Free Trial row: publisher "is responsible for setting up billing and collection of user fees after the trial period outside of the Marketplace"; "Publishers who wish to restrict the number of subscriptions customers may create for Free Trial offerings are responsible for including appropriate restrictions in their Terms of Use." — [same](https://cdn.vsassets.io/v/M187_20210610.3/_content/Visual-Studio-Marketplace-Participation-Policies.pdf)
- [RULE] ToU §1: "include the terms (including a privacy policy, if applicable) in a prominent location, such as a license file or an embedded readme file. If no terms are included and the offering is not a BYOL offering, then the Microsoft Standard Agreement terms will apply." ToU §4(v): behaviour must be "clearly documented at the top of both the package description and package README". — [Terms of Use](https://cdn.vsassets.io/v/M264_20251020.18/_content/Microsoft-Visual-Studio-Marketplace-Terms-of-Use.pdf)
- [RULE] Manifest: `pricing` is the only pricing field and takes `Free` or `Trial`; the Marketplace displays it as a label; `sponsor.url` is the only other monetisation field. — [Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest); [Publishing Extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)
- [PRACTICE] GitLens states its licence split and trial terms in the README body itself ("14-day Pro trial — no credit card required"). — [GitLens listing](https://marketplace.visualstudio.com/items?itemName=eamodio.gitlens)
- [PRACTICE] The Standard Agreement link in PA §4(c) (https://aka.ms/vsm-standard-agreement) resolves to a Bing search page (302) as of 2026-09-28. — [aka.ms/vsm-standard-agreement](https://aka.ms/vsm-standard-agreement)
- [RULE] Open VSX: if no licence is specified the offering "will be made available under the MIT license" (§4(a)) — a trap for a proprietary BYOL extension mirrored there. — [Open VSX Publisher Agreement](https://www.eclipse.org/legal/documents/eclipse-openvsx-publisher-agreement.pdf)

### Inferences
- There is no rule that the EULA text must appear *in* the description; a link in the Listing Information satisfies PA §4(c). The prudent layout is: first screen of README and description = pricing model, trial terms, licence link, privacy-policy link, and the access disclosure; LICENSE file in the package; `license: "SEE LICENSE IN LICENSE"`.
- A BYOL/Trial extension must supply its own terms in any case, because the default that would otherwise apply (Standard Agreement) is currently unreachable and Open VSX's default is MIT.

### Gaps
- The Microsoft Standard Agreement's content and whether it permits licence-key gating were not retrievable.
- No Microsoft document specifies a required wording or position for the `Trial` label beyond the manifest value; how the Marketplace UI renders it was not captured.
